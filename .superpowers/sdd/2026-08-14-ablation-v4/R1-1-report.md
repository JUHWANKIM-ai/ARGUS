## 1. Step 0a — `_EQUATION_RE` 가 굵게 감싼 등식 결과를 못 봤다

### 정규식 전 / 후

```python
# 전
_EQUATION_RE = re.compile(rf"({_EQ_NUM})((?:\s*{_EQ_OP}\s*{_EQ_NUM})+)\s*=\s*({_EQ_NUM})")
#                                                                        ~~~~~
# 후
_EQUATION_RE = re.compile(rf"({_EQ_NUM})((?:\s*{_EQ_OP}\s*{_EQ_NUM})+)\s*=[\s*_]*({_EQ_NUM})")
#                                                                        ~~~~~~~~
```

**바뀐 것은 `\s*` → `[\s*_]*` 하나다** (`=` 뒤). 선례를 그대로 따랐다 — 같은 파일의
`_RESTATE_OPEN = re.compile(r"^[\s*_]*\($")` 이 이미 같은 이유로 같은 문자류를 쓴다.

### 무엇을 못 봤나

실측 `Q-107`(밸류체인 · `vc/A8`)의 답변:

```
- 1,250,850,298,678 + 2,081,254,239,072 + 1,715,754,987,100 = **4,967,110,535,840원**
```

좌변합 **5,047,859,524,850** vs 우변 **4,967,110,535,840** — **덧셈이 실제로 틀렸다.**
그런데 `=` 뒤의 `**` 때문에 정규식이 **아예 매치하지 않았고**, `checked` 에 `equation` 이
실리지 않았다. 즉 *"사슬이 끊겨서 정당하게 안 본 것"* 과 구별되지 않는 침묵이었다.

## 3. `recomputed` 필드의 최종 규격

```python
# verify_calculation(answer, evidence) -> dict
#   "recomputed": dict[str, float]          # 검사 종류 -> 재계산값. 없으면 {}
# verify_answer_arithmetic(answer) -> dict
#   "recomputed": dict[str, float]          # 같은 규격 (equation 만 실린다)
# aggregate_calculation(reports) -> dict
#   "recomputed": dict[str, float] | None   # 🔴 유일하지 않으면 None
```

### 실릴 조건이 둘이다 (`critic._recomputed`)

| 조건 | 왜 |
|---|---|
| ① 기대값이 **수치**다 | `period` 의 기대값은 `"8년 5개월"` 이라 갈아 끼울 수가 없다 |
| ② 답변에서 **바꿀 자리**(`targets`)를 못 박았다 | `restatement` 는 원값과 괄호 환산값 중 어느 쪽이 틀린지 검사가 **모른다** |

🔴 **`restatement` 를 뺀 근거는 실측 두 건이 방향이 반대라는 것이다.** `Q-018` 은
**괄호가 옳고**(1조 8,422억원) 원값 13자리에서 한 자리가 틀렸다. `Q-110` 은 **원값이
옳고**(590,947,351,842원) 괄호 환산이 10배 틀렸다(591억 → 실제 5,909억). 어느 쪽을
정본으로 치환해도 절반은 파괴한다. 계획서도 `Q-018` 을 `A15` 로 돌려 뒀다.

### 곁딸린 규격 — 불일치 레코드의 `targets`

`mismatches[*]` 에 `"targets": list[str]` 이 추가됐다 (기존 키는 그대로 · `reason` 형식
불변). **답변에서 갈아 끼울 원문 조각**이고, `_compare` 는 기대값과 로그10 거리가
`SUBSTITUTE_LOG_TOLERANCE=0.05`(±12%) 안인 후보를 **전부** 싣는다.

🔴 **왜 하나가 아닌가** — 실측 `Q-097` 의 답변은 **같은 값을 두 표기로** 쓴다.

```
- 1척 당 평균 투자금액 = 207,848,465,710원      ← 채점이 보는 자리 (원 단위 13자리)
따라서 … 약 2,078억 원입니다.                   ← _compare 가 보고하는 자리 (기대값에 더 가깝다)
```

보고된 `2,078억` 만 고치면 **채점은 그대로 오답**이다(골든 `207,684,631,210` · tolerance 0).
둘을 함께 고쳐야 Δ 가 선다. 총액 `2,492,215,574,520원` 은 기대값의 12배(로그10 거리 1.08)
로 창 밖이라 건드리지 않는다.

> 🔴 **구현 중에 이 자리에서 버그를 하나 잡았다.** 처음에는 배율을 불일치 레코드의
> `claimed_value` 로 나눠 구했는데, `targets` 에는 `claimed` 아닌 표기도 들어 있어서
> 배율이 1 이 아니라 0.99977 로 잡혔고 `207,733,070,012원` 이라는 **미묘하게 어긋난
> 값**이 찍혔다 — 채점은 여전히 오답이었다. 배율은 `target` 자신의 단위 표지에서 읽어야
> 한다(`critic._rendered`). 고친 뒤 `Q-097` 이 정확히 골든으로 치환된다.

### 🔴 계획서의 "+3건" 추정은 성립하지 않았다

계획서는 *"확정 2건 + 배선하면 3건 더"* 로 5건을 추정했다. 실측 결과 **배선이 발화를 3건
늘리는 것은 맞다**(`Q-044`·`Q-109`·`Q-115` 계열). 그러나 **밸류체인 합산 문항은 치환이
일어나지 않는다** — `vc/A8` 의 `Q-107`·`Q-109`·`Q-110`·`Q-115` 넷 다 유일성 판정이 `None`
이다. 레코드마다 `amount` 재계산값이 다르기 때문이다.

**그리고 그것이 옳다.** `Q-107` 은 근거 3건의 계약금액을 **더한 것이 맞고** 덧셈만 틀렸다
(좌변합 5,047,859,524,850). 레코드 단위 `amount` 검사는 그 사실을 모르고 *"답변 금액이 한
레코드 금액의 10배다"* 라고 말한다 — 무조건 치환하면 정당한 합계 4,967,110,535,840원을
**한 레코드의 490,881,723,100원으로 갈아엎는다.** 계획서가 *"유일성 조건이 필수"* 라고 못박은
자리가 정확히 여기다. **`explained` 관용과 같은 이유로 존재하는 조건이 실제로 하중을 받았다.**

### 측정 시점의 한계 두 가지

1. **`R2` 의 Δ 와 같지 않다.** 위 수치는 v3 저장 답변에 `_verify` 를 다시 태운 것이다.
   `A20` arm 을 실제로 돌리면 답변 생성은 캐시 적중이라 같은 답변이 오지만, `--force`
   재생성이 끼면 값이 움직일 수 있다.
2. **서술형 2건은 0원으로 잴 수 없다.** `A8-lean/Q-023`(`amount: 1,102,000,000,000원 →
   1,013,700,000,000원`)과 `L1/Q-024`(금액 3자리 치환)는 `answer_form=narrative` 라 유료
   개방형 judge 가 있어야 정오가 갈린다. **둘 다 제출 구성(`A8`)이 아닌 arm 이고**, `A8`
   에서 본문이 바뀐 것은 `Q-044`·`Q-097` 둘 뿐이며 **둘 다 `number_won` 폐쇄형**이다.

## 7. 다음 라운드가 알아야 할 것

- 🔴 **`A20` arm 이 `ablation.ARMS`·`RUN_ORDER` 에 등록돼 있지 않다.** 계획서 Step 6 은
  플래그만 지시했고 arm 등록은 `R2` 몫이다. `A20 = replace(A8, name="A20",
  substitute_verified=True)` 이고 **사다리도 LOO 도 아닌 곁가지**(`SIDE_ARMS` 자리 ·
  `A8-lean` 과 같은 취급)다. 등록하지 않으면 `--arm A20` 이 안 돈다.
- 🔴 **`substitute_recomputed` 는 한 번만 돈다.** 한 답변에서 종류가 둘 이상 발화하면
  (실측 `vc/ORACLE/Q-115`: `amount` + `equation`) `amount` 치환이 등식 좌변을 바꿔 놓아
  등식 총계가 낡는다. 664건에서 이 겹침은 **1건**이고 그 문항은 치환 전후 모두 오답이다.
  되풀이해 수렴시키지 않은 이유는 통제 변수다 — 그러면 재는 것이 '치환' 이 아니라
  '반복 교정' 이 된다. `R1-2`(`A20r`)가 재생성 축을 따로 잰다.
- **`A20r`(`R1-2`)이 바로 쓸 수 있는 것**: `agg["recomputed"]`·`agg["failed"]` 와
  `unique_recomputed(reports + arith_reports)` 가 이미 서 있다.
- **`Q-018` 은 `A20` 이 못 고친다** — `restatement` 의 치환 자리가 정의되지 않는다(§3).
  `A15`(원값↔환산값 배율 대조) 몫으로 남는다.
- 게이트 문서(`docs/pipeline/09-ablation.md`)의 플래그 표에 `substitute_verified` 칸이
  자동으로 생긴다(`FLAG_NAMES` 파생). 문서 정본 갱신은 다른 트랙 몫이라 건드리지 않았다.
