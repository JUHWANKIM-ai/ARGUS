# 🔴 §1. 먼저 arity 판정 — **HyperGraphRAG 의 전제가 우리 데이터에 안 맞는다**

계획서 `R2-3a` 가 지시한 0원 사전 점검이다. **LLM 0회 · 지출 0원**
(`scripts/build_nary.py --arity`).

`arity = 1(주체 = 공시 기업) + 실제로 값이 채워진 논항 수`. 논항 넷은 `T1` 이 뽑으려는
것과 같다 — 계약상대 · 계약금액 · 계약기간 · 대상. **라벨만 있고 값이 `-` 인 칸은
세지 않는다** — 유보 서식이 라벨을 전부 갖고 있어서 라벨로 세면 arity 가 통째로 부풀려진다.

## 판정: 🔴 **arity ≤ 2 가 과반(58.4%)이다. 논문의 전제가 안 맞는다**

```
schema_matched=False 238건 (exchange 233 · major 5 · holding 0)

  arity 1      1건 (  0.4%)
  arity 2    138건 ( 58.0%)     ← 이항 관계. 일반 그래프로 그대로 표현된다
  arity 3     64건 ( 26.9%)
  arity 4     21건 (  8.8%)
  arity 5     14건 (  5.9%)

  🔴 arity >= 3   99건 (41.6%)
     arity <= 2  139건 (58.4%)
```

HyperGraphRAG 자신의 ablation 이 **"arity ≤ 2 면 하이퍼그래프의 이득이 0"** 을 보고한다.
우리 `T1` 대상의 58.4% 가 정확히 그 구간이다.

## 🔴 그런데 진짜 결론은 대조군에 있다 — **n-ary 는 규칙이 이미 먹었다**

```
                          arity >= 3 비율
schema_matched=False 238    41.6%      ← T1 이 겨냥하는 곳
schema_matched=True 1,829   84.2%      ← 규칙이 이미 구조화한 곳
```

**규칙이 성공한 레코드가 실패한 레코드보다 2배 더 n-ary 다.** 즉 우리 코퍼스에서
고차 관계는 `T1` 이 회수할 미지의 영역이 아니라 **규칙이 이미 먹어치운 영역**이다.
`T1` 에 남은 238건은 그 반대쪽 — 논항이 애초에 둘뿐인 잔반이다.

(대조군을 exchange+major 로 좁혔다. holding 1,083건은 지분보고라 계약 논항이 아예
없어 arity 1 이 대부분이고, 섞으면 대조군 arity 가 통째로 내려가 **없는 차이를 만든다.**)

## 그리고 arity 가 높은 쪽은 **손해만 낼 자리**다

```
버킷                건   arity>=3   뜻
open (withheld=F)  171    21.1%    금액 칸이 서식에 없거나 원문에도 값이 없다
withheld=True       67    94.0%    🔴 발행사가 의도적으로 비공개한 것
```

**유보 67건의 94% 가 arity ≥ 3 이다.** 라벨(계약상대·기간·대상)은 다 있고 **금액만
`-` 로 비어 있기** 때문이다. 즉 238건에서 "n-ary 구조가 살아 있는 곳" 은 대부분
`T1` 이 회수할 곳이 아니라 `R0-1` 이 *"손해만 낼 여지"* 로 지목한 바로 그 67건이다.

## 🔴 그래서 `A18` 을 재는 이유가 격상된다

계획서 `R2-3a` 의 문장 그대로다 — 이것으로 `A18` 은 *"논문 아이디어라서 재는 것"* 이
아니라 **"논문의 전제가 우리 데이터에 맞는지 재서 기각하는 것"** 이 된다.
제안서 `§7` 이 쓸 문장은 이것이다:

> HyperGraphRAG 는 n-ary 관계가 이항으로 분해되면 이득이 사라진다고 스스로 보고한다.
> 우리 코퍼스에서 규칙이 파싱하지 못한 238건은 **58.4% 가 arity ≤ 2** 이고, 반대로
> 규칙이 성공한 1,829건은 **84.2% 가 arity ≥ 3** 이다. 고차 관계는 이미 결정적으로
> 구조화돼 있고, 하이퍼그래프 추출에 남은 것은 이항 잔반이다.

# 🔴 §3. 추출 중에 도구 결함 둘을 잡았다 — **안 잡았으면 Δ=0 이 거짓이 됐다**

이 절이 이 라운드에서 가장 값진 부분이다. 둘 다 **"추출기가 못 뽑은 것"** 을
**"뽑을 것이 없었다"** 로 보고할 뻔했다.

## ① `"["` 한 글자 — 238건 중 **135건**(56.7%)

첫 판은 최상위를 **JSON 배열**로 요구했다. HCX-005 가 135건에 **`"["` 한 글자만**
돌려주고 `finishReason=stop` 으로 끝냈다. 파싱 사유를 `parse_error` 로 남겨 두지
않았다면 이것이 그대로 *"뽑을 값이 없다"* 로 집계되고, **Δ=0 이 데이터의 성질이
아니라 깨진 도구의 성질**이 됐을 것이다.

**처방**: 최상위를 객체로 감싸고(`{"relations": [...]}`) 형식 예시 하나를 붙였다.
같은 원문에 `{"relations": []}` 로 정확히 답한다(3/3 재현 → 전량 재추출에서 0건).

## ② `\$` — JSON 이 허용하지 않는 이스케이프 · **하필 `Q-101` 의 레코드**

```
20250325800001  "evidence": "… 투자금액 : \$58억"   ← \$ 는 JSON 규격에 없다
                → bad_json · 그 레코드의 추출이 통째로 사라졌다
```

🔴 **그 레코드가 평가셋 근거에 노출된 9건 중 하나다.** 안 고쳤으면 근거가 바뀌는
문항이 **0개**로 나오고, "Δ=0" 이 파서 결함의 결과가 됐을 것이다.
**처방**: 되돌릴 수 있는 서식 오류만 되돌린다 — 유효하지 않은 이스케이프의 백슬래시를
떼고 재파싱한다. 값은 한 글자도 안 고친다.
