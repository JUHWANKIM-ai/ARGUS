## D-2. periodic 섹션 인덱스 — 완료

정기공시는 전체 토큰의 95%이고 평가 질의의 절반이 여기서 나온다. **없으면 답할 수 없다.**

구현: `src/argus/corpus/sections.py` · `scripts/build_sections.py` · `tests/test_sections.py`

```
python scripts/build_sections.py        # 1,054건 → 112,450 섹션, 185초, LLM 0회
```

### 목차는 추론할 필요가 없다 — 원문에 이미 마크업돼 있다

DART XML(dart4.xsd)은 목차를 `ATOC="Y"` 로 직접 표시한다.

```xml
<SECTION-1><TITLE ATOC="Y" ATOCID="9">II. 사업의 내용</TITLE>
  <SECTION-2><TITLE ATOC="Y" ATOCID="11">2. 주요 제품 및 서비스</TITLE> … </SECTION-2>
```

`SECTION-n` 중첩이 계층, `TITLE` 이 목차 항목이다. **휴리스틱 없이 마크업만 따라가면 된다** —
"사업보고서 파싱이 가장 어렵다"(CONVENTION §7.1)는 경고의 실제 난도는 목차 추출이 아니라
표·인라인 스팬 처리 쪽에 있었다(아래 함정 3종).

| 파싱 성공 | **1,052 / 1,054** (실패 2건은 뷰어 셸 HTML, 아래) |
| 섹션 | **112,450개** · 본문 546M자 · 표 1,540,768개 |

`path` 예시 (삼성전자 2025 사업보고서 = 슬라이드 예시 문서)

성립하는 근거다.

### `text` 저장 방식 — 오프셋 lazy 확정 (실측)

| 방식 | 파일 | 파이썬 상주 | 판정 |
|---|---|---|---|
| 전량 인라인 | jsonl **780MB~1,019MB** | **1,077MB~1,394MB** | ✗ 게이트 500MB 의 2~2.8배, 서버 2.8GiB 의 38~50% |
| **오프셋 lazy** | jsonl 55MB + 블롭 926MB | 225MB | ○ |
| **오프셋 + 문자열 인턴** | 동일 | **174MB** | ✅ **채택** |

- 인라인 상주량은 20건·100건 표본을 실측해 섹션 수 비율로 환산했다(두 표본이 1,077MB·1,394MB로
  갈리는 건 삼성전자 편중 때문이며, 어느 쪽이든 상한을 넘는다).
- 인턴 대상은 `doc_id`·`corp_code`·`corp_name`·`sector`·`doc_subtype`·`rcept_dt`·`path`.
  `path` 고유값이 8,636개뿐이라 **인턴만으로 225MB → 174MB (-23%)**.
- **지연 비용은 사실상 0** — 블롭 seek+decode 가 **0.04 ms/섹션** (매번 `open` 해도 동일).
  `read_section` 전체가 0.3ms, 상위목차 8개 섹션 집계가 0.4ms.
- 블롭 926MB는 디스크에만 있고 상주하지 않는다. 원본 5.3GB를 서버로 옮길 필요도 없앤다
  (인덱스가 원본 XML이 아니라 자기 블롭을 가리키므로).

### 파싱 함정 3종 — 전부 재무 수치에 직결

| 함정 | 증상 | 처리 |
|---|---|---|
| **COLSPAN 미전개** | 병합 셀만큼 값이 왼쪽으로 밀린다. 삼성전자 매출 표의 `총 계` 행(COLSPAN=2)에서 매출액 3,336,059가 '주요 제품' 열로 들어간다 | 빈 칸으로 전개 |
| **SPAN 분절** | 색·굵기가 바뀔 때마다 SPAN 이 갈리고 사이에 개행이 들어간다. 태그를 공백으로 치환하면 `스마트폰 은 전년 대비` 로 조사가 떨어진다 | 태그 사이 공백을 먼저 제거한 뒤 태그 삭제 |

`(단위 : 억원, %)` 가 뭉개지므로 문장으로 푼다(§7.7 ⑤ "단위 표기·표 제목 보존").

### 스키마 (§7.3 + 운영 필드)

```json
{"chunk_id":"periodic_20260310002820#010","doc_id":"periodic_20260310002820",
 "corp_code":"00126380","corp_name":"삼성전자","sector":"반도체·전자부품",
 "doc_subtype":"annual","base_year":2025,"base_month":12,"rcept_dt":"20260310",
 "is_correction":false,
 "path":"II. 사업의 내용 > 2. 주요 제품 및 서비스","level":2,
 "n_chars":979,"n_tables":3,"is_stub":false,"is_container":false,
 "text_offset":123456,"text_bytes":1723}
```

`text` 는 `section_text(record)` 가 블롭에서 꺼낸다. 슬라이드 스키마와 다른 점은
`text` → `text_offset`/`text_bytes` 하나뿐이고, `read_section` 반환값은 `text` 를 채워 준다.

**설계 결정**

| 항목 | 결정 | 근거 |
|---|---|---|
| 청킹 단위 | **목차 섹션** (`ATOC="Y"` 전수) | 설명회 권고 · 원문 마크업 |
| 섹션 본문 범위 | **자기 소유 구간만** (하위 섹션 제외) | 상위까지 담으면 같은 문장이 3중 색인된다 |
| 스텁 | 색인에 **넣고** `is_stub` 로 표시 | 배제는 `list_sections` 가 한다 — 값이 있어야 판정 재현 |
| 표 처리 | 마크다운 인라인 (분리는 D-3 실험) | 설명회 권고 |
| 본문 저장 | **오프셋 lazy** | 위 실측 |
| 감사보고서 첨부 | 포함, `[감사보고서]`/`[연결감사보고서]` 접두 | 목차 제목이 동일해 접두 없이는 `path` 충돌 |

### 후속 트랙에 넘기는 사실

- **Phase B (골든셋 periodic 24문항)** — 정답 근거는 `doc_id` + `path` 로 적으면 그대로 채점된다.
  단 **분기보고서는 목차의 27.9%가 빈 껍데기**이므로, 분기보고서 대상 문항을 만들 때
  `list_sections(doc_id)` 기본 출력(스텁 제외)에 실제로 남는 섹션인지 먼저 확인할 것.
  `IV. 이사의 경영진단 및 분석의견`·`VI. 이사회 등`·`VIII. 임원의 보수 등`은 분기보고서에서
  통째로 "기재하지 않습니다" 다 — 사업/반기보고서로 유도해야 답이 나온다.
- **Phase D (검색)** — 검색 대상은 **비스텁 88,654 섹션**이다. 고유 `path` 8,636개는
  메타 프리필터의 새 축이 된다(`corp_name` + `base_year` + `path` prefix).
  섹션 길이 p99가 77K자이므로 BM25 문서 길이 정규화가 exchange(짧은 레코드)와 다르게 동작한다.
- **개인정보(R6)** — 표지 섹션에 대표이사 성명·본점 전화번호가, `VIII. 임원 및 직원 등의 현황`
  에 임원 개인정보가 그대로 있다. 마스킹은 답변 생성 단계에서 걸어야 한다.

## D-5. 검색 인덱스 커버리지 확대 — 완료

색인이 exchange 1,469건뿐이라 **periodic·major·holding 질의는 후보에 아예 없었다.**
평가셋 60문항 실측에서 그 세 문서군의 골든 적중이 전부 0이었다. hop 로직 실패가 아니라
커버리지 공백이다.

구현: `src/argus/retrieve/bm25.py` · `scripts/build_section_index.py` ·
`src/argus/agent/{router,query,tools,pipeline}.py` · `tests/test_section_index.py`

```
python scripts/build_section_index.py     # 112,450 섹션 → 157,397 조각, 23초, LLM 0회
python scripts/build_index.py --group major     # 598건
python scripts/build_index.py --group holding   # 1,083건
```

### 판정 1 — 통합 인덱스가 아니라 **별도 인덱스** (실측)

exchange 레코드는 길이 중앙 764자, periodic 섹션은 p99 77,454자다. 한 인덱스에 섞으면
BM25 의 길이 정규화와 IDF 가 어느 한쪽에 맞춰진다. **추측 대신 둘 다 지어 재 봤다** —
스코어러(`SectionBm25Index` = BM25Okapi 수식)를 고정하고 코퍼스 구성만 바꿨다.

동일 질의(hop 0~2 의 질의어·필터를 그대로) 로 exchange 골든 30건의 순위를 잰 결과:

| 구성 | top-50 회수 | 1위 | top-3 | 평균순위 | avgdl |
|---|---:|---:|---:|---:|---:|
| **별도** (exchange 1,469건만) | **27** | 17 | **25** | 2.74 | 83 |
| 통합 (exchange + periodic 88,654) | 26 | 19 | 24 | 1.54 | 407 |

- **회수가 27 → 26 으로 떨어진다.** Q-023 의 1차 정정본 `20240322800822` 이 35위에서
  top-50 밖으로 밀려난다. top-3 도 25 → 24 다.
- **통합으로 periodic 이 얻는 것은 없다** — periodic known-item 300건 표본에서
  R@5 가 별도 0.427 · 통합 0.427 로 동일하다.
- `avgdl` 이 83 → 407 로 5배가 된다. 짧은 exchange 레코드가 길이 정규화에서 불리해진다.

**얻는 것 없이 기존 성능만 깎는다.** 별도로 간다.

축 자체가 다르다는 것이 더 근본적인 이유다. 정기공시는 **접수연도 ≠ 사업연도**다 —
'2023년 사업보고서'는 2024-03 에 접수된다. exchange 에서 결정적이었던 `rcept_dt` prefix 를
그대로 걸면 골든이 통째로 필터에서 빠진다. 한 인덱스는 한 벌의 축밖에 못 가진다.

정형 레코드 3종(exchange·major·holding)도 같은 이유로 나눠 두었다. 셋을 합쳐 재 보면
major 0/11 → 9/11, holding 0/8 → 6/8 로 회수되지만 **exchange 골든이 29 → 28 로 하나

### 판정 2 — 섹션 2차 분할은 **한다** (표 경계 보존)

정기공시는 **BM25 만으로는 문서를 못 가른다.** 같은 기업의 분기·반기·사업보고서가 같은

`path_hints()` 가 그 64개와 질문의 어절 겹침만으로 후보 3개를 고른다 — 조사 한 글자는
떼고 본다('배당에' 는 '현금배당금' 과 안 맞지만 '배당' 은 맞는다).
제출·서식 어휘와 짝 경로 처리는 [D-6](#d-6-다지점-질의-분해--목차-짝-경로--완료) 에 있다.

**`path` 완전일치는 쓰지 않는다.** 제출인 오타가 목차에 그대로 들어온다 —
HMM `20240514001580` 의 `"12, 관계기업투자 (연결)"` 는 마침표 자리에 쉼표다.
`path` 축의 비교는 구두점·공백·대소문자를 지운 정규형으로 한다(`norm_path`).

hop 사다리 4단 (`plan_section_hops`):

```
hop 0 toc_narrow — 목차 후보 2개 + (접수연월 ▸ 없으면 보고서 종류 + 사업연도)
hop 1 toc_corp   — 목차 후보 3개, 기간·종류 해제   (수록 기수가 겹치지 않는 문항 대응)
hop 2 doc_narrow — 목차 해제, 종류 + 사업연도       (목차 추정이 빗나간 경우)
hop 3 corp_only  — 기업 필터만
```

hop 0 이 경로를 **2개** 보는 이유는 D-6 ②③ 이다 — 같은 지표가 다른 목차에 실리는
문항이 실재한다. 1순위가 근거 칸의 대부분을 갖고 짝 경로는 1칸씩만 가져간다.

접수 시점이 질문에 적혀 있으면 그게 1순위다. `'2024년 3월 20일 제출한 제25기 사업보고서'`
는 사업연도가 질문에 없어서(2023인데 적힌 숫자는 2024뿐) `base_year` 로 걸면 정반대
문서만 남는다 — Q-055 가 이 케이스이고 접수연월 축을 넣자 골든이 1위·2위로 올라왔다.

매치만** 쓰기 때문에 Q-014 는 삼성SDI·고려아연 둘 다 `ym=202503` 으로 검색됐고
고려아연의 2024-10 공시는 필터에서 통째로 빠졌다.

시점을 제대로 걸어 재질의하면 골든은 **셀 안에서 전부 1위**다:

| 문항 | 셀 | 골든 순위 · 점수 |
|---|---|---|
| Q-012 | `ym=202503` / `ym=202603` | **1위** 65.9 / **1위** 68.8 |
| Q-014 | 삼성SDI `ym=202503` / 고려아연 `ym=202410` | **1위** 33.7 / **1위** 41.6 |
| Q-015 | `ym=202507` / `ym=202405` | **1위** 57.7 / **1위** 57.8 |

교차곱이 헛돌지도 쟀다 — 고려아연 `ym=202503` 은 후보 1건, 삼성SDI `ym=202410` 은 0건.
**어긋난 셀은 필터가 스스로 비운다.**

**과잉 탐색 제동 3종 (실측으로 임계값을 정했다).**

| 제동 | 값 | 실측 근거 |
|---|---|---|
| ① 발동 조건 | 시점 축이 **2개 이상**일 때만 | dev 42문항 중 7건만 해당. 나머지 33문항은 검색 인자까지 종전과 **완전히 동일** |
| ② 셀별 할당량 | `min(SPLIT_TOP_K, MAX_EVIDENCE / (셀수 × 기업수))` | 골든이 셀 안에서 1위이므로 셀당 3칸이면 남는다. 공평 몫만 쓰면 2셀×1기업에서 5칸으로 헐거워져 근거가 부푼다 |
| ③ 분해 범위 | **hop 0 만** | 넓히는 hop 까지 곱하면 스텝 상한 8을 넘긴다. 실측 최대 셀 4개(Q-014 = 2기업×2시점) → hop 0 이 4스텝 + 체인 1스텝 = 5스텝 |

시점 축 상한은 `MAX_TIME_POINTS = 3` 이다 (dev 실측 최대는 2).

근거가 **줄었다**는 것이 분해가 넓히기보다 싸다는 증거다 — Q-012 는 8블록 2,951자에서
2블록 751자로, Q-020(정답 유지)은 8블록 2,951자에서 3블록 1,135자로 줄었다.
넓히기(hop 1 `relax_period`)가 같은 연도의 무관한 공시 8건을 담던 자리를, 정확한 두
셀이 2건으로 대체했다.

**정기공시에는 시점 분해를 걸지 않는다.** 실측이 말린다 — Q-046 의 '제53기(2021년)' 는
사업연도 2021 이 아니라 **제55기 사업보고서(사업연도 2023)** 에 실려 있고 코퍼스에
사업연도 2021 보고서는 아예 없다. 연도로 쪼개면 한쪽 셀이 통째로 빈다.

### 병목 B — `WRONG_SECTION`: 문서는 맞고 목차가 틀린다

세 가지가 겹쳐 있었다.

**① 제출·서식 어휘가 경로를 골랐다.** `path_hints` 는 목차 제목과 질문의 어절 겹침으로
경로를 고르는데, 겹치는 어휘가 **내용이 아니라 형식**일 때 엉뚱한 경로가 1위가 된다.

| 문항 | 오답 경로 (겹침 비율) | 정답 경로 | 겹친 어휘 |
|---|---|---|---|
| Q-046 | `【 전문가의 확인 】` **0.400** | `II. 사업의 내용 > 4. 매출 및 수주상황` 0.333 | '어느 보고서에서 **확인**했는지' |
| Q-052 | `II. 사업의 내용` **0.400** | `III. 재무에 관한 사항 > 6. 배당에 관한 사항` 0.286 | '2023년 **사업**보고서' |

두 오답 경로는 1,052 문서 **전부**에 있는 보일러플레이트라 변별력이 애초에 0 이다.
매칭 전에 제출·서식 어휘(`보고서 · 공시 · 제출 · 기재 · 확인 · 작성`)를 지운다.

**② 같은 지표가 여러 경로에 실린다.** dev 정기공시 골든에서 매출·손익 지표는 두 경로로
갈린다 — `II. 사업의 내용 > 4. 매출 및 수주상황`(Q-043·044·045·046·047·049·050) 과
`III. 재무에 관한 사항 > 1. 요약재무정보`(Q-048·049·051). Q-049 는 **한 질문 안에서**
두 기업이 같은 '연결 매출액' 을 서로 다른 경로에 실었다. 겹침 점수로는 풀 수 없다 —
'연결 매출액' 은 '요약재무정보' 와 글자가 하나도 겹치지 않는다.

경로 동의어를 **사전으로 만들지 않았다.** 상위 20개 경로가 1,052 문서 전체에 나오므로
사전은 금방 전 목차를 덮어 버린다. 대신 **짝 경로 한 쌍**만 규칙으로 1순위 바로 뒤에
끼운다 — 1순위를 밀어내지 않으므로 지금 맞히는 문항이 깨지지 않는다. hop 0 이 보는
경로는 `MAX_SECTION_PATHS = 2` 다 (병목 2건이 요구하는 짝이 정확히 2개다).

**③ `정 정 신 고 (보고)` 가 모집단 밖이었다.** 이 경로는 1,052 문서 중 **157건**에만
있어 `tools.section_paths()` 의 '200문서 이상' 문턱에 걸려 후보가 될 수 없었다. 그런데
dev 골든 3건(Q-048·Q-052·Q-054)이 바로 이 경로다. 정정을 묻는 질의에서만 후보로
되살리고, **짝 경로보다 앞에 둔다** — 뒤로 뒀더니 Q-048 에서 지표 짝에 밀려 hop 0
후보에 못 들어왔다.

**④ 기수(제N기)는 사업보고서를 가리킨다.** 종류 표기가 없고 기수만 있는 문항
3건(Q-046·Q-049·Q-050)의 골든 **5건이 전부 사업보고서**다. `doc_subtype=annual` 을
걸면 Q-046 의 골든 둘이 3·5위에서 **1·2위**로 올라온다 (근거 칸 4건에 5위는 안 들어온다).

### 근거 칸 배분 — 순서가 곧 회수율이다

글자 예산(`MAX_SECTION_CHARS = 12,000`)이 근거 칸의 진짜 제약이라 **어떤 순서로 담느냐가
회수율을 결정한다.** 잘못 잡으면 정확히 반대로 간다.

| 규칙 | 결정 | 실측 |
|---|---|---|
| 기업 축 | **라운드로빈** | Q-049 는 두산에너빌리티 `매출 및 수주상황` 이 6,649자라 도착 순서대로 담으면 LG 뒤에 두산만 남고 예산이 마른다 |
| 기업 안 순서 | **도착 순서 그대로** | 짧은 것부터 담아 봤더니 Q-045·Q-046 의 골든(3,679자 · 3,371자)이 뒤로 밀려 잘렸다. 도착 순서는 이미 목차 순위와 BM25 점수가 정한 순서다 |
| 예산 초과 블록 | **건너뛰고 계속** (끊지 않는다) | Q-049: 끊으면 3블록 12,316자에 골든이 하나 빠지고, 건너뛰면 3블록 11,381자에 골든 둘이 다 든다. 상한은 그대로라 토큰은 늘지 않는다 |
| 짝 경로 할당 | 1순위가 나머지, **짝 경로는 1칸씩** | 반씩 나눴더니 Q-050 의 골든(1순위 경로 안에서 3위)이 잘렸다 — 4칸을 2/2 로 쪼개면 3위가 못 들어온다 |

### 넣지 않은 것

- **(문서, 목차) 중복 제거** — 한 섹션의 8,000자 조각들이 근거 칸을 다 먹는 것을 막으려
  했으나, 골든 적중을 **하나도 못 올리면서** hop 10 → 12, 근거 1,079자 증가만 남겼다
  (Q-054 한 문항의 변화가 전부다). 넣지 않았다.
- **정기공시 사업연도 분해** — 위 병목 A 참조. 셀이 통째로 빈다.

### 남은 미적중 1건 — A3 re-ranker 대상

**Q-054** 는 1/2 그대로다. 골든 둘 중 `정 정 신 고 (보고)` 는 회수했지만
`III. 재무에 관한 사항 > 3. 연결재무제표 주석` 은 못 실었다. 질문이
"무엇이 정정됐는지" 라 **목차 단서가 질문에 없고**, 정정본이 가리키는 원문 섹션을
따라가야 나온다. 규칙으로는 풀리지 않는다 — 목차 경로 re-ranking(A3) arm 이 재야 한다.

### 게이트를 재는 모집단은 dev 뿐이다 — 옛 분모 60·93 의 정체

게이트 D 에 한동안 `dev 60문항 … 골든 근거 단위 70/93 (0.753)` 이라고 적혀 있었다.
**dev 는 42문항이다.** 분모를 코드로 세어 정체를 확정했다.

| 파일 | 문항 | 골든 근거 |
|---|---:|---:|
| `evalset/questions.jsonl` (dev) | 42 (골든 보유 36 · `answerable=false` 6문항은 0건) | **60** |
| `evalset/heldout.jsonl` | 18 | **33** |
| 합 | **60** | **93** |

- **60 은 dev 문항 수가 아니라 dev 42 + heldout 18 의 문항 수**다. 분리 이전 표기가 남았다.
- **93 = 60 + 33** 이므로 그 줄은 heldout 을 섞어 잰 값이다.
- **70 = 45 + 25** 다 — [D-5 실측 표](#실측--dev-42--heldout-18)의 `골든 적중` 열을 분할별로
  더하면 dev 19+4+5+17 = 45, heldout 10+5+2+8 = 25 로 정확히 떨어진다.

두 가지가 동시에 틀려 있었다. ① **모집단** — heldout 은 최종 1회용이라 그것으로 게이트를
재는 것 자체가 오염이다. ② **시점** — 70/93 은 D-5 시점 값이고, D-6 이 dev 골든 적중을
49 → 59 로 올린 뒤 갱신되지 않았다.

### 실측 — dev 42문항 (A6 기본 구성 · LLM 0회)

`_gather_evidence` 를 dev 전수로 돌려 hop 로그의 후보 순서로 골든 순위를 쟀다.
채점은 `scripts/error_analysis.py` 의 `golden_positions`(후보 순위) 와
`evidence_hit`(프롬프트에 실렸는가) 를 그대로 쓴다. **CLOVA 호출 0회.**

| 분할 | 문항 | 골든 | **Recall@5** | 근거 칸 적중 | 문항 단위 |
|---|---:|---:|---:|---:|---|
| **dev** | 42 | **60** | **58 (0.967)** | 59 (0.983) | @5 최소 1건 **36/36** · 전건 34/36 |

- 게이트 문턱 0.85 를 **0.967 로 통과**한다.
- `근거 칸 적중`(59)이 `Recall@5`(58)보다 하나 큰 것은 정의가 다르기 때문이다 —
  근거 칸은 10건까지 담고 체인 hop 이 순위 밖 문서를 끌어온다(아래 Q-023).
- **교차검증** — `artifacts/ablation/A6/responses/` 의 캐시된 A6 실행(기준선 dev 31/36)을

## D-4b. 재측정 — full 코호트 88문항 (**2026-08-10 → 2026-08-11 갱신** · LLM 0회)

평가셋이 §B-9·게이트 H-6 증설로 **dev 42 → 78 + 회귀 10 = 88문항**으로 늘었다. `measured 42`는
v1(Phase H) 시절의 비교축으로 그대로 남기고(위 D-4 표, 값 불변), **여기서 새 모집단을 추가로
잰다.** `70/93` 사고가 "수치에 모집단·시점이 안 적혀 낡은 줄 몰랐던 것"이었으므로, 이 섹션의
모든 줄에 **코호트 이름과 측정 시점을 함께 적는다.**

측정은 두 경로로 교차검증했다 — 둘 다 **CLOVA 호출 0회**.

1. **캐시 재집계** — `scripts/error_analysis.py --cohort full`(캐시만 읽음, 실행 없음)이 남긴
   `artifacts/eval/error_analysis_v2.json`(T7 산출물) 의 `rows[].golden_rank` 를 그대로 센다.
2. **하네스 재실행** — `scripts/ablation.retrieval_metrics("A6", cases)` 를 스크래치패드에서
   직접 호출해(T7 §1 과 같은 방법) `_gather_evidence` 만 다시 돈다. 생성 프롬프트를 만들지
   않으므로 LLM 호출이 없다.

두 경로가 **`measured 42`·`full 88` 전부 소수점 셋째 자리까지 동일**했다 — 코드 드리프트 없음.

🔴 **아래 표는 2026-08-11 W1·W2·W3 후 재측정 값이다** (`retrieval_metrics("A8", load_cases("full"))`,

없어 옛 세대에 얼어붙어 있다** — heldout 원장과 같은 구조다. 두 수는 **다른 세대의 코드**를
잰 것이므로 한 줄에 겹쳐 적지 않고, 여기서만 나란히 낸다.

### 판정 — 게이트 D 는 `measured 42` 와 `full 88` **둘 다 병기한다**
