## B-2. 스키마 — 축 3개를 독립 필드로

`closed_lookup` 처럼 유형과 답변형식이 뭉친 라벨을 쓰면
[08-error-analysis](08-error-analysis.md) 에서 축별 집계가 불가능하다.

```yaml
question_id: Q-012
question: "HD현대일렉트릭이 2023년 1월에 체결한 변압기 공급계약의 계약금액은?"

# ── 독립 축 3개 (CONVENTION §5·§6) ──────────────────
task_type:   search_extract      # search_extract | multi_compare | complex_reason
answer_mode: closed              # closed | open
difficulty:  하                   # 상 | 중 | 하
# ───────────────────────────────────────────────────

answerable: true                 # false 면 정보한계 대응 문항
answer: "97,000,000,000"
answer_form: number_won          # 판정기를 결정한다 (B-5)
tolerance: 0                     # 수치 허용 오차(%)

evidence:
  - rcept_no: "20230131800162"
    section: null                # periodic 이면 목차 경로
    why: "계약금액 필드"

reasoning_steps:
  - "기업 해소: HD현대일렉트릭"
  - "기간 필터: 202301"
  - "계약금액 필드 조회"

required_tools: [resolve_company, search_chunks]
doc_group: exchange              # exchange | periodic | major | holding
split: dev                       # dev | heldout
source: manual                   # manual | derived | error_analysis
notes: ""
```

**`answer_form` — 판정기를 결정한다**

| 값 | 판정 | 예 |
|---|---|---|
| `number_won` | 정규화 EM (콤마·단위 제거) | `97,000,000,000` |
| `number_pct` | 정규화 EM (소수 1자리) | `5.37` |
| `duration` | 정규화 EM | `1년 9개월` |
| `boolean` | 예/아니오 매핑 | `있다` |
| `list` | 항목 집합 F1 | `유상증자, CB, BW` |
| `narrative` | LLM-as-a-Judge | 서술형 |
| `refusal` | 거부 문구 포함 여부 | `확인되지 않` |

### B-2 확장 — 실제 스키마에 추가된 필드

B-2 원안만으로는 B-7 의 검증 6·7번과 게이트 B 의 '정정 이력' 항목을 **기계로 확인할 수 없어서**
필드를 덧붙였다. 판정 로직은 바꾸지 않는다.

| 필드 | 타입 | 왜 필요한가 |
|---|---|---|
| `corp_name` | `[str]` | B-7 검증 6·7 (홀드아웃 섹터 소속 · dev/heldout 기업 중복) 의 대상. 복수 기업 비교 문항 때문에 리스트다 |
| `correction_tracking` | `bool` | 게이트 B 의 "'상' 문항에 정정 이력 추적 포함" 을 셀 수 있게 한다. 거래소공시 문항은 `exchange_records.jsonl` 의 `related` 와 대조해 **정답 자체를 재검증**한다 |
| `type` · `gold` · `must_cite` | 파생 | `scripts/eval_e2e.py` 하위호환. 손으로 쓰지 않고 축 3개에서 생성한다 |
| **`track`** | `str` | `grid` · `info_limit` · `regression` · `valuechain`. **셀 카운트의 모집단을 정의한다** (B-8 · B-10). 이전에는 `answerable` 로 그리드 안팎을 갈랐는데, 회귀 트랙에 `answerable=true` 문항과 `false` 문항이 **둘 다** 있어서 그 대용으로는 못 가른다 |
| **`regression_of`** | `[str]` | 이 문항이 재현하는 **실측 실패 유형**. `validate_evalset.py` 의 `FAILURE_MODES` 8종으로 검증한다. 회귀 문항이 아니면 `null` |
| **`hub`** | `[str]` | 밸류체인 문항이 경유하는 **계약상대 노드**(정규화형). C12 가 근거 레코드의 `counterparty` 와 대조한다. 다른 트랙은 없는 필드 (B-10) |
| **`answer_recipe`** | `dict` | `{"plus": [rcept…], "minus": [rcept…]}`. C13 이 이 식을 실행해 `answer` 를 원본 `amount` 로 재계산한다. 밸류체인 closed 수치 문항만 (B-10) |

정보한계 문항(`answerable: false`)은 3×2×3 그리드 밖이므로
`task_type` · `answer_mode` · `difficulty` 를 **`null`** 로 둔다. 그래야 축별 표본 수가 오염되지 않는다.

**3축 라벨은 `answerable` 을 따르고, 그리드 소속은 `track` 을 따른다.** 회귀 문항도
`answerable=true` 면 3축 라벨을 **채운다** — 축별 분석에 쓸 수 있어야 하기 때문이다.
다만 `track != "grid"` 라 셀 카운트에는 들어가지 않는다.

## B-3. 난이도 조작적 정의

감으로 붙이면 축이 무의미해진다. **문서 수 · 연산 수 · 이력 추적 여부**로 정의한다.

| 난이도 | 정의 | 실제 예 (우리 코퍼스) |
|---|---|---|
| **하** | 단일 문서 · 단일 필드 · 직접 조회 | "HD현대일렉트릭 2023-01 변압기 계약의 계약금액은?" → `97,000,000,000` |
| **중** | 단일 문서 복수 필드 **또는** 복수 문서 단일 필드 · 1회 연산 | "그 계약의 계약기간은 몇 년 몇 개월인가?" → `1년 9개월` |
| **상** | 복수 문서 종합 · 다단계 연산 · **정정 이력 추적** · 시점 비교 | "삼성전자 반도체 위탁생산 계약이 정정된 뒤 금액이 얼마나 바뀌었나?" → 원본 `20250728800035` vs 정정 `20250731800028` |

> **'상' 문항에 정정 이력을 반드시 포함한다.** 정정이 전체의 24%(1,004건), 거래소공시만 43%(631건)인데
> 현재 6문항에는 정정 문항이 **하나도 없다.**
> → **해소.** '상' 18문항 중 **15문항이 정정 이력 추적**이다 (전체 60문항 중 17문항).
> 정기공시도 정정이 159건 있어 4문항(Q-048·Q-052·Q-054·Q-055)을 여기서 뽑았다.

### B-3 판정 규칙 — 표만으로는 갈리는 경우가 있어 우선순위를 못박는다

세 축은 **독립**이다. 난이도는 `task_type` 과 무관하게 **근거 문서 수 · 필드 수 · 연산 수 · 이력 추적**
넷으로만 정한다. 위에서부터 먼저 걸리는 것을 쓴다.

| 순위 | 조건 | 난이도 |
|---|---|---|
| 1 | **정정 이력 추적**이 필요하다 (원본↔정정본 대조, 체인 내 최신본 판별) | **상** |
| 2 | **시점 비교**가 필요하다 (서로 다른 기준일 문서 2건 이상 대조) | **상** |
| 3 | 근거 3건 이상을 **종합**해야 한다 (단순 합산·나열은 제외) | **상** |
| 4 | 연산이 **2회 이상** | **상** |
| 5 | 단일 문서 **복수 필드**, 또는 복수 문서 단일 필드 + **1회 연산** | **중** |
| 6 | 근거 1건 · 필드 1개 · 연산 0회 | **하** |
| 7 | 근거 2건 이상이지만 필드 1개 · **연산 0회** (단순 대소 비교) | **하** |

7번이 핵심이다. `multi_compare`/`complex_reason` 이라도 **연산이 없으면 '중'의 요건
(1회 연산)을 만족하지 못하므로 '하'** 다. 이 규칙이 없으면 `multi_compare × 하` 셀을 채울 수 없다.

### 난이도 라벨은 Phase H 에서 실측 정답률로 재조정한다

**지금 논쟁으로 확정하지 않는다.** 지금 중요한 것은 §B-3 규칙을 **일관되게** 적용하는 것이지
라벨을 절대적으로 맞히는 것이 아니다. 라벨의 정오는 실측이 판정한다 —
[07-eval](07-eval.md)/[08-error-analysis](08-error-analysis.md) 에서
**'하' 셀 정답률이 '상' 셀보다 낮게 나오면 그 라벨이 틀린 것**이고, 그때 고친다.

경계가 애매한 문항은 규칙대로 라벨을 붙이고 **아래 목록에 추가한 뒤 넘어간다.**
고민하다 멈추지 않는다.

| dev 만 (축별) | 12 → **24** · 2원 교차 6 → **12** |

> **왜 올렸는가 — 잴 수 없었기 때문이다.** 증설 전 dev 채점대상 n=36 은 95%CI ±11.3%p 였고
> 1문항이 2.8%p, 셀 하나(dev 2)에서는 1문항이 50%p 였다. McNemar 로 유의하려면 불일치쌍이
> 8개 이상이어야 하는데 Ablation v1 의 A0→A1 은 불일치 1개, A5→A6 은 0개로 **판정 자체가 불가능**했다.
> 남은 작업(A7 거절 강제 · A3 목차 re-ranker)이 전부 0~2문항을 겨냥하므로,
> 지금 크기로는 고쳤는지 아닌지 영원히 알 수 없다. dev 채점대상 n=72 로 CI 가 ±11.3 → **±8.0%p** 로 좁는다.

### periodic 18문항의 dev/heldout 배분 — 셀당 정확히 1개씩

periodic 6문항을 heldout 으로 돌렸다. 근거 두 가지다.

1. **비율 유지.** 기존 그리드 36문항 중 heldout 이 12 = **1/3**. 18문항 중 6을 heldout 으로
   두면 54문항 중 18 = 그대로 1/3 이다. B-6 의 홀드아웃 규모(70개사 중 22개사 ≈ 31%)와도 맞는다.
2. **셀당 heldout 1개 균등화.** 기존 heldout 12문항은 18셀 중 12셀에만 들어가 있었고
   6개 셀(se/closed/상, se/open/하, mc/closed/중, mc/open/상, cr/closed/하, cr/open/중)에는
   heldout 이 **하나도 없었다.** 새 periodic 6문항을 정확히 그 6셀에 넣어
   **이제 18셀 전부가 dev 2 + heldout 1** 이다. 셀 단위로 dev↔heldout 일반화 격차를 볼 수 있다.

heldout periodic 기업은 기존 8개사 안에서만 골랐다 — 한국항공우주 · 하이브 · 현대로템 ·
삼성바이오로직스 · 한화에어로스페이스 · 미래에셋증권. dev 기업과 겹치지 않는다 (C7 이 강제).

## B-5. Closed / Open 판정기 분리 — policy §5

| | 판정 | 추가 지표 | 비용 |
|---|---|---|---|
| **closed** | `answer_form` 별 정규화 EM | Self-Consistency 일치율 | **0** |
| **open** | LLM-as-a-Judge | Groundedness · Evidence Score | judge 1회 |

**judge 프롬프트 규격** — 판정이 흔들리면 측정이 무의미하다.

```
[근거] {evidence}
[질문] {question}
[모범답안 요소] {answer_key_points}
[제출답변] {answer}

각각 0/1 로 판정하고 JSON 한 줄로만 답하라.
  covers_key_points : 모범답안 요소를 빠짐없이 포함했는가
  grounded          : 모든 서술이 근거에서 확인되는가
  no_fabrication    : 근거에 없는 내용을 사실처럼 쓰지 않았는가
{"covers_key_points":0/1,"grounded":0/1,"no_fabrication":0/1,"reason":"한 문장"}
```

open 문항은 `answer` 대신 **`answer_key_points: [str]`** 를 채운다.

## B-6. Train / Held-out 분리 — policy §7

**기업이 아니라 섹터 단위로 홀드아웃한다.** 기업만 나누면 같은 섹터의 서식·용어를 이미 본 셈이라
일반화 측정이 되지 않는다.

```
dev     : 16개 섹터 (universe 48개사)  ← 프롬프트·규칙 튜닝은 여기서만
heldout :  4개 섹터 (universe 22개사)  ← 최종 측정 1회만
```

> 초안에 적혀 있던 `약 14개사` 는 실제 22개사와 맞지 않아 **오기로 확정**했다.
> 실제 문항이 쓰는 기업은 dev 18개사 · heldout 8개사다.

| 홀드아웃 섹터 | 왜 |
|---|---|
| 바이오·제약 (6) | 임상 단계·기술이전 — 서식이 가장 이질적 |
| 금융·보험 (8) | NIM/CSM·충당금 — 지표 체계가 다름 |
| 조선·건설·방산 (4) | 수주잔고 — 누적 개념 |
| 엔터테인먼트 (4) | 부문별 매출·아티스트 계약 |

> 🔴 **홀드아웃을 보고 튜닝하면 그 순간 홀드아웃이 아니다.**
> `evalset/heldout.jsonl` 로 분리하고 평가 스크립트에서 기본 제외한다.

## B-8. 회귀 트랙 — 게이트 H-6 환류 (2026-08-09)

[08 게이트 H](08-error-analysis.md) 의 마지막 항목이다. Phase H 와 Ablation v1 이 찾아낸
실패 유형을 **각각 재현하는 문항**을 골든셋에 넣는다. 없으면 고친 뒤 다시 깨져도 아무도 모른다.

### 왜 그리드를 올리지 않고 별도 트랙인가 — (a) 를 버리고 (b) 를 골랐다

B-7 갱신 규칙이 제시한 두 길 중 **(b) 그리드 밖 별도 분류**를 골랐다. 근거 셋이다.

**① 회귀 문항은 난이도 축에 중립적이어야 한다.** 목적은 변별이 아니라 감시다 —
"고친 것이 다시 깨지면 반드시 실패한다" 면 쉬워도 된다. Q-062(근거 1건·필드 1개·연산 0회)가
정확히 그런 문항이다. 이런 문항을 그리드에 넣으면 '하' 셀 정답률이 회귀 문항의
쉬움으로 올라가고, **난이도 축 자체가 측정 도구이기를 그만둔다.**

**② 실패 유형은 18셀에 고르게 분포하지 않는다.** 정정체인은 본질적으로 '상' 이고
`INDEX_FIELD_MISSING` 은 단일 문서 조회라 '하~중' 이다. (a) 로 가면 재현할 실패가 없는
셀 여럿을 **억지 문항으로 채워야** 한다 — B-7 절차 2("답을 먼저 알고 질문을 쓴다")를 어긴다.

**③ 결정적으로, `questions.jsonl` 은 길이가 동결돼 있었다.** 이 트랙 밖의 테스트 둘이
그 파일의 크기에 게이트를 걸어 두었다.

| 테스트 | 당시 고정값 | 깨지면 |
|---|---|---|
| `tests/test_error_analysis.py::test_only_dev_split_is_loaded` | dev **42문항** | Phase H 의 42문항 기준선과 `artifacts/eval/` 캐시가 어긋난다 |
| `tests/test_pipeline.py::test_gate_d_recall_denominator_is_the_dev_golden_count` | dev 골든 근거 **60건** | 게이트 D 의 Recall@5 분모가 움직여 04-retriever 게이트가 무효가 된다 |

(a) 든 (b) 든 **같은 파일에 넣으면 둘 다 깨진다.** 회귀 문항을 별도 파일에 두면
Phase H·I 의 기준선이 그대로 보존되고, 그것이 오히려 정확하다 —
**회귀 트랙 정답률을 arm 정답률에 섞으면 Δ 가 오염된다.**

> ✅ **두 고정값은 §B-9 에서 유도값으로 바뀌었다.** 42 와 60 이라는 리터럴은 사라졌고,
> 각각 **그리드 규격**과 **실측 코호트**에서 따라 나온다. 회귀 트랙을 별도 파일에 두는
> 결정 자체는 그대로다 — ①②번 이유가 여전히 유효하기 때문이다.

### 스키마

**거기 둔 회귀 문항은 감시하지 않는 감시**다. heldout 잔여 실패 3건의 *유형*
(`VERIFY` · `INDEX_FIELD_MISSING` · `MULTI_POINT_QUERY`)은 전부 dev 쪽 회귀 문항
(Q-069 · Q-062~064 · Q-065)이 재현한다. `C8` 이 `track=regression → split=dev` 를 강제한다.

## B-10. 밸류체인 트랙 — `counterparty` 2-hop (2026-08-10)

[03-graph-schema C-0b](03-graph-schema.md#c-0b-기각의-절반을-철회한다--counterparty-를-노드로-올리면-다르다-2026-08-10) 의
재측정에서 **기업-기업 엣지 기각 근거의 절반이 틀렸다**는 것이 나왔다. `counterparty` 를 노드로
승격하고 2-hop 을 열면 기업 쌍이 20 → 44 로 늘고, 원전·방산·그룹 내부거래 클러스터가 그대로 떨어진다.

**그런데 골든셋에 이 유형이 0건이었다.** 엣지를 먼저 만들면 효과를 잴 수 없으므로 **문항을 먼저 만들었다.**

```
evalset/valuechain.jsonl   dev 12문항 (그리드 밖 · 전부 exchange · 전부 answerable)
```

### 왜 그리드 밖인가 — 세 가지 이유

**① CONVENTION §6 에 대응 항목이 없다.** 그리드 3축 18셀은 §6 의 질의 6종
(검색·정보추출 / 다중조회·비교·연산 / 복합 문서 추론 × closed·open)과 정확히 대응한다.
**§6 에는 발주처·밸류체인 단위 질의가 없다.** 넣으면 그 대응이 깨진다.

**② 셀 균등이 즉시 무너진다.** C5/C5b 는 18셀이 정확히 `--per-cell` 개씩이기를 요구한다.
12문항을 넣으면 셀당 4~5 가 뒤섞이고, 균형을 지키려면 18셀 동시 증설(+18문항)이 필요한데
밸류체인으로 채울 수 없는 셀이 있다 — 실제로 **`search_extract` 는 한 문항도 나오지 않았다**
(아래 참조). B-8 ②번과 같은 이유다.

**③ `search_extract` 가 구조적으로 비어 있다.** 밸류체인 질의는 정의상 **문서 2건 이상**을
허브로 이어야 성립한다. 단일 사실 추출(`search_extract`)로 표현하면 그 순간 밸류체인이 아니다.
이 공백 자체가 "그리드에 넣으면 안 된다" 는 증거다.

`regression.jsonl` 이 같은 이유(B-8)로 이미 그리드 밖에 있다. **그 선례를 따랐다.**

**C12 는 작성 중 실제로 오류를 잡았다.** Q-110 의 우리기술 근거로 `20230417900068` 을 넣었는데
그 건의 계약상대는 한수원이 아니라 두산에너빌리티였다. 근거 문서 하나가 다른 허브에
속해 있었고, 눈으로는 보이지 않았다 — 같은 기업의 비슷한 자율공시였기 때문이다.

C13 은 G2·G3 과 같은 성격이다. 형식이 아니라 **정답 자체를 원본으로 재확인**한다.

### 현재 시스템으로 풀리는가 — LLM 0회 도달성 측정

`counterparty` 는 지금 **문자열 속성**이다. `query_events` 파라미터는
`corp_name`·`doc_subtype`·`year`·`min_amount`·`is_latest` 다섯뿐이고 계약상대 필터가 없다.
남는 경로는 `search_chunks` 의 자유 텍스트 BM25 뿐이라 그것으로 근거 도달률을 쟀다.

| 조건 | Recall@5 | Recall@20 |
|---|---:|---:|
| 기업을 **이미 알고** 기업별로 검색 (상한선) | **74.4%** | — |
| 기업을 모르고 허브명으로만 검색 (실제 조건) | **50.0%** | **80.0%** |

**개별 근거는 꽤 닿는다. 못 하는 것은 완결성이다.**

| 문항 | Recall@20 | 판정 |
|---|---|---|
| Q-109 · Q-111 · Q-112 · Q-113 · Q-115 · Q-118 · Q-107 · Q-108 | 전부 도달 | 🟡 **풀릴 수 있다** — 근거는 닿는다. 남는 위험은 배제 판단(Q-107)과 체인 선택(Q-113) |
| Q-116 | 3/3 | 🟡 근거는 닿지만 "이 셋이 전부인가" 를 확인할 방법이 없다 |
| **Q-110** | 3/6 | 🔴 **구조적으로 불가** — fan-in 6개사 완전 열거 |
| **Q-114** | 2/5 | 🔴 **구조적으로 불가** — 66건 전수 분류 |
| **Q-117** | 3/5 | 🔴 **구조적으로 불가** — fan-out 5개 발주처 완전 열거 |

즉 실패는 검색 품질이 아니라 **"허브에 걸린 기업이 전부 몇 곳인가" 를 물을 수단이 없다**는
데서 온다. BM25 top-k 는 완결성을 보장하지 않고, 보장할 수도 없다.
**이것이 다음 단계(계약상대 노드 + 2-hop 탐색)의 정확한 겨냥점이다.**

> 🔴 **이 문항들은 지금 못 푸는 것이 정상이다.** 쉽게 만들지 않았고, 원문에 답이 없는 것도 묻지 않았다.
