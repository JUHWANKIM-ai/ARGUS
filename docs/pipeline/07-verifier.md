## G-2. 계산 검증은 LLM 에게 묻지 않는다

policy §4 의 논리를 그대로 적용한다 — 계산이 Tool 의 일이면 **계산 검증도 Tool 의 일**이다.

```python
def verify_calculation(answer: str, evidence: dict) -> dict:
    """답변에서 수치를 파싱해 compute.py 로 재계산하고 대조한다. LLM 0회."""
```

절차:
1. 답변 텍스트에서 수치·단위 추출 (`22,764,764,160,000원`, `7.6%`, `8년 5개월`)
2. 근거 레코드의 원값으로 `compute.py` 재계산
3. 허용 오차(반올림 1자리, `ROUND_TOLERANCE = 0.05`) 밖이면 `TOOL` 실패로 귀속

**실측 근거**: HCX 는 계약기간 산정(`2025-07-24 ~ 2033-12-31 → 8년 5개월`)을
Direct·CoT **둘 다 오답**(9년 5개월)이었다. 검증 없이는 잡히지 않는다.

### 검사 6종

| kind | 근거 키 | 답변에서 찾는 것 | 재계산 |
|---|---|---|---|
| `period` | `period_start` · `period_end` | `N년 M개월` | `compute.period_parts` |
| `amount` | `amount` | `…원` · `…억원` · `…조원` (**레이블 게이트**, 아래) | 단위 환산 후 대조 |
| `share` | `amount` + 최근매출액(`raw_rows`) · 없으면 `ratio` | `N%` | `compute.share` |
| `pct_change` | `before` · `after` | `N%` | `compute.pct_change` |
| `cagr` | `begin` · `end` · `years` | `N%` | `compute.cagr` |
| `total` · `mean` | `values[]` | 합계/평균 키워드가 있을 때만 | `compute.total` · `mean` |

`evidence` 는 `exchange_records.jsonl` 레코드를 그대로 받고,
`query_events` 반환형(`{"count":…, "events":[…]}`)도 그대로 받는다.

### `amount` 레이블 게이트 — 답변이 **그 금액**을 말했을 때만 대조한다

한 레코드에는 대표 금액(`amount` · `amount_type`) 밑에 하위 항목이 함께 실린다.
유상증자 `조달금액` 2,000,113,200,000 밑의 `시설자금` 454,100,000,000 이 그 예다.
`_money_claims` 는 답변의 금액 표기를 **전부** 긁으므로, 하위 항목을 물은 질문에
정확히 답해도 대표 금액과 대조돼 `TOOL` 오류가 된다.

**A6 스냅샷 실측 거짓 경보 (`Q-014`)**: 질문은 "시설자금 조달액", 답변은
`454,100,000,000원` (정답). 그런데 근거 8건 중 어느 레코드의 `amount` 와도 안 맞아
`calc_failed` 가 섰다.

그래서 답변이 레코드의 **금액 레이블(`amount_type`)** 을 한 번도 말하지 않았으면
그 금액을 주장한 적이 없는 것으로 보고 `skipped` 로 넘긴다. 비교는 공백을 지우고
한다 — 실측 답변은 `**총 조달 금액**` · `**투자 금액**` 처럼 레이블을 띄어 쓴다.
`amount_type` 이 없는 근거는 게이트를 세울 재료가 없으므로 종전대로 검사한다.

비용은 재봤다. `amount` 검사가 도는 문항은 **A6 15 → 14**, **Phase H 8 → 8** 이다.
거짓 경보 1건만 빠지고 나머지 검사는 그대로 돈다.

### 허용 오차 — 답변이 쓴 자릿수만큼만 봐준다

`max(0.05, 표기 자릿수의 절반)`. `227,648억원` 은 ±5천만원까지 같은 값으로 본다
(실제 원값 `22,764,764,160,000` 과 3,584만원 차이 → 통과).

### 안 말한 것과 틀린 것을 섞지 않는다

답변이 해당 수치를 아예 말하지 않으면 불일치가 아니라 **`skipped`** 다.
섞으면 Phase H 의 병목 판정이 오염된다.

### 반환 (Phase H Error Analysis 입력)

```python
{"ok": False, "llm_calls": 0,
 "checked": ["period", "share"], "skipped": ["amount"],
 "failed_kinds": ["period", "share"],
 "failure_stage": "TOOL",          # ok 면 None
 "mismatches": [{"kind": "period", "claimed": "9년 5개월", "claimed_value": 113,
                 "expected": "8년 5개월", "expected_value": 101,
                 "tolerance": 0, "detail": "2025-07-24 ~ 2033-12-31"}],
 "reason": "period: 답변 9년 5개월 vs 재계산 8년 5개월"}
```

`failure_stage` 는 policy §9 의 `Retriever → Re-ranker → Reasoning → Tool` 중
**`TOOL`** 로 바로 귀속된다 — Phase H 는 이 값을 그대로 집계하면 된다.

## G-4. 완전성 — 지지와 다른 축

**`judge` 는 "답이 근거로 지지되는가"만 본다.** 그래서 정정 전 금액만 근거에 있으면
모델이 그 값을 답하고 critic 은 "근거에 있으니 지지됨" 으로 통과시킨다 —
**근거 자체가 불완전하다는 것을 못 본다.**

Phase H dev 42문항 실측에서 정확히 이 기전으로 **오답 5건이 `supported=True`** 로
빠져나갔다: `Q-005` `Q-006` `Q-018` `Q-035` `Q-049`.

### 5건의 공통 패턴 (저장 응답에서 관측)

앞의 4건은 한 모양이다. **질문이 정정·해지의 결과값을 요구했는데 근거에는 원본만
왔고, 모델이 "정정공시에 대한 언급이 없으므로 … 유지됩니다" 로 답했다.**
근거에 있는 금액을 그대로 옮겼으니 `supported=True` 는 거짓이 아니다 — 판정 축이
틀렸을 뿐이다. `Q-049` 만 다르다. 근거에 반기보고서와 사업보고서가 함께 왔고
모델이 **반기 누계**(11,830,403)를 연간 값으로 답했다. 여기서도 답한 수치는
근거 안에 있다.

### 검사 4종 — `verify_completeness(question, answer, evidence, *, companies=None)`

| kind | 전제(없으면 `skipped`) | 결함 | 귀속 |
|---|---|---|---|
| `evidence_gap` | 질문이 정정·해지 **결과값**을 요구 | 답이 근거 부족을 자백 | `RETRIEVAL` |
| `stale_value` | 근거에 대체본과 최신본이 **서로 다른 문서로** 함께 있음 | 답이 대체본 값만 씀 | `GENERATION` |
| `interim_source` | 연간 질의 + 반기·분기와 사업보고서가 함께 옴 | 답이 반기 값만 씀 | `GENERATION` |
| `missing_corp` | `companies` 를 넘겼고 2곳 이상 | 근거에 없는 기업이 있음 | `RETRIEVAL` |

귀속은 **근거가 안 온 것**(`RETRIEVAL`)과 **온 근거를 잘못 고른 것**(`GENERATION`)으로
가른다. 반환 규격은 `verify_calculation` 과 같다 —
`ok` · `llm_calls` · `checked` · `skipped` · `failed_kinds` · `failure_stage` · `reason`
(불일치 목록만 `mismatches` 대신 `gaps`). Phase I 의 A6 arm 이 이 판정의 Δ 를 잰다.

### 존재 질의를 걸면 안 된다 — 과잉 차단이 더 나쁘다

`Q-026` 이 경계다. 근거에 정정본이 없는 것은 `Q-005` 와 **똑같지만 정답**이다.
질문이 "정정공시가 **있었는가**" 라서 정정본의 부재 자체가 답이기 때문이다.
그래서 규칙은 정정 축을 건드리는 질문 전부가 아니라 **결과값을 요구하는 질문**
(`얼마로 바뀌` · `반영 후` · `얼마나 증가` · `이력` …)에만 걸고, 존재 질의
(`정정공시가 있었는가` · `철회되었는가`)는 전제에서 뺀다.

`Q-048` `Q-054` 도 결과값을 요구하지만 **정답**이다. 이 둘은 답이 정정 전·후를
모두 말하므로 자백 신호가 없어 통과한다 — 전제는 성립하되(`checked`) 발화하지 않는다.
(A6 스냅샷에서 `Q-048` 이 실제로 발화한 적이 있다. 자백 신호 때문이 아니라
`stale_value` 의 두 결함 때문이었고, 아래 **재조정** 절에서 고쳤다.)

### 대체본 규칙에 결과값 전제를 왜 다는가 — 실측

`stale_value` 를 질문 전제 없이 "근거에 정정본이 있는데 답이 정정 전 값을 썼다" 로만
돌리면 dev 정답 문항에 **거짓 경보 4건**(`Q-008` `Q-031` `Q-033` `Q-034`)이 뜬다.
해지·정정 공시 자체를 묻는 질문은 원본 금액을 말하는 것이 정답이기 때문이다.
결과값 전제를 달면 **0건**이 된다.

### `ablation_a7` — 규칙은 한 줄도 안 고쳤는데 전제 성립 수가 움직였다

A7 은 arm 이 아니다. 플래그가 A6 과 하나도 다르지 않고 **코드가 바뀐 것**이다
(거절 강제 + 시점 규칙, 06-agent-tool F-9). 그런데 `checked` 가 이렇게 움직였다.

| kind | `ablation_a6` | `ablation_a7` | 배율 | 왜 |
|---|---|---|---|---|
| `evidence_gap` | 7 | 7 | 1.00 | — |
| `stale_value` | 7 | **6** | 0.86 | Q-040 이 근거 없이 거절로 빠져 체인 블록이 사라졌다 |
| `interim_source` | 3 | **2** | 0.67 | 같은 이유 |
| `missing_corp` | 3 | 3 | 1.00 | — |

배율이 전부 `PREMISE_DRIFT_FACTOR`(2.0) 밖이라 드리프트 경보는 안 뜬다. 그래도 수치를
새로 박는다 — **수치는 스냅샷과 함께만 의미가 있다**는 것이 이 절의 전부이기 때문이다.
정답이 36 → 38 로 늘어난 뒤에도 정답 문항 거짓 경보는 **0건**, 정밀도는 **1.00** 이다.

`stale_value` 는 A7 에서도 `Q-023` 한 건에만 발화한다. 시점 규칙이 답변을 "원공시 값 +
정정 이력" 형태로 바꿨는데도 거짓 경보가 안 생긴 이유는 규칙의 전제가 `used_stale and
not (said & latest_only)` 이기 때문이다 — 두 시점을 **함께** 쓴 답변은 전제에서 빠진다.

### 🔴 재조정 — 규칙이 틀린 게 아니라 규칙이 가정한 세계가 바뀌었다

A6 실행에서 발화 3건 중 **2건이 거짓 경보**였다 (정밀도 0.33). 저장 응답에서 원인을
직접 확인했고, 규칙을 먼저 고치지 않고 관측한 대로만 고쳤다.

| 문항 | 발화 kind | 관측한 원인 | 처방 |
|---|---|---|---|
| `Q-014` | `calculation` | 답이 말한 것은 하위 항목 `시설자금` 454,100,000,000원인데 레코드 `amount` 는 `조달금액` 2,000,113,200,000 이었다. 다중지점 질의라 서로 다른 기업·시점 레코드 8건이 전부 같은 대조를 받았다 | `amount` 레이블 게이트 (G-2) |
| `Q-048` | `stale_value` | ① 발화한 '대체본 값' 은 **20,230,515** — 답이 인용에 적은 **공시일** `20230515` 였다. 근거 머리글의 `(공시일 20230515)` 와 짝이 맞았다. ② 정기공시는 원공시와 정정본이 같은 `path` 를 갖고, 정정본 **본문** 블록과 `정 정 신 고` 블록이 **접수번호를 공유**한다. 기업 단위 추정이 이 둘을 갈라 정정본 본문을 대체본으로 몰았다 | 8자리 날짜 제외 + 같은 접수번호는 같은 문서 |

`Q-014` 의 발화는 완전성이 아니라 **계산** 검증이었다. 완전성만 재현하면 안 보인다.

**바꾼 전제 3가지.**

1. **`amount` 는 답변이 그 금액의 레이블을 말했을 때만 대조한다** (G-2).
2. **8자리 `YYYYMMDD` 는 값이 아니다.** 14자리 접수번호를 빼는 것과 같은 이유다 —
   값이 아니라 **주소**다. 근거와 답변 양쪽에서 똑같이 빠지므로 발화만 줄고
   적중은 줄지 않는다.
3. **같은 접수번호를 단 블록은 같은 문서다.** 서로 대체본·최신본일 수 없다.
   `[기재정정]` 머리글로 가르는 것은 `is_latest` 가 없을 때만 쓰는 **기업 단위
   추정**이라 여기서 한 발 물러선다.

셋 다 **발화를 줄이는 방향으로만** 움직인다. 새 발화 조건을 만들지 않았다 —
적중을 늘리려고 거짓 경보를 만들면 지금 맞히는 36건이 깨진다.

### 🔴 규칙이 낡는 것을 드러내는 계기 — `checked` 와 발화를 분리한다

이번 일의 기전은 하나다. **검색이 좋아지면 완전성 규칙의 전제가 더 자주 선다.**
발화 수만 보면 이 변화가 안 보인다.

| kind | `checked` (전제 성립) | 발화 | | |
|---|---|---|---|---|
| | `phase_h` | `ablation_a6` | `phase_h` | `ablation_a6` |
| `evidence_gap` | 7 | 7 | 5 | 0 |
| `stale_value` | **1** | **7** | 1 | 1 |
| `interim_source` | 4 | 3 | 1 | 0 |
| `missing_corp` | 3 | 3 | 0 | 0 |

`stale_value` 의 전제가 **1회 → 7회(7배)** 로 뛰었다. 발화는 1회로 같다. 거짓 경보는
바로 여기서 나왔다 — 골든 근거 38/60 → 59/60 이 되면서 "대체본과 최신본이 함께
온다" 는 전제가 훨씬 자주 서고, 규칙의 세부 결함이 그제서야 드러난 것이다.

```python
critic.completeness_audit(reports, baseline="phase_h")
# → {"checked": {...}, "fired": {...},
#    "fire_rate": {...},          # 발화 / 전제 성립. 전체 문항 수로 나누지 않는다
#    "drift": {"stale_value": {"checked_then": 1, "checked_now": 7, "factor": 7.0, ...}},
#    "drifted": ["stale_value"]}  # factor >= PREMISE_DRIFT_FACTOR(2.0)
```

`fire_rate` 의 분모는 **전제가 선 횟수**다. 전체 문항 수로 나누면 전제가 안 선
문항까지 분모에 들어가 규칙이 저절로 좋아진 것처럼 보인다.

기준선은 `critic.COMPLETENESS_SNAPSHOTS` 에 스냅샷 이름·응답 경로·골든 근거와 함께
박아 뒀고, `tests/test_critic.py::test_completeness_premise_counts_match_the_recorded_snapshot`
가 저장 응답 전수로 매번 재확인한다. **다음 트랙이 Recall 을 더 올리면 이 표가
먼저 어긋난다** — 그때가 거짓 경보를 다시 재야 할 때다.

### 안 한 것

- **`SYSTEM_CRITIC` 프롬프트는 건드리지 않았다.** 완전성 항목을 프롬프트에 더하면
  검증에 LLM 호출이 필요해지고, 그 변경의 과잉 차단 여부를 이 트랙에서는
  **측정할 수 없다**. 측정 못 하는 차단은 넣지 않는다.
- **적중을 늘리는 새 규칙은 넣지 않았다.** A6 에서 못 잡은 오답 5건은 그대로 둔다.
  거짓 경보 0 을 지키는 것이 이 트랙의 계약이고, 확신할 수 없으면 통과시킨다.
- `verify_calculation` 의 나머지 5종은 그대로다. `skipped` / `mismatches` 분리도
  유지한다 — 레이블 게이트도 불일치가 아니라 `skipped` 로 적는다.
- `missing_corp` 은 `companies` 를 넘겼을 때만 돈다. 두 스냅샷 모두 전제 3회
  성립 · **0회 발화** — `pipeline._sufficiency` 의 `missing_corp` 이 이미 같은 축을
  앞에서 막고 있다.
