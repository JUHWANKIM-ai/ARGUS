## H-1. 단계별 실패 귀속

각 문항의 실패를 **가장 앞선 단계에 귀속**시킨다. 뒤 단계는 앞이 실패하면 자동으로 실패하므로,
첫 실패 지점만 세야 병목이 보인다.

| 실패 유형 | 판정 기준 | LLM 필요? |
|---|---|---|
| `ROUTING` | 라우팅이 틀림 (unanswerable 오판 · 기업·문서군 추출 실패) | ❌ 무료 |
| `RETRIEVAL` | 골든 `rcept_no` 가 **모든 hop 의 `ids` 어디에도** 없음 | ❌ 무료 |
| `RANKING` | 후보엔 있으나 근거 칸까지 못 올라옴 (정기공시는 문서는 맞고 섹션이 틀림) | ❌ 무료 |
| `TOOL` | `critic.verify_calculation()` 이 결정적 재계산과 불일치 판정 | ❌ 무료 |
| `GENERATION` | 근거는 맞는데 답이 틀림 | closed ❌ / open ✅ |
| `VERIFY` | critic 이 잡았어야 할 오류를 통과시킴 | ❌ 무료 |

**6종 중 5종이 골든셋 대조만으로 판정된다.** open 문항의 `GENERATION` 만 judge 가 필요하다.
`CITATION` 은 단계가 아니라 **보조 지표**로 뺐다 — 근거 표기 누락은 답의 정오와 독립이고,
단계로 두면 첫 실패 귀속에서 앞 단계를 가린다. 별도 표기율로 집계한다.

### 정답률 분모에서 빼는 것 · 따로 세는 것

| 라벨 | 정의 | 분모 |
|---|---|---|
| `DATA_LIMIT` | **원본에 값이 없다** (공시유보 · 금액 없는 서식 · 범위 밖 참조 · 본문 부재) | **제외** |
| `HALLUCINATION` | `answerable=false` 인데 거절하지 않고 답을 지어냄 | 포함 (**진짜 실패**) |

데이터 상한을 실패로 세면 병목 판정이 통째로 틀어진다. 반대로 환각을 상한으로 봐주면
정보한계 대응 능력이 측정에서 사라진다. **둘은 반대 방향의 오염이라 반드시 갈라야 한다.**

### 골든이 2건 이상이면 하나만 빠져도 실패다

`RETRIEVAL` 을 "첫 골든을 찾았는가"로 재면 **다건 근거 문항이 통째로 GENERATION 으로 샌다.**
dev 36문항 중 18문항이 골든 2건 이상이고, 실측 실패 17건 중 11건이 여기서 나왔다 (§H-6).

### 같은 단계 안에서도 arm 이 갈린다 — `root_cause`

`RETRIEVAL` 이 "인덱스에 없다"인지 "에이전트가 안 물어봤다"인지에 따라 처방이 정반대다.
`scripts/error_analysis.py` 의 `root_cause()` 가 기계적으로 가른다.

| root_cause | 뜻 | arm |
|---|---|---|
| `CHAIN_NOT_TRAVERSED` | 놓친 골든이 `related` 로 이미 연결돼 있다 | A4 |
| `MULTI_POINT_QUERY` | 다른 시점·다른 기업을 한 번 더 물었어야 했다 | A4 |
| `WRONG_SECTION` | 문서는 맞고 목차 경로가 틀렸다 | A3 |
| `INDEX_FIELD_MISSING` | 근거 마크다운에 값 자체가 없다 | A1b |
| `REASONING` | 값은 근거에 있는데 답이 틀렸다 | A4 |

## H-2. 축별 교차 집계 — 핵심

병목은 **전체 평균이 아니라 축별로 다르게** 나타난다.

```
① 난이도   × 실패단계    난이도가 올라갈수록 어디서 깨지는가
② 답변형식 × 실패단계    closed 와 open 의 실패 원인이 다른가
③ 과제유형 × 실패단계    복합추론이 검색에서 깨지는가 추론에서 깨지는가
```

채워진 표는 [§H-5.4](#h-54-축별-주변합) 에 있다 (dev 12/12/12 · 18/18 · 12/12/12).

### 해석 규칙 → arm 연결

| 관측 | 원인 | 대응 arm | **실측 (dev)** |
|---|---|---|---|
| 난이도↑ 할수록 `RETRIEVAL` 증가 | 검색 리콜 부족 | **A2 임베딩** | ✅ 관측됨 (상 9건). 단 **리콜 부족이 아니라 미탐색** — A2 가 아니라 A4 |
| 난이도 무관 `RANKING` 높음 | 순위 품질 | **A3 리랭커** | 2건. periodic 목차 경로 한정 |
| `상` 에서만 `REASONING` 급증 | 다단계 추론 한계 | **A4 Agent 루프** | ❌ 상의 `GENERATION` 은 **0건** |
| `closed` 가 `TOOL` 에서 깨짐 | **policy §4 위반** — 계산이 LLM 으로 샘 | **A5 계산 Tool** | ❌ **0건**. 재계산 12회 전부 통과 |
| `open` 만 `CITATION` 나쁨 | 서술형 근거 표기 강제 부족 | 프롬프트 · **A6 Verifier** | ✅ closed 13/18 vs open 10/18 |
| `REFUSAL` 양방향 오류 | 정보한계 임계 오설정 | 라우터 임계 조정 | ❌ 정보한계 6/6 정답 · 환각 0 |

**해석 규칙 자체가 절반 틀렸다.** "난이도↑ → `RETRIEVAL`↑" 은 맞았지만 원인 진단이 틀렸고,
나머지 넷 중 셋은 관측되지 않았다. 규칙표는 측정 전의 추측이었고 실측이 이겼다.

## H-3. Closed / Open 채점 분리 — policy §5

| | 정답 판정 | 추가 지표 |
|---|---|---|
| **closed** | `answer_form` 별 정규화 EM | Self-Consistency 일치율 |
| **open** | LLM-as-a-Judge ([02](02-golden-set.md) B-5 규격) | Groundedness · Evidence Score |

**두 축을 합산한 단일 점수를 만들지 않는다.** 합치면 어느 쪽이 나쁜지 사라진다.

### 자동 채점기가 틀리면 병목 판정도 틀린다 — 실측으로 고친 3건

첫 집계에서 **채점기 버그가 실패 단계를 3건 오염**시켰다. 전부 회귀 테스트로 고정했다.

| 증상 | 원인 | 오염된 결론 |
|---|---|---|
| Q-040 을 `HALLUCINATION` 으로 셈 | 거절 정규식이 파이프라인 고정 문구만 잡음. 모델이 자기 말로 거절("…포함되어 있지 않습니다")하면 환각 처리 | 환각 1건 → **실제 0건** |
| Q-025 를 오답으로 셈 | boolean 이 "네, … 했습니다"를 못 읽음 | `VERIFY` 1건 → **실제 정답** |
| Q-047 을 오답으로 셈 | boolean 이 "A가 크다 … 따라서 B가 작다"를 '판정 불가'로 버림. **결론은 마지막에 온다** | `GENERATION` 1건 → **실제 정답** |

추가로 **정기공시 근거 적중을 문서 단위로 재던 것**을 섹션 단위로 고쳤다.
Q-052 는 문서는 맞히고 목차 경로를 틀렸는데 doc 단위로는 '적중'이라 `GENERATION` 으로 샜다.
→ `RANKING/WRONG_SECTION` 이 정확한 진단이고, 처방이 A4 가 아니라 A3 로 바뀐다.

### 재실행 안전장치

| 위험 | 장치 |
|---|---|
| 재실행 재과금 | 응답·judge 를 문항별 JSON 으로 캐시. 온도 0.0 이라 결과 동일 |
| 429 로 중단 | `with_retry()` 지수 백오프 + 문항 간 1초 간격 |
| **429 가 오답으로 굳음** | 파이프라인은 상류 장애를 삼키고 한계 고지를 반환한다(게이트 F). `run_case()` 가 trace 의 `생성 실패` 를 되던져 **캐시에 쓰지 않는다** |
| heldout 오염 | 스크립트에 `heldout.jsonl` 경로가 없고 `_assert_dev_only()` 가 split 검사. 테스트가 소스에 문자열이 없음을 확인 |

> 🔴 실측 중 실제로 429 가 났고, Q-051·Q-053 이 오답으로 캐시됐다. 위 장치는 그 사고 이후에

| 임상·품목허가 (금액 없는 서식) | 84건 (`투자판단관련주요경영사항`) | 0 |
| `※관련공시` 2023-01-01 이전 참조 | 1,005 / 2,041 (49.2%) | 0 (Q-007·Q-008·Q-023·Q-024·Q-033·Q-034 가 플래그를 물지만 답은 본문에 있다) |

플래그가 붙는 것과 답을 막는 것은 다르다. **막힌 것만 분모에서 뺐고, 그 결과가 0이다.**

### H-5.6 근본 원인 — 6단계만으로는 arm 이 안 갈린다

같은 `RETRIEVAL` 이라도 "인덱스에 없다"(→ A2 임베딩)와 "에이전트가 안 물어봤다"(→ A4 루프)는
처방이 정반대다. 기계로 갈랐다.

| 단계 / 원인 | 건수 | 문항 | 겨냥할 arm |
|---|---|---|---|
| `RETRIEVAL / CHAIN_NOT_TRAVERSED` | **6** | Q-005 Q-006 Q-018 Q-023 Q-024 Q-030 | **A4** |
| `GENERATION / INDEX_FIELD_MISSING` | **4** | Q-010 Q-020 Q-022 Q-028 | **A1b** |
| `RETRIEVAL / MULTI_POINT_QUERY` | **4** | Q-012 Q-014 Q-015 Q-046 | **A4** |
| `RANKING / WRONG_SECTION` | 2 | Q-049 Q-052 | **A3** |
| `RETRIEVAL / CHAIN_PARTIAL` | 1 | Q-035 | **A4** |

**🔴 검색은 실패하지 않았다. 검색을 안 한 것이다.**
놓친 골든 11건 전부를 **그 문서의 실제 기간으로 다시 질의**해 봤다 (LLM 0회):

```
Q-005 20260203800709  ym=202602 -> rank 1      Q-023 20240322800822  ym=202403 -> rank 1
Q-006 20250225800764  ym=202502 -> rank 1      Q-023 20250605800294  ym=202506 -> rank 3
Q-012 20260305001006  ym=202603 -> rank 1      Q-023 20251030800728  ym=202510 -> rank 3
Q-014 20241030000098  ym=202410 -> rank 1      Q-023 20251204800395  ym=202512 -> rank 3
Q-015 20240529800105  ym=202405 -> rank 1      Q-035 20251217800853  ym=202512 -> rank 2
Q-018 20241223800052  ym=202412 -> rank 1      Q-035 20251217800800  ym=202512 -> rank 1
Q-024 20250102800164  ym=202501 -> rank 1      Q-046 20260310002820  base_year=2025 -> rank 1
Q-030 20241113000148  ym=202411 -> rank 1
```

**14건 전부 top-3, 11건이 1위다.** 인덱스에도 있고 BM25 도 찾는다.
파이프라인이 hop 0 에서 `verdict=sufficient` 를 내고 멈췄을 뿐이다 —
`_sufficiency()` 는 "원공시 1건 + 금액 라벨" 로 충족되므로 정정본을 찾을 이유가 없다.

그리고 놓친 7건은 **`exchange_records.jsonl` 의 `related` 에 이미 연결돼 있다.**
`get_history` 도구가 이미 있는데 ReAct 루프가 한 번도 부르지 않는다.

**`GENERATION` 4건도 생성 실패가 아니다.** 근거 마크다운에 답이 아예 없었다:

| 문항 | 요구 필드 | 근거 마크다운에 실린 것 |
|---|---|---|
| Q-010 | 권면총액·표면이자율·전환가액·사채만기일 | 공시일·섹터·기간·확정일 **뿐** |
| Q-022 | 시설자금 4,541억 · 타법인증권취득 1조5,460억 | 〃 |
| Q-020 | 보유비율 30.67% · 보유주식 196,488,145주 | 공시일·섹터·확정일 **뿐** |
| Q-028 | 보유비율 3.65% | 〃 |

`pipeline.py` 의 `FIELD_HINTS` 주석이 이미 실측으로 적어 둔 사실이다 —
"holding 실측 1,083건에 금액 54건뿐이고 나머지 라벨은 없다".
**모델이 잘못한 게 아니라 우리가 안 뽑았다.** 원문 XML 에는 값이 있으므로 `DATA_LIMIT` 도 아니다.

### H-5.7 TOOL 과 VERIFY 가 0인 이유 — 확인한 결과다

`verify_calculation()` 을 dev 42문항 전수에 돌렸다 (LLM 0회).

```
checked   amount 8 · period 4        (11문항에서 1종 이상 검사)
skipped   share 16 · period 15 · amount 8
mismatch  0
```

**`skipped` 와 `mismatches` 를 섞지 않았다.** 31건의 `skipped` 는 "답변이 그 수치를 말하지
않았다"이지 "틀렸다"가 아니다. 실제로 검사한 12건은 전부 통과했다 — **dev 에서 계산 오류는
한 건도 없다.** policy §4 가 우려한 "계산이 LLM 으로 새는" 현상은 관측되지 않았다.

`VERIFY` 0건은 첫 실패 귀속의 결과다. 다만 **부수 관측이 하나 있다**:
in-pipeline critic 은 18문항에서 돌아 12건을 `supported=True` 로 통과시켰고,
그중 **5건(Q-005·Q-006·Q-018·Q-035·Q-049)이 오답**이었다.
critic 은 "주어진 근거로 답이 지지되는가"만 보고 **"근거가 완전한가"는 안 본다.**
정정본이 빠진 채로도 원공시만 보면 답이 지지되므로 통과한다 — A6 설계에 반영할 사실이다.

## H-6. 예상 검증 — 예상은 틀렸다

착수 시점 가설은 **"검색은 이미 강하니 GENERATION·TOOL·VERIFY 에 실패가 몰릴 것"** 이었다.

| | 예상 | 실측 |
|---|---|---|
| GENERATION | 다수 | 4건 — 그나마 **전부 인덱스 필드 부재**로 재분류 |
| TOOL | 다수 | **0건** |
| VERIFY | 다수 | **0건** |
| RETRIEVAL | 소수 | **11건 (64.7%)** |

**가설이 깨진 지점은 "검색이 강하다"의 정의였다.** 기존 실측
(`exchange dev 16/16 · periodic dev 12/12`)은 **문항당 골든 1건**을 찾았다는 뜻이고,
골든이 2건 이상인 문항에서 **두 번째 건**을 세지 않았다. dev 36문항 중 18문항이 골든 2건
이상이고, 실패 17건 중 11건이 정확히 여기서 나왔다.

> 한 문항의 검색은 "첫 골든을 찾았는가"가 아니라 **"필요한 골든을 다 찾았는가"** 로 재야 한다.
> [09](09-ablation.md) 의 Recall@k 도 문항 단위 완전회수로 다시 정의한다.

## H-7. 난이도 라벨 검증

원칙: **'하' 셀 정답률이 '상' 셀보다 낮으면 라벨이 틀린 것.**
축 주변합은 단조 감소(하 0.750 > 중 0.667 > 상 0.167)라 **난이도 축 자체는 유효하다.**
셀 단위로는 두 곳이 뒤집혔다.

| 문항 | 현재 | 실측 | 판정 |
|---|---|---|---|
| **Q-014** | 하 | ✗ `RETRIEVAL/MULTI_POINT_QUERY` | **중으로 올릴 것.** 서로 다른 두 기업의 서로 다른 달 공시 2건이라 질의를 두 번 나눠야 한다. B-3 규칙 7('연산 0회 → 하')이 **질의 횟수를 세지 않는** 것이 원인이다. 02 문서의 후보 지목을 실측이 지지한다 |
| **Q-049** | 하 | ✗ `RANKING/WRONG_SECTION` | **중으로 올릴 것.** 두 기업이 같은 지표를 다른 목차 경로(`매출 및 수주상황` vs `요약재무정보`)에 싣는다. 문항 `notes` 가 이미 적어 둔 사실이고 실측이 확인했다. `multi_compare×open×하` 셀이 0/2 인 유일한 원인 |
| Q-020 | 하 | ✗ `GENERATION/INDEX_FIELD_MISSING` | **하 유지.** 실패 원인이 난이도가 아니라 우리 인덱스다. 02 문서의 재조정 후보 지목은 **실측이 지지하지 않는다** |
| Q-025 · Q-026 | 하 | ✓ ✓ | **하 유지.** 02 문서 후보였으나 둘 다 정답 |
| Q-047 | 하 | ✓ | **하 유지 + 주석.** 결론은 맞았으나 중간 단위환산이 틀렸다(`3,336,059억 × 1,000`). 02 문서의 '단위 정규화 → 중' 논거는 절반만 맞다 |
| Q-034 | 중 | ✓ | 중 유지 |
| Q-028 | 중 | ✗ `INDEX_FIELD_MISSING` | 중 유지. 원인이 라벨이 아니다 |

**변별력 경고 — `multi_compare × closed` 는 세 난이도가 전부 1/2 다.**
이 행에서 난이도 축이 아무것도 가르지 않는다. Phase I 에서 이 행의 Δ 는 읽지 말 것.

> 🔴 `evalset/` 은 이번 Phase 에서 수정하지 않았다. 위 두 건은 **지목만** 한 것이다.

**갱신 (2026-08-09, Ablation v1 이후) — 지목 근거가 뒤집혔다.**
검색이 38/60 → 59/60 이 되자 A6 에서 **Q-014 · Q-049 둘 다 정답**이 됐다.
'중으로 올릴 것' 의 근거였던 오답이 사라졌으므로 **라벨을 옮기지 않는다.**
반대로 **Q-047 이 A6 에서 오답(`VERIFY`)으로 뒤집혀** 후보로 돌아왔다 —
'하' 12문항 중 유일한 오답이다. 갱신된 판정표는
[02 B-3](02-golden-set.md#난이도-재조정--실측-판정-phase-h--ablation-v1-2026-08-09) 에 있고,
`tests/test_evalset.py::test_difficulty_relabel_candidates_stay_pinned` 이 9건의 라벨을 못박는다.
한 문항만 옮기면 C5/C5b 가 깨지고 위 §H-5.4 의 `/12` 분모가 조용히 무효가 되기 때문이다.

## H-8. 병목 상위 2개 → [09](09-ablation.md) LOO 입력

### 1위 — 정정·후속 공시 체인 미탐색 (7건 · 실패의 41%)

```
Q-005 Q-006 Q-018 Q-023 Q-024 Q-030 (CHAIN_NOT_TRAVERSED) + Q-035 (CHAIN_PARTIAL)
```

**근거 셋.**
① 상 난이도 실패 10건 중 7건이 여기다. 상 12문항 중 10문항이 `correction_tracking=true` 이고 정답은 2건.
② 놓친 골든이 **이미 `related` 로 연결돼 있고** 재질의하면 rank 1~3 이다 — 검색력이 아니라 미탐색이다.
③ `get_history` 도구가 이미 구현돼 있는데 ReAct 루프가 한 번도 호출하지 않는다.

**→ arm `A4` (Agent 루프).** `_sufficiency()` 에 "정정 체인 미확인" 조건을 넣고
`get_history` hop 을 추가한다. LLM 0회로 붙는다.
**LOO `L1 = A6 − 정정체인 hop`.** 이 Δ 가 가장 클 것으로 예상되며, 예상이 또 틀리면 그렇게 보고한다.

### 2위 — `major`·`holding` 레코드 필드 부재 (4건 · 24%)

```
Q-010 Q-022 (major) · Q-020 Q-028 (holding)
```

**근거 둘.**
① 문서군별 정답률이 `major 0/4 (0%)` · `holding 1/4 (25%)` 로 `exchange 9/16` · `periodic 15/18` 과 자릿수가 다르다.
② 근거 마크다운에 요구 필드가 **한 줄도 없다.** 원문 XML 에는 있으므로 `DATA_LIMIT` 이 아니라 추출 누락이다.

**→ arm `A1b` (인덱스 커버리지).** `major` 에 권면총액·표면이자율·전환가액·자금용도별 금액,
`holding` 에 보유비율·보유주식수를 추가한다. LLM 0회 파싱이다.
**LOO `L2 = A6 − major·holding 필드 추출`.**

### 겨냥할 실패가 없는 arm — 실측이 순서를 또 바꾼다

| arm | dev 에서 겨냥하는 실패 | 판정 |
|---|---|---|
| **A2 임베딩** | **0건** | 놓친 골든 14건 전부 BM25 재질의로 top-3. **후순위로 내린다** |
| **A3 리랭커** | 2건 (`WRONG_SECTION`) | periodic 목차 경로 한정. 유지하되 기대치 낮게 |
| **A5 계산 Tool** | 0건 (`verify_calculation` mismatch 0) | dev 에서 계산 오류 없음. **Δ 를 못 잴 수 있다** |
| **A6 Verifier** | 0건 (첫 실패 귀속 기준) | 단, critic 이 오답 5건을 통과시켰다 — 근거 **완전성** 판정을 추가하면 겨냥점이 생긴다 |

> [09-ablation §I-7](09-ablation.md) 의 갱신 규칙대로, **A2 를 A1b·A4 뒤로 미루는 것**이
> 이 Phase 의 arm 순서 권고다. A1b 가 A2 앞이어야 한다는 §I-2 의 논리와 방향이 같다.

### 환류 대상 3건이 어떻게 처리됐는가

Q-101 은 반대로 명확하다. 근거 블록에 공시일·섹터·확정일 세 줄뿐이고 **금액 줄이 아예 없다.**
문항 `notes` 가 이미 "`schema_matched=false` 라 정규화 amount 가 null 이고 값이 본문 문장
안에만 있다 — `INDEX_FIELD_MISSING` 과 같은 조건이다" 라고 적어 두었다. **A1b 다.**

**분류 코드는 고치지 않았다.** 새 버킷을 넣으면 v1 ↔ v2 의 `root_cause` 히스토그램이 같은
이름으로 다른 것을 세게 되고, 그 표가 09 의 arm 겨냥 근거다. 위 배분표가 정본이고,
분류 자체를 바꾸는 것은 **전용 측정과 함께** 별도로 다룰 일이다.

### H-10.7 밸류체인 6/12 — 별도 행이다

`--cohort valuechain` 12문항. **그리드와 같은 분모에 넣지 않는다** — 현재 시스템이
원리상 못 푸는 문항이 들어 있어(Q-117 은 `한전기술` 이 계약상대로 등장한 적이 없어
노드가 아니다) 섞으면 양쪽이 다 거짓말이 된다.

```
정답 6/12 · ROUTING 1 · RETRIEVAL 3 · TOOL 1 · GENERATION 1 · DATA_LIMIT 0
근거 표기율 0.25
```

검색 지표는 **재는 경로에 따라 값이 다르다. 둘 다 적는다.**

| 경로 | 골든 근거 | Recall@5 | 전건 | 정본 용도 |
|---|---|---|---|---|
| 리트리버 하네스 (`ablation.retrieval_metrics`, LLM 0회) | **30/46** | 26/46 | 5/12 | **T5 회귀 기준선** — 이 값과 비교한다 |
| 파이프라인 관통 (`answer_question`, v2 실행) | **28/46** | — | 5/12 | 정답률과 같은 실행의 근거 칸 |

차이는 **Q-111 한 문항**(하네스 2/3 → 파이프라인 0/3)에서 전부 나온다. 하네스는
`_gather_evidence` 를 예산 새로 잡아 직접 부르고, 파이프라인은 라우팅·충분성 판정·검증까지
지나며 예산을 나눠 쓴다. **회귀 감시는 하네스 값(30/46)으로 계속 하고**, 정답률을 설명할
때는 파이프라인 값(28/46)을 쓴다. Q-111 의 격차는 별도 확인 대상으로 남긴다.

검색이 골든의 61~65% 만 회수하는데 정답률이 50% 이므로, **이 트랙의 병목은 여전히 검색이고**
생성이 아니다. `TOOL` 1건은 이 트랙에서만 나왔다 — 허브별 금액 합산이 실제 연산이라
그렇다.
