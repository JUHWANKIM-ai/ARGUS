## F-2. 계산 도구 노출 — 완료

`compute.py` 를 만들어놓고 **`TOOL_SPECS` 에 넣지 않아** LLM 이 계산을 스스로 하던 상태였다.
7종을 function calling 스펙으로 노출하고 `_DISPATCH` 에 등록했다.

| 도구 | 입력 | 반환 | policy §4 항목 |
|---|---|---|---|
| `calc_pct_change` | before, after | `value`·`rounded`·`unit`·`expr` | 증가율 |
| `calc_share` | part, whole | 〃 | 비율 |
| `calc_total` | values[] | 〃 | 합계 |
| `calc_mean` | values[] | 〃 | 평균 |
| `calc_cagr` | begin, end, years | 〃 | CAGR |
| `calc_compare` | a, b | `larger`·`diff`·`ratio` | 순위 |
| `calc_period` | start, end | `value`·`years`·`months` | (LLM 오답 영역) |

설계 규칙

- **인자는 전부 `required`** — 계산 도구는 인자가 빠지면 계산 자체가 성립하지 않는다.
- `rounded` 는 답변에 그대로 쓰라고 주고, `expr` 은 계산 과정 **설명**용으로 준다.
  LLM 은 `expr` 을 읽고 서술할 뿐 재계산하지 않는다.
- `expr` 은 지수표기를 쓰지 않는다 (`compute.fmt_num`). `2.27648e+13` 이 답변에 새면 안 된다.
- 계산 불가 입력(0 나눗셈·빈 목록·해석 불가 날짜)은 예외가 아니라 `{"error": ...}` 로 돌려준다.
  `execute()` 가 `ValueError` 를 잡으므로 파이프라인이 죽지 않는다.

**실측 근거**: HCX 는 계약기간 산정을 Direct·CoT **둘 다 오답**(`8년 5개월` → `9년 5개월`).
`calc_period("2025-07-24", "2033-12-31") → "8년 5개월"` 이 회귀 테스트로 고정돼 있다.

## F-3. ReAct 반복 루프 — 완료

단발 검색을 `_gather_evidence` 안의 반복 루프로 바꿨다. **LLM 호출은 여전히 0회다.**

```
검색 → 근거 충분? ─ 예 → 생성
          └─ 아니오 → 질의 재구성 → 재검색 (hop ≤ 3, 총 스텝 ≤ 8)
```

**hop 0 은 최초 검색이라 예산을 쓰지 않고, 재검색 3회가 `Budget.spend_hop()` 을 쓴다.**
상한을 넘겨도 예외를 밖으로 던지지 않는다 — 그 시점 근거로 생성으로 넘어간다.

**스텝 상한 근거**: ReAct 논문에서 정답 궤적 중 7스텝을 쓴 것은 **0.84%**.
주최 측 참조 아키텍처도 **최대 8스텝**. 도구 호출 1건 = 1스텝.

### 재구성 4단 + 체인 hop (`agent/query.py::plan_hops`, `pipeline._expand_chain`)

**필터는 넓히고 질의는 좁힌다** — 기간·기업 필터가 걸러주던 잡음을 필터를 풀면 질의어가 뒤집어쓴다.

| hop | 전략 | 기간 필터 | 기업 필터 | 질의어 | `top_k` |
|---|---|---|---|---|---|
| 0 | `narrow` | 연월(또는 연도) | ✅ | 전체 어휘 | 5 |
| 1 | `relax_period` | 연월 → 연도 → 없음 | ✅ | 전체 어휘 | 8 |
| 2 | `corp_only` | 없음 | ✅ | **핵심어만** | 10 |
| 3 | `global` | 없음 | ❌ | 핵심어만 | 10 |

핵심어(`core_terms`) = 숫자 토큰과 **실측 DF ≥ 0.30** 어휘를 뺀 나머지.
1,469건 기준 `계약` 0.80 · `상대` 0.77 · `금액` 0.73 · `매출` 0.72 · `대비` 0.72 · `정정` 0.43.
서술어 어미는 떼어내 어간을 살린다 — `체결한`→`체결`(불용어, 제거) · `해지된`→`해지`(변별어, 유지).

> **불용어 목록 정정** — `해지` 를 `체결` 과 나란히 손으로 불용어에 넣은 것이 잘못이었다.
> 실측 DF 는 `해지` 0.014(21건) 대 `체결` 0.766(1,125건) 이다. 되살리니 두산퓨얼셀 해지 3건
> 질의의 상위 3위가 1건 → 3건이 됐다 (16.9/16.2/16.1 vs 9.7/9.4/9.3).

### F-6 정정·후속 공시 체인 hop — Phase H 1위 병목

Phase H 실측: dev 36문항 정답률 19/36, 실패 17건 중 **RETRIEVAL 11건**. 그런데 놓친
골든 14건을 각 문서의 실제 기간으로 재질의하니 **전부 top-3 안에 있었고 11건은 1위였다.**
인덱스에도 있고 BM25 도 찾는다. **검색이 실패한 게 아니라 hop 0 에서 `sufficient` 를 내고
멈춘 것이다.** 그중 7건(전체 실패의 41%)은 `related` 로 이미 이어져 있는데
`get_history` 를 한 번도 부르지 않았다.

```
hop=0 검색 → 씨앗 판정(스텝 0) → get_history(스텝 1) → 충분성 판정 → 생성
                    │
                    └─ 대체본(is_latest=False)이 상위 후보에 있는가?
```

**체인은 hop 이 아니라 스텝 하나로 붙는다.** `plan_hops` 사다리 밖이라 재검색 예산(hop 3)을
쓰지 않고, `think_trace` 에는 `hop=5 strat=chain` 으로 남는다.

| 단계 | 비용 | 하는 일 |
|---|---|---|
| `tools.chain_probe(doc_id)` | **0 스텝** | 레코드 한 건 조회 — `is_latest` 와 링크 목록. `section_paths()` 와 같은 취급. 🔴 엣지를 **세 갈래로 갈라** 돌려준다 (`related` · `followups` 역방향 · `terminates` 순방향). `links` 는 종전대로 합집합 |
| `get_history(rcept_no)` | 1 스텝 | 정정 체인 + 후속 공시 + 🔴 `terminated`(해지 대상 원계약). `markdown` 을 함께 실어 돌려주므로 근거 재조회가 없다. `terminated` 는 `followups` 와 **절대 합치지 않는다** — 시간 방향이 반대라 합치면 원계약이 '후속 공시' 로 찍힌다(`Q-066` v2 오답의 기전). 대신 `include_followups` 로 **함께 가린다**(둘 다 `※ 관련공시` 가족이라, 따로 열면 `L4` 가 재는 것의 정의가 바뀐다) |

**연결 단서가 둘이다.** 정정은 `related`(정정 체인), 후속 해지는 `※ 관련공시` **역방향**이다.
실측: 해지 공시 20건 중 `related` 로 이어진 것은 **0건**, `※ 관련공시` 로 원계약을 명시한 것은
11건. `artifacts/references.jsonl` 의 `resolved` + `form_matched` 엣지만 뒤집어 쓴다
(`form_matched=False` 1,154건은 '같은 날 같은 기업' 만으로 붙은 약한 엣지라 잡음이다).

> **`is_latest` 는 체인 위치로만 정한다.** 금액 크기로 정하면 안 된다 — 한화오션 잠수함
> 체인은 1,102,000,000,000 → 443,500,000,000 → … → 899,400,000,000 으로 **줄었다가 오른다**.
> '가장 큰 값 = 최신' 규칙이었다면 전부 틀렸다. 회귀 테스트로 고정돼 있다.

### 충분성 판정 — LLM 0회

판정에 LLM 을 쓰면 hop 마다 호출이 붙어 6회 상한을 태운다. 네 가지만 본다.

| 규칙 | 임계 | 근거 |
|---|---|---|
| 후보 수 | `closed_lookup` 1 · `multi_compare`·`complex_reason` 2, **기업 수 이상**, CoT 경로는 2 이상 | ReAct 단독은 CoT 보다 낮다 (27.4 vs 29.4) — 더 돌린다고 이기지 않는다. 최소치만 채운다 |
| BM25 최고 점수 | **`≥ 10.0`** | 실측 — 무관 질의('우주선 발사 로켓 엔진' 8.7 · '블록체인 가상자산 채굴' 6.6) 와 평가셋 최고점 최솟값 10.8 사이 |
| 골든 필드 존재 | 질문이 요구한 필드 라벨이 근거에 있는가 (`금액:` · `대비:` · `기간:` · `계약상대:`) | 금액을 물었는데 근거에 금액 필드가 없으면 답을 만들 수 없다 |
| 기업 커버리지 | 비교 질의는 **기업마다 1건 이상** | 한쪽만 찾으면 비교가 성립하지 않는다 |
| **집합 완결성** | 근거 안의 문서가 가리키는 정정·후속 공시가 **하나도 안 빠졌는가** (`chain_open:접수번호`) | 앞의 넷은 전부 '개수' 축이라 덜 온 것을 다 왔다고 읽는다. dev 42문항 중 **18문항이 골든 2건 이상**이고 실패 11건이 정확히 거기서 났다 |

### 넓히는 것이 늘 이득은 아니다 — 3+3 가지 제동

체인 탐색의 진짜 위험은 못 찾는 게 아니라 **과잉**이다. 모든 문항에서 체인을 끌어오면
근거가 부풀고 잡음이 늘어 지금 맞히는 문항이 깨진다. 아래 셋은 dev 42문항 실측으로 정했다.

| 제동 | 값 | 실측 근거 |
|---|---|---|
| ① 씨앗은 **상위 후보**까지만 | `CHAIN_SEED_WINDOW = 2` | 3위까지 넓히면 Q-033(현재 정답)이 무관한 체인 11건을 끌고 온다 |
| ② 씨앗은 **대체본만** (`is_latest=False`) | — | 최신본을 씨앗으로 삼으면 Q-008·Q-031·Q-033·Q-034(전부 현재 정답)에 근거가 붙는다 |
| ③ 체인에서 끌어올 문서 상한 | `MAX_CHAIN_DOCS = 6` | 한화오션 잠수함 체인이 7건이라 상한이 없으면 근거 칸을 혼자 다 먹는다 |

절단(`MAX_EVIDENCE = 10`)은 **체인을 먼저 살린다**. 한화오션은 검색 5건 + 체인 6건 = 11건이라
도착 순서대로 자르면 **체인의 마지막 정정본(=정답)이 잘려 나간다.**

닫지 못한 링크(`chain_open`)만 남은 판정은 `stop=chain_unresolved` 로 루프를 끝낸다 —
도구 오류이거나 스텝이 마른 것이라 재검색으로 안 닫힌다.

### 기존 제동 3가지 (그대로 유지)

1. **`global` hop 은 기업 특정 질의에 근거가 이미 있으면 건너뛴다.** 다른 회사 공시가 섞이면
   요약·비교가 통째로 오염된다.
2. **`global` hop 은 `MIN_TOP_SCORE` 미만 후보를 버린다.** 필터가 하나도 없는 검색은 점수만이
   관련성의 보증이다. (실측: 카카오 전환사채 질의가 무관 공시 10건을 근거로 끌고 왔다 → 0건으로)
3. **코퍼스 기간(2023.01~2026.03) 밖 연도는 재검색하지 않는다.** 기간 필터를 푸는 순간 2021년
   질문에 2025년 공시가 근거로 둔갑한다. 범위 밖은 못 찾은 게 아니라 없는 것이다.

두 hop 연속 새 후보가 없으면(`stop=stalled`) 남은 hop 을 태우지 않는다.
단, **근거가 0건일 때는 수렴이 아니라 못 찾은 것**이므로 끝까지 넓힌다.

### `think_trace` hop 로그 — Phase H 입력

hop 별로 질의어·필터·후보 수·후보 `doc_id` 를 `key=value` 로 남기고 `pipeline.parse_hops()` 로 되읽는다.

```
hop=0 strat=narrow tool=search_chunks corp="HD현대일렉트릭" period=ym:202301 top_k=5
      q="HD 현대일렉트릭 2023 변압기" n=1 top_score=32.605 ids=exchange_20230131800162
hop=0 verdict=sufficient evidence=1
hop=1 verdict=insufficient evidence=1 reason=few:1<2,low_score:8.8<10.0,missing_corp:고려아연
hop=3 strat=global skip=corp_scoped (기업 특정 질의에 근거 2건 확보 — 전역 검색은 오염)
hop=5 strat=chain tool=get_history corp="삼성중공업" rcept=20230602800079
      latest=20260203800709 chain_length=2 n=1 top_score=- ids=exchange_20260203800709
```

```python
ids = [d for h in parse_hops(resp["think_trace"]) for d in h["ids"]]
RETRIEVAL  — 골든 rcept_no 가 ids 어디에도 없음
RANKING    — ids 에는 있으나 상위 3위 밖
```

`strat` 값: `narrow` · `global` · `toc_narrow` · `toc_corp` · `chain` ·
**`enumerate`** 🆕. 마지막 것은 `pipeline._enumerate_events` 다 — 한 기업의 한 서식을
**계약상대(canonical)별로 묶어 그룹이 큰 순서로 각 그룹의 최신본**을 한 건씩 담는다
(스텝 1 · LLM 0회 · 검색 0회). 기존 `not picked` 폴백과 **배타**(`elif`)로 둔다:
같은 hop 번호라 배타여야 `parse_hops` 가 두 종류를 한 레코드로 섞어 읽지 않는다.
발화 제동이 다섯이다 — ① exchange 문서군 ② 기업이 정확히 하나 ③ **그 기업이 발주처가
아닐 것** ④ 갈래를 묻는 표지(`갈래`·`나뉘`·`나뉜`·`유형`) ⑤ 검색이 이미 뭔가 찾았을 것.
실측 발화는 100문항 중 **1건(`Q-117`)** 이다(표지만으로는 11문항이 걸리는데 ①②③ 이
10건을 거른다).

`reason` 코드: `no_candidate` · `few:n<need` · `low_score:s<임계` · `missing_field:필드` ·
`missing_corp:기업` · **`chain_open:접수번호`**.
`notes` 에는 `skip=tool_error` · `stop=hop_budget` · `stop=step_budget` · `stop=stalled` ·
`stop=out_of_range` · **`stop=chain_unresolved`** 가 실린다.

체인으로 끌어온 문서도 `ids` 에 실린다 — Phase H 의 `RETRIEVAL`/`RANKING` 귀속이
"검색으로 못 찾았다" 와 "체인을 안 밟았다" 를 구분할 수 있어야 하기 때문이다.

### 체인 hop 실측 — dev 42문항, LLM 0회

정답률이 아니라 **골든 근거가 프롬프트에 실렸는가**를 잰다. 정답률은 Phase I 의 몫이다
(`_gather_evidence` 는 LLM 을 부르지 않으므로 이 표는 크레딧 0원으로 재현된다).

| 지표 | 수정 전 | 수정 후 |
|---|---|---|
| 골든 근거 적중 (건) | 38 / 60 | **49 / 60** |
| 골든 **전건** 적중 문항 | 20 | **27** |
| hop 합계 | 12 | **11** |
| 스텝 최대 (상한 8) | 3 | **4** |
| `get_history` 호출 문항 | 0 | 10 |

## F-7. 상류 장애를 삼키지 않는다

게이트 F 상 `/answer` 는 어떤 경우에도 5키 스키마를 돌려줘야 한다. 그래서 429 를 받아도
파이프라인은 죽지 않고 한계 고지를 채워 내보낸다. 문제는 **그게 모델의 정당한 거절과
구분되지 않는다**는 것이다 — 호출부가 그대로 캐시하면 전송 실패가 영원히 오답으로 굳는다.
실측으로 그 사고가 났다 (Q-051·Q-053).

스키마는 그대로 두고 `think_trace` 에 기계가 읽는 표식을 남긴다.

```
upstream_error stage=generate status=429 retryable=True 생성 실패: CLOVA 호출 실패 429: {...}
```

```python
pipeline.upstream_failure(resp["think_trace"])
# {"stage": "generate", "status": "429", "retryable": True}  또는 None
```

- `stage` 는 `generate` · `critic`. critic 이 죽은 것은 **검증을 안 한 것**이지 통과가 아니다.
- `retryable` 은 408·425·429·5xx 와 상태를 못 읽은 경우다. 401·400 은 재시도해도 같다.
- **`BudgetExceeded` 에는 표식을 붙이지 않는다.** 우리 상한은 장애가 아니다.
- 사람이 읽는 `생성 실패: …` 문구는 그대로 둔다 — 기존 호출부(`scripts/error_analysis.py`
  의 `run_case`)가 그 문구로 캐시를 막고 있다.

## F-8. periodic 섹션 하강 — **넣지 않는다** (판정, 2026-08-10)

게이트 F 의 마지막 미완 항목이었다. 결론부터 — **하강은 얻는 것이 0 이고 스텝을 2배 쓴다.**

### 겨냥할 오답이 0건이다

정기공시 골든 회수는 이미 0.929 이고(목차 축 없이는 0.679), dev 42 코호트의 정기공시
12문항 18골든 중 못 회수한 것은 **1건뿐**이다. 그 1건(Q-054)의 기전은 목차 깊이가 아니다.

```
hop=0 strat=toc_narrow path="정 정 신 고 (보고)" n=4
  ids=periodic_20240514001580 ×4      ← 같은 문서·같은 섹션의 조각 4개가 칸을 다 먹었다
```

원공시(`20240514000756`)가 못 들어온 것은 **한 셀 안의 문서 다양성** 문제다. 하강은 경로를
더 좁히는 조작이라 이 문항에서는 오히려 같은 섹션에 더 집중한다 — 반대 방향이다.

### 실측 — 하강을 붙여 그대로 돌려 봤다 (LLM 0회 · 임베딩 0회)

`path_hints` 가 고른 깊이 2단 경로 대신, **상위 목차로 먼저 검색 → 1위가 가리키는 하위
목차로 좁혀 재검색** 하는 경로를 시뮬레이션했다.

| | 골든 후보 회수 | hop 0 스텝 |
|---|---|---|
| 현재 (한 번에 경로 지정) | **17 / 18** | **27** |
| 하강 (상위 → 하위) | 17 / 18 | **54** |

**달라진 문항 0건.** 회수는 글자 하나 안 움직이고 스텝만 정확히 2배가 된다.

### 왜 얻는 것이 없는가 — 좁힐 여지가 이미 없다

| 관측 | 값 |
|---|---|
| 골든이 **경로 셀 안에서 1위**인 비율 | **26 / 27** (예외 1건은 3위, 그 문항도 정답) |
| 상위 목차만 걸었을 때 1위가 **지금 고른 하위 목차**와 같은 비율 | 8 / 23 |
| 공통 목차 경로 모집단 | 64개 (깊이 1단 26 · 2단 38) |

첫 줄이 결론이다. 골든이 이미 셀 안 1위이므로 **더 좁혀서 올릴 순위가 없다.** 둘째 줄은
위험 쪽이다 — 하강이 고르는 하위 목차가 지금 고른 것과 다른 경우가 15/23 이라, 회수가
안 깨진 것은 hop 0 이 경로 후보를 **2개** 보기 때문이지 하강이 정확해서가 아니다.

### 스텝 예산이 실제로 걸린다

현재 스텝 최대 5 (상한 8). hop 0 셀은 (경로 2 × 기업 최대 3) 이고 실측 최대가 4셀이다
(Q-047·Q-049 = 2기업 × 2경로). 셀마다 탐색 1스텝이 더 붙으면 hop 0 만 8스텝이 되어
정정 체인 스텝을 남길 자리가 없다. 근거 길이도 같은 방향이다 — 42문항 코호트 기준
문항당 최대 **11,385자**(dev 78 + 회귀 10 전체로는 11,675자)로 이미 토큰 비용에 직결된다.

### 그래서 게이트 항목을 고쳤다

"하강 동작" 을 억지로 체크하지 않는다. 목차 축이 검색을 가른다는 요구는 **한 번에 경로를
지정하는 지금 방식**으로 이미 충족돼 있고, 하강은 그 위에서 순손실이다.
정기공시에 남은 진짜 병목은 목차 깊이가 아니라 **섹션 인덱스에 `related` 축이 없다는 것**
(F-6 "아직 안 한 것") 과 **한 셀 안의 문서 다양성** 이다.

## F-9. 지목한 문서가 코퍼스에 없다 — 검색으로 구제하지 않는다

A1b 까지 환각 0건이던 것이 A4(Agent 루프 + 체인 hop)부터 1건 생겼다. 근거가 풍부해지자
답할 수 없는 질문에 지어냈다. 저장 응답이 기전을 그대로 보여준다 (Q-040).

```
hop=0 strat=toc_narrow filters=base_year=2026,doc_subtype=half  n=0   ← 지목한 문서가 없다
hop=1 strat=toc_corp   filters=-                                n=10  ← 필터를 통째로 풀었다
generate → 2026년 1분기 **분기보고서** 값을 '2026년 반기보고서' 로 답했다
```

정보한계 6문항 중 나머지 5건은 이 경로에 아예 안 들어온다 — 4건은 라우터가 범위 밖
기업·연도로 단락시키고(LLM 0회), 1건은 미래 예측이라 어떤 공시에도 값이 없다.
**Q-040 만 다른 점은 '완화하면 그럴듯한 근거가 생긴다'** 는 것이다.

사다리는 `못 찾았다` 와 `없다` 를 구분하지 못한다. 그래서 검색이 아니라 **manifest** 에
묻는다 (`router.missing_named_report`, 스텝 0 · LLM 0회 · 인덱스를 열지 않는다).

🔴 과잉 거절이 진짜 위험이라 문턱을 셋 뒀다.

| 문턱 | 이유 |
|---|---|
| 보고서 **종류만으로는 막지 않는다** | '제57기 사업보고서'(Q-046)·'기아 사업보고서'(Q-076)는 문서가 특정되지 않는다 |
| 사업연도·접수시점 축이 **둘 다 비어야** 막는다 | `base_year` 는 추정이 섞인다 — Q-052 '2024년 3월 20일 제출한 2023년 사업보고서' |
| 기업이 여럿이면 **한 곳이라도 있으면** 막지 않는다 | 비교 질의에서 한쪽만 없는 것은 거절 사유가 아니다 |

실측 (dev 78 + 회귀 10 = 88문항, LLM 0회): 발화 **2건** — Q-040 · Q-070. 둘 다
`answerable=false` 다. **답할 수 있는 문항에서의 발화는 0건.**

한계 고지 문구도 가른다. `UNANSWERABLE`("범위 안의 기업과 기간으로 질문해 주시면")은
여기서 틀린 안내다 — 기업도 연도도 범위 안이고 **그 보고서만** 없기 때문이다.
`NO_SUCH_REPORT` 가 어느 사업연도·종류를 확인해 줄지 되묻는다.
