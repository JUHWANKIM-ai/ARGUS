### A1b 는 실측으로 추가된 arm이다 (2026-08-09)

Phase F-3 ReAct 트랙이 평가셋 30문항을 전수로 돌려 골든 적중을 쟀다:

```
exchange 문서군    16 / 16  적중   (14건 1위, 2건 2위 — 전부 top-3)
미적중              8건 — 전부 major(4) · holding(4)
periodic           검색 대상 0건   ← 코퍼스의 95.4%
```

**미적중 8건은 검색 알고리즘의 실패가 아니다.** 인덱스가 `exchange` 1,469건만 덮어
후보 집합에 애초에 없었다. `exchange` 안에서는 BM25 가 이미 16/16 을 1~2위로 올린다.

→ **A2(임베딩)를 A1b 앞에 두면 안 된다.** 후보에 없는 문서는 어떤 임베딩으로도 못 찾는다.
A1b 없이 A2 를 재면 "임베딩이 별로다"라는 **틀린 결론**이 나온다.

> 이것이 [09-ablation](09-ablation.md) 을 살아있는 문서로 두는 이유다.
> 계획 시점의 arm 순서는 **측정 전의 추측**이었고, 실측이 순서를 바꿨다.

## I-4. 누적 추가 vs Leave-one-out

**논문들은 대부분 제거(w/o X) 방식이고, 우리 A0~A6 은 누적 추가다.** 둘은 다른 것을 본다.

| 방식 | 답하는 질문 | 비용 |
|---|---|---|
| 누적 (A0→A6) | 순서상 **한계 기여도** | 7회 |
| Leave-one-out | 완성 구성에서의 **필수성** | 구성요소 수만큼 |

**설계**: 누적을 기본으로 하고, **[08](08-error-analysis.md) 병목 상위 2개만 leave-one-out** 을 추가한다.
전체 LOO 는 비용이 2배가 되므로 하지 않는다.

```
L1 = A6 − (병목 1위 요소)
L2 = A6 − (병목 2위 요소)
```

> **v4 갱신** — v2 실행에서 LOO 를 **3개**로 늘리고 기준선을 완성 구성 `A8` 로 옮겼다.
> 기준선이 사다리 마지막 칸과 같아야 "누적으로 더한 것" 과 "빼면 잃는 것" 이 같은
> 구성 위에서 비교된다.
>
> ```
> L1 = A8 − 정정체인 hop        L2 = A8 − major·holding 필드
> L3 = A8 − 발주처 2-hop        ← v2 신규. 플래그로 보면 L3 ≡ A7 이다
> ```
>
> `L3` 의 Δ 는 사다리 `Δ(A7→A8)` 과 **부호만 다른 같은 값**이어야 한다. 아니면
> 어딘가 틀렸다는 뜻이라, 이 항등식을 `tests/test_ablation.py` 가 고정한다.

논문들의 LOO 결과(부록 D)와 대조해 우리 Δ 가 타당한 크기인지 판정한다.

### 세 가지가 새로 드러났다

**① §I-1 의 가설이 수치가 됐다 — 그리고 바닥은 A0 이 아니라 A1 이었다.**

**커버리지가 랭킹보다 먼저다** — A1b 의 +36.1%p 가 같은 말을 반대편에서 한다.

**② A5 의 Δ 는 계산 도구의 function calling 이 아니라 '근거에 박아 둔 계산 결과' 다.**

**③ A6(Verifier)의 정답률 Δ 는 0.0%p 다.** 숨기지 않는다.
`verify_calculation`·`verify_completeness` 는 둘 다 LLM 0회이고 답을 갈아엎지 않으므로

발화 3건 중 오답 적중 1건(Q-023 `stale_value`), 거짓 경보 2건(Q-014·Q-048).

훨씬 자주 서면서 거짓 경보가 생겼다. 규칙 임계 재조정이 다음 트랙 몫이다.

돈이 아니라 다른 둘이다:

```

```

**세 게이트 중 둘이 막는다.** 그래서 범위를 줄였다.

### ④ 줄인 범위와, 그래서 못 재는 것

| 문서군 | dense 범위 | 근거 |
|---|---|---|
| `exchange` · `major` · `holding` | **전량 3,150건** | 53원 · 6.2MB · 55분. 줄일 이유가 없다 |
| `periodic` | **메타 프리필터 통과 후보만** (지연 임베딩 · 디스크 캐시) | 전량은 상주 307MB · 46시간 |

**이 축소가 측정을 훼손하지 않는 이유**는 융합 지점 때문이다. dense 는 §I-1 에 따라
**메타 프리필터 뒤**에 있다. 프리필터가 거른 조각은 전량 인덱스가 있어도 **후보가 아니다.**
따라서 "후보만 임베딩" 과 "전량 임베딩" 은 이 질의 집합에서 **같은 순위를 낸다.**

잃는 것은 측정 타당성이 아니라 **배포 일반성**이다. 새 기업·새 사업연도 질의는 최초 1회
후보 풀을 임베딩하는 지연·비용이 붙는다 (풀 최대 331건 = 약 6분). 평가기간에 이 구성을
쓰려면 그 지연을 감수하거나 대상 기업을 미리 예열해야 한다 — **A2 를 제출 구성으로
채택하지 않는 또 하나의 실무적 이유**다.

### ⑤ 구현 — Dense + RRF, 부록 B(G-Retriever · HippoRAG)

```
메타 프리필터(corp_name · rcept_dt · path)  ->  후보 집합
                                                 ├─ BM25 순위   (상위 20~40)
                                                 └─ dense 순위  (상위 20~40)
                                                      -> RRF(k=60) -> top_k
```

설계에서 **깨지 않은 것 셋**:

1. **문서군별 인덱스 + 라우터 선택** — dense 도 문서군마다 따로 붙는다 (사이드카
   `artifacts/embeddings/<group>_dense.npz`). 통합하면 exchange 골든이 27→26 이 된다(D-5).
2. **메타 프리필터가 맨 앞** — dense 는 후보 집합 안에서만 순위를 만든다.
3. **점수 스케일** — 융합 뒤에도 `score` 는 **BM25 원점수**를 그대로 돌려준다.
   RRF 점수(≈0.03)를 흘리면 `MIN_TOP_SCORE=10.0` 과 `_sufficiency` 의 `low_score` 가
   전 문항에서 발화해 **재는 것이 dense 가 아니라 hop 예산**이 된다.

융합 전 각 리스트를 `top_k` 보다 깊게(×4, 최소 20) 뽑는다. 둘 다 `top_k` 로 잘라 합치면
순서만 바뀌고 **후보 집합이 절대 안 바뀌어** dense 가 새 문서를 못 올린다.

정기공시를 전량 담았다면 여기에 **+307MB(float16)** 가 붙어 748MB 가 된다.

### ⑫ 결론 — 이 코퍼스에서 임베딩이 안 듣는 이유는 기법이 아니라 후보 집합이다

부록 D-4 기준으로 A2 의 Δ 0.0%p 는 "10% 미만 = 버그 의심" 칸에 걸린다.
**버그가 아니다.** 근거 셋:

1. **후보가 없다.** 검색 호출 75회 중 32회(42.7%)가 후보 1건, 76%가 5건 이하다.
   재순위·융합이 손댈 대상이 정의상 없다. 메타 프리필터가 §I-1 대로 1,469 → 1건까지
   좁혔기 때문이고, 이건 **DART 공시가 `corp_name` × `rcept_dt` 로 거의 완전히 식별된다**는
   코퍼스의 성질이다.
2. **남은 여지를 BM25 가 이미 먹었다.** 골든 60건 중 55건이 top-3, 41건이 1위다.
3. **미적중 2건이 임베딩의 문제가 아니다.** Q-023 은 체인 목록 길이(7 > `MAX_CHAIN_DOCS`=6)
   문제이고 골든 5건은 **이미 근거에 다 실려 있다**. Q-054 는 목차 단서 부재 →
   A3(리랭커)의 겨냥점이다.
4. **코퍼스 성질이 dense 에 불리하다** — [01-eda](01-eda.md): 숫자 토큰비 7.5~20%,
   표 문자비 0.71~0.93. 의미 유사·패러프레이즈가 걸릴 자리가 거의 없다.
   dense 가 실제로 31건을 새로 올렸는데 **골든이 0건**이었던 것이 이 성질의 직접 증거다.

**따라서 A2 는 제출 구성에서 뺀다.** 성능 Δ 0 · 상주 +9.5MB · 배포 시 신규 기업 질의마다
후보 풀 지연 임베딩(최대 331건 ≈ 6분) 이 붙는다. **얻는 것이 0 인데 비용이 0 이 아니다.**
G1 이 허용으로 확정돼도 결론은 같다 — 이 판정은 규정이 아니라 실측이 내렸다.

> 이 결과 자체가 기술제안서에 쓸 산출물이다. "임베딩을 안 썼다" 가 아니라
> **"임베딩을 붙여서 재 봤더니 이 코퍼스에서는 기여가 0 이었고, 그 이유는 이것이다"** 로 쓴다.

`A1` 의 `ROUTING` 실패 **39건**(A0 은 0건)은 라우터 버그가 아니다 — arm 정의상 검색이
exchange 로 강제되므로 `parse_trace` 가 문서군 불일치로 읽는다. 실체는
**major·holding·periodic 질의가 검색 단계에서 통째로 떨어지는 것**이고, 그것이 곧 A1b 의 Δ 다.

🔴 **"증설 문항에 그 문서군이 더 많아서" 가 아니다.** 신규 그리드 36문항의 문서군 구성은
기존 36과 **완전히 동일**하다(각각 exchange 16 · major 4 · holding 4 · periodic 12).
구성으로는 %p 차이가 나올 수 없다.

### ⓿b 뒤집힘의 절반은 문항 증설이 아니라 **v1→v2 코드 변화**다

같은 36문항(`measured` 코호트)에서 갈라 보면 **동일 코호트가 이미 뒤집혀 있다.**

|---|---|---|---|
| **v1** measured 36 | 10/36 | 11/36 | **+2.8%p** |
| **v2** measured 36 (동일 코호트) | 11/36 | 9/36 | **−5.6%p** |
| **v2** 증설 36 | 13/36 | 9/36 | **−11.1%p** |

"문항이 42→88 로 늘자 부호가 뒤집혔다" 는 **절반만 맞다.** 증설 효과(−11.1%p)와
**코호트 효과(−5.6%p)** 가 따로 있고, 뒤엣것은 v1 이후의 파이프라인 변화 몫이다.
🔴 **어느 커밋이 원인인지는 v2 산출물로 특정할 수 없다** — 이 트랙은 arm 플래그만 변수로
뒀고 v1 이후 여러 트랙이 파이프라인을 바꿨다. 특정하려면 커밋별 재측정이 필요하다.

→ **"커버리지가 랭킹보다 먼저다" 가 v1 보다 강하게 성립한다.** A1 은 A0 보다 싸고
(734원 vs 2,106원) **동시에 더 못 맞힌다**(25.0% vs 33.3%).

🔴 **제출 후보에서 A0·A1 을 배제한다** — *제거 지시가 아니다.* `_gather_meta` 는
`uses_bm25=False` 에서만 도달하므로 **A8 안에 떼어낼 "A0" 구성요소가 없다.** 뜻은 사다리의

### ① `counterparty_hop` 을 A4 에서 A8 로 옮겼다 — 자리를 틀리면 전부 헛일이다

v1 은 이 플래그를 `A4` 에서 켰다. 그 자리에서는 **자기 Δ 를 낼 수 없다.**

`tests/test_ablation.py` 가 이 항등식과 "A0 에서는 켜도 발화하지 않는다" 를 함께 고정한다.

### 🔴 재측정 규율 — **내용이 바뀌었으면 `--force`.** 안 붙이면 무효 연산이다

두 라운드 연속으로 밟았으므로 규칙으로 박는다.

```
run_case(case, force)       캐시 키 = question_id            ← 내용 해시가 없다
run_judge(case, resp, force) 캐시 키 = question_id            ← 같은 결함
embed.VectorStore.ensure    캐시 키 = doc_id                 ← 같은 결함 (재빌드 233건이 낡는다)
```

색인·프롬프트·arm 구성을 바꾼 뒤 `--force` 없이 돌리면 **저장 응답이 그대로 재생되고
성적이 안 움직인다.** 그리고 그것이 *"수정이 효과가 없었다"* 로 읽힌다 — 이 결함이
위험한 이유는 실패가 조용하기 때문이다.

| 라운드 | arm | `--force` 없이 | `--force` 로 |
|---|---|---|---|
| R2D | `A8` full 88 | 적중 **0** / 미적중 **0** · 62/72 (직전과 동일) | 62 → **66/72** |
| R2E | `ORACLE` full 88 | 적중 **0** / 미적중 **0** · 61/72 (직전과 동일) | 61 → **64/72** |

> 🔴 **`--force` 없이 돌려 `캐시 적중 0 / 미적중 0` 이 나오면 그것이 무효 연산 신호다** —
> 적중도 미적중도 0 은 파이프라인이 **한 번도 안 돌았다**는 뜻이다.
>
> **`--force` 는 제동 우회가 아니다.** 응답 파일 캐시만 뚫고 **요청 캐시(프롬프트 해시)는
> 살아 있어서** 프롬프트가 한 글자도 안 바뀐 문항은 **0원**이다. R2E 실측:
>
> ```
> ORACLE full 88   적중 162 / 미적중 9   88문항 중 4문항만 결제   160.0원
> L1     full 88   적중 160 / 미적중 8   88문항 중 5문항만 결제    69.9원
> L2     full 88   적중 164 / 미적중 4   88문항 중 4문항만 결제    27.7원
> L3     full 88   적중 167 / 미적중 0   결제 0문항                 0.0원
> ```
>
> 🔴 **키 자체를 고치는 것은 다음 라운드다** — 키에 `(색인 스냅샷, arm 구성, 프롬프트
> 해시)` 를 더하면 저장된 산출물 전부가 미적중이 되어 재구매가 붙고, 그러면 이번
> 재측정과의 비교가 깨진다.

**비용을 미리 세는 법** — `--offline` 은 미적중에서 **프로세스를 죽이므로** 문항별로
못 센다. R2E 는 요청 캐시를 **읽기 전용**으로 감싸고 미적중에서 **그 문항만 중단**하는
탐침을 써서 `L1`·`L2`·`L3` 의 결제 문항을 크레딧 0원에 전수로 셌다(5 / 4 / 0문항).
추정 175.9원 → 실측 97.6원. **다음 견적도 이 방법으로 낸다.**

| G-Retriever | **제거** | 4개 컴포넌트 각각 |
| HippoRAG | **대체** | OpenIE 대안(REBEL·Llama) · PPR 대안(노드만/이웃까지) |
| GraphRAG | **조건 비교** | 6개 조건 head-to-head 승률 |
| SWE-Lancer | **조건 비교** | test-time compute · pass@k |
| **우리** | **누적 + 부분 LOO** | A0→A6 + 병목 상위 2개 제거 |

**HippoRAG 의 '대체' 방식이 우리에게 유용하다.** 제거하면 파이프라인이 안 돌아가는 구성요소
(예: 검색 자체)는 제거 대신 **더 단순한 것으로 대체**해 측정한다.

### D-4. 판정 기준

| 우리 Δ | 해석 |
|---|---|
| 논문 보고값의 **50% 이상** | 정상. 도메인 차이로 설명 가능 |
| 논문 보고값의 **10~50%** | 구현 확인 필요. 해당 arm 이 제대로 켜졌는가 |
| **10% 미만 또는 음수** | **버그 의심**. [08](08-error-analysis.md) 로 되돌아가 병목 재확인 |

> 예: A3(리랭커)에서 Relink 가 −19.4% 를 보고했는데 우리가 +1%p 만 얻었다면,
> 이미 메타 프리필터로 후보가 1~26건까지 좁혀져 **리랭커가 개선할 여지 자체가 없는 것**일 수 있다.
> 이 경우는 버그가 아니라 **우리 파이프라인의 구조적 특성**이며, 기술제안서에 그렇게 쓴다.
