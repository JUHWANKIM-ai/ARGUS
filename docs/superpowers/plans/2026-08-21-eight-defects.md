## 2. 🔴 먼저 결정해야 하는 것 — P1 은 우리 점수를 **내린다**

`P1` 은 답변을 고치는 처방이 아니라 **자를 고치는 처방**이다. `Q-054`·`Q-114` 는 지금
정답으로 세어지고 있고, 판정기가 답변에 없는 사실을 covered 로 인정한 덕이다. 요점에
박힌 숫자·접수번호를 기계로 확인하게 만들면 **둘이 오답으로 내려갈 수 있다.**

```
지금        110/112   (판정기가 Q-054·Q-114 를 통과시킨 상태)
P1 적용 후   108/112 이 될 수 있다
```

이것을 어떻게 볼 것인가.

- **주최측이 채점하는 것은 우리 판정기가 아니다.** 우리 판정기는 계측기이고, 계측기를
  엄격하게 만드는 것은 제출물을 좋게 만들지 않는다 — **우리가 아는 것을 정확하게** 만든다.
- 그래도 필요하다. 계측기가 느슨하면 `P6`·`P7` 처방이 먹었는지 **판정할 수 없다**.
  `Q-054` 는 접수번호를 안 적었는데 요점 4를 통과했다. 그 상태로 `P6` 을 재면 고쳤는지
  안 고쳤는지 구분이 안 된다.
- v8 에서 판정기를 엄격하게 바꿀 때와 같은 처분을 쓴다 — **두 잣대의 수를 다 적는다.**

**제안: P1 을 먼저 넣고, 이후 모든 측정을 새 잣대로 한다. README 는 두 수를 병기한다.**

각 과제는 **진단(실측) → 처방 → 스위치 → 검증 → 위험** 으로 적는다. 처방은 후보이고,

### P1 · 판정기가 답변에 없는 사실을 covered 로 인정한다

**진단(실측).** `Q-054` 의 골든 요점 4는 *"원공시(20240514000756)와 정정공시
(20240514001580)는 접수일이 같아 접수번호로만 선후를 가릴 수 있다"* 인데 답변은 두
접수번호를 한 번도 적지 않았다. 판정기는 `covered[3]=True` 를 냈다. `Q-114` 는 골든이
*"삼성E&A 47건 / 삼성중공업 19건"*, *"19건 중 17건에 FAB동"* 을 요구하는데 답변은 그 수를
말하지 않았다. 판정기는 6/6 을 냈다.

**처방.** 판정기 프롬프트를 다시 만지지 않는다 — 프롬프트로 엄격함을 사는 것은 v8 에서
이미 재현성 문제를 겪었다. 대신 **판정기 뒤에 결정적 게이트**를 둔다. 골든 요점 문자열이
① 14자리 접수번호 또는 ② 콤마 묶음 금액 또는 ③ `N건` 꼴 개수를 명시하면, 그 토큰이
답변에 있는지 기계로 보고 없으면 `covered[i]` 를 False 로 내린다. LLM 0회.

기존 축을 재사용한다 — `covers_key_amounts`(R3b)가 이미 금액 축을 이렇게 본다. 같은
검사를 두 곳에 만들지 않고 그 함수를 요점 단위로 확장한다.

**스위치.** `keypoint_literal_gate` (채점 쪽. `amount_coverage_gate` 와 같은 계열)

**검증.**
- `Q-054` 요점 4 · `Q-114` 요점 1·2 가 `covered=False` 로 내려간다
- 게이트가 **다른 문항의 판정을 바꾸지 않는다** — 112문항 전수에서 `covered` 배열 diff
- 요점에 숫자가 없는 문항은 게이트가 발화하지 않음을 확인 (발화 대상 수를 센다)

**위험.** 점수가 내려간다(§2). 그리고 과잉 발화 위험 — 답변이 `47건` 대신 `47개` 로
적으면 잡힌다. 표기 변이를 어디까지 접을지가 이 과제의 실제 난점이다.

### P2 · 정정 체인 역행 인용 (`Q-116`)

**진단(실측).** 같은 계약(함안복합 파워블록)의 두 판.

```
20240722800037  원본    581,790,000,000원   is_latest=False   ← 답변이 인용
20250923800193  정정본  583,874,002,800원   is_latest=True    ← 골든
                        차액 2,084,002,800원
```

답변은 *"금액은 581,790,000,000원으로, 약 5,818억 원"* 이라 적었다. **폐기된 값**이다.
정답으로 채점된 것은 이 문항의 골든 답이 회사명(`answer_form=list`)이라 금액이 채점
대상이 아니기 때문이다.

**처방.** 두 겹.
1. **근거 쪽** — 금액을 묻는 분기에서 후보 레코드가 `is_latest=False` 이고 `related` 에
   `is_latest=True` 형제가 있으면 그 형제로 바꿔 싣는다. 지금도 `is_latest` 필드가 있고
   `related` 가 양방향이라 조회는 결정적이다.
2. **답변 쪽** — 답변에 실린 금액이 `is_latest=False` 레코드에서만 나오고 최신본의 값이
   다르면 최신본 값으로 치환하고 접수번호를 최신본으로 바꾼다. `aggregate.substitute`
   계열의 처분을 재사용한다.

**착수 전 확인.** `numeric_self_consistency` 가 왜 이걸 안 잡았는지 먼저 본다. 그 검사는
*"근거 밖 수"* 를 보는데 581,790,000,000 은 **근거 안에 있는 수**다 — 근거 안의 낡은 수라는
축이 없다. 새 검사를 만들기 전에 이 진단을 확정한다.

**스위치.** `latest_pin`

**검증.**
- `Q-116` 이 583,874,002,800 을 말하고 `20250923800193` 을 인용한다
- 정정 체인이 있는 문항 전수(`is_latest=False` 골든을 가진 문항)에서 퇴행 0
- 🔴 **정정 이력 질의는 낡은 값을 말해야 한다** — `Q-054` 처럼 *"무엇이 얼마로 바뀌었나"* 를
  묻는 분기에서 원본 값을 지우면 오답이 된다. 이 처방이 그 분기를 건드리지 않음을
  시험으로 고정한다

**위험.** 중간~높음. 정정 체인은 시스템의 대표 기능이라 건드리는 면적이 넓다.
위 세 번째 검증 항목이 이 과제의 핵심 위험이다.

### P3 · 근거에 실린 골든을 두고 다른 문서를 인용한다 (`Q-110`)

**진단(실측).**

```
골든 6건        20250829800405 20230329801108 20240329800342
                20230102900376 20230417800192 20231211800339
근거에 실린 것 5건  위 중 20240329800342 만 빠짐

```

회사 여섯을 열거하고 '근거' 표기를 **열 번** 붙였다. 표기를 안 한 것이 아니라 **손에 쥔
근거 다섯을 두고 다른 문서를 가리켰다.** 오픈이슈 2(회수)와 다른 문제다 — 회수를 다
고쳐도 이 결함은 남는다.

**처방.** 열거형 답변에서 접수번호를 모델이 고르게 하지 않는다. `roster_line`(A39)이 이미
로스터를 근거 **머리**에 싣고 있으니, 그 줄이 항목마다 **공급 레코드의 접수번호를 함께
나르게** 하고, 표기 부착 처분이 모델이 적은 표기를 로스터 기준으로 덮어쓴다.

README §4.4 가 *"접수번호 14자리처럼 전사 오류가 발생하기 쉬운 값은 모델에 옮겨 적게
하지 않고 시스템이 부착한다"* 고 적어 둔 원칙의 미구현 부분이다.

**스위치.** `roster_citation`

**검증.**

- 열거형이 아닌 문항의 표기가 **한 글자도** 바뀌지 않는다 (112문항 답변 diff)
- 로스터 없는 분기에서 발화하지 않음

**위험.** 중간. 표기를 시스템이 덮어쓰면 문면이 바뀌므로 diff 면적이 크다.

### P4 · 질문이 지목한 보고서를 다른 보고서로 바꿔 읽는다 (`Q-105`)

**진단(실측).** 질문이 *"2025년 3분기 분기보고서"* 를 지목하고 골든도
`20251114002201` 인데 답변은 `20250515002428`(2025년 **1분기**, 2025-05-15)을 인용했다.
지목된 보고서가 코퍼스에 **있는데도** 다른 분기를 대신 썼다.

라우터에 「지목한 보고서 부재 → 되묻기」 갈래가 있지만(README §4.5) 여기는 **부재가
아니라 조용한 치환**이라 되묻지도, 고지하지도 않았다.

**처방.** 질문이 연도와 분기·반기·사업연도를 명시한 정기공시 질의에서, 선택된 섹션의
출처 문서 `base_year`·`base_month` 가 질문이 지목한 기간과 맞는지 결정적으로 확인한다.
어긋나고 지목된 기간의 문서가 코퍼스에 있으면 그것으로 바꾼다. 없으면 기존 「보고서 부재」
갈래로 넘긴다.

**스위치.** `period_pin`

**검증.**
- `Q-105` 가 `20251114002201` 을 인용한다
- 정기공시 문항 전수에서 퇴행 0 (섹션 선택을 건드리므로 면적이 넓다)
- 기간을 명시하지 않은 질의에서 발화하지 않음

**위험.** 중간~높음. 정기공시 섹션 선택은 많은 문항이 지나가는 경로다.

### P5 · 일부 문서만 보고 전체가 같다고 단정한다 (`Q-105`)

**진단(실측).** 답변이 *"모든 문서에서 … 기재하지 않습니다"*, *"따라서 세 문서 간

**처방.** 비교형 질의에서 문서별 상태를 결정적 줄로 근거 머리에 싣는다.


그리고 답변이 *"차이 없다"* 계열을 말하면서 그 줄이 서로 다른 상태를 보이면 결정적으로
바로잡는다. `state_total` 이 *"아는 값이 답변에 없으면 결론을 우리가 적는다"* 를 하는 것과
같은 처분이다.

**스위치.** `contrast_line`

**검증.**

- 비교형이 아닌 문항에서 줄이 실리지 않음
- 🔴 *"차이 없다"* 판정 자체가 맞는 문항에서 잘못 뒤집지 않음 — 실제로 세 문서가 같은
  사례를 찾아 시험으로 고정한다

**위험.** 중간. 세 번째 검증 항목이 없으면 이 처방은 반대 방향 오답을 만든다.

### P6 · 접수번호 자리에 접수일을 적는다 (`Q-054`)

**진단(실측).** 표기가 `(근거: 분기보고서 2024, 정정신고, 20240514)` 다. `20240514` 는
**접수일 8자리**이고 접수번호는 14자리다. 접두 8자리를 공유해 문면이 그럴듯하다.
하필 골든 요점 4가 그 접수번호로 선후를 가려야 한다고 말한다.

**착수 전 확인.** 「근거 표기 부착」 처분이 왜 발화하지 않았는지 먼저 본다. `CITATION_RE`

## 4. 순서와 파도

프리즈까지 **4일**(08-25). 7 과제를 전부 퇴행 0 으로 넣는 것은 **비현실적이다.**
그래서 파도를 나누고 **컷라인을 미리 정한다** — 시간이 모자라면 아래에서 자른다.

| 파도 | 과제 | 왜 이 순서인가 |
|---|---|---|
| **W1** | P1 | 자를 먼저 고친다. 느슨한 자로는 P6·P7 을 검증할 수 없다 |
| **W2** | P2 · P3 | 무게가 가장 크다. 둘 다 「손에 쥔 것을 안 쓴다」 계열이라 진단이 겹친다 |
| **W3** | P4 · P6 | 문서 선택과 표기. 면적이 좁고 검증이 명확하다 |
| **W4** | P5 · P7 | 결정적 줄 신설 둘. 반대 방향 오답 위험이 있어 마지막에 둔다 |

**컷라인.** W1·W2 가 들어가면 이 캠페인은 성공이다. W3 는 가능성이 높다. **W4 는
스트레치이고, 못 넣으면 미측정으로 남긴다** — 프리즈 직전에 결정적 줄을 새로 세우는 것이
지금 상태(퇴행 0)를 잃는 가장 빠른 길이다.
