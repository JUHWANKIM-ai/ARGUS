### 1-1. 판정기를 엄격하게 하면 모든 성적이 내려간다

```

  "법인등록번호"          0건
  [0-9]{6}-[1-4][0-9]{6}  0건
```

개인정보 마스킹을 좁히는 변경은 미탐이 오탐보다 나쁜 영역이라 하지 않는다 —
이슈 3 자신이 그렇게 적었고, 이번 실측이 그 판단을 강화한다.

## 2. A. 판정기 요점별 판정 — 오픈 이슈 8

### 무엇이 문제인가

`critic.OpenVerdict.covers_key_points` 는 **요점 전체에 대한 불리언 하나**다.
요점 여섯 중 셋만 담은 답이 통과할 수 있고, 실제로 그렇게 통과했다.

```python
# src/argus/agent/critic.py:56
@dataclass
class OpenVerdict:
    covers_key_points: bool     # ← 요점 5개든 7개든 값 하나
    grounded: bool
    no_fabrication: bool
```

### 어떻게 바꾸는가

판정기가 **요점마다** 0/1 을 내고, 그 배열을 그대로 보관한다.

```python
@dataclass
class OpenVerdict:
    covered: tuple[bool, ...]   # 요점별 판정, 골든 요점과 같은 길이
    grounded: bool
    no_fabrication: bool
    reason: str

    @property
    def covers_key_points(self) -> bool:
        """과반 초과. 요점 5개면 3개, 6개면 4개."""
        if not self.covered:
            return False
        return sum(self.covered) * 2 > len(self.covered)

    @property
    def correct(self) -> bool:
        return self.covers_key_points and self.grounded and self.no_fabrication
```

`covers_key_points` 를 **속성으로 남긴다**. `critic.py` 밖에서 이 이름을 읽는
자리가 10 군데, 파일로는 넷이다 (`scripts/error_analysis.py`,
`scripts/ablation.py`, `scripts/judge_closed.py`,
`scripts/build_goldenset_review.py`). 전부 고치면 변경 면적이 필요 이상으로
넓어진다. 읽는 쪽 계약은 그대로 두고 **의미만 엄격해진다**.

`covered` 배열은 산출물에도 실어야 한다 — 어느 요점을 놓쳤는지가 이 변경의
절반이다. `error_analysis.py:1471` 의 판정 저장과 `scripts/ablation.py:953`
의 `JUDGE_FIELDS` 에 `covered` 를 더한다.

### 문턱

**과반 초과** — 사용자 결정. 요점 수 분포와 두 규칙의 차이는 이렇다.

| 요점 수 | 문항 수 | 과반 초과 | 70% |
|---|---|---|---|
| 2 | 3 | 2 | 2 |
| 3 | 6 | 2 | 3 |
| 4 | 10 | 3 | 3 |
| 5 | 10 | **3** | **4** |
| 6 | 12 | **4** | **5** |
| 7 | 2 | **4** | **5** |

겨냥 문항: Q-094 5개 · Q-106 6개 · Q-110 6개 · Q-112 5개 · Q-117 5개.

### 프롬프트

`prompts.SYSTEM_OPEN_JUDGE` 와 `build_open_judge_messages` 를 고친다.
`prompts.py` 를 건드리지만 **생성 프롬프트(`_BASE_RULES`·`_DIRECT`·`_COT`)는
손대지 않는다.** 그쪽은 측정 대상이라 동결이고, 판정기는 채점기라 사용자가
바꾸라고 지시한 대상이다. 이 구분을 파일 주석에 남긴다.

요점에 번호를 매겨 제시하고, 같은 길이의 배열을 요구한다.

```
[모범답안 요소]
1. …
2. …

{"covered":[0,1,...],"grounded":0,"no_fabrication":0,"reason":"한 문장"}
```

### 파싱 실패와 길이 불일치

- 파싱 실패 → 세 축 모두 거짓 (현행과 동일)
- 배열 길이 ≠ 요점 수 → **거짓으로 채워 맞추지 않고** 실패 처리
  길이가 다르다는 것은 판정기가 요점을 세지 못했다는 뜻이고, 임의로 채우면
  채점 실패가 오답으로 둔갑한다
- 골든 요점이 없는 문항 (`answer_key_points = null`) → `covered = ()`,
  `covers_key_points = False`. 개방형인데 요점이 없으면 채점할 수 없다.
  현재 개방형 43문항 전부 요점을 갖고 있으므로 이 경로는 발화하지 않는다

### 시험

- 요점 6개 중 3개 → 오답, 4개 → 정답 (경계 양쪽)
- 요점 5개 중 2개 → 오답, 3개 → 정답
- 요점 2개 중 1개 → 오답 (과반 **초과**이므로 동수는 탈락)
- 길이 불일치 → 채점 실패
- 요점 0개 → 오답
- `judge_open` 가 배열을 그대로 `covered` 에 싣는지

## 3. B. 비율 전수 검사 — 오픈 이슈 9

### 무엇이 문제인가

`verify_completeness` 의 `amount_gap` 은 **금액**만 본다 (`money_values`).
Q-106 처럼 답이 비율로만 이뤄진 문항은 이 검사가 닿지 않아, 68.11% → 50.06%
라는 18.05%p 폭락을 통째로 빠뜨려도 아무 표시가 안 난다.

### 어떻게 바꾸는가

`amount_gap` 검사의 값 추출을 금액 ∪ **비율**로 넓힌다. `critic._PCT_RE` 가
이미 있으므로 재사용한다.

- 근거에 비율이 `RATIO_GAP_MIN_EVIDENCE = 3` 개 이상 있고
- 답변의 비율 집합이 근거 비율 집합을 **절반 미만** 덮으면
- 거절 답변이 아닐 때만 (기존 `_ADMIT` 반전 프록시 유지)

발화 조건을 금액 쪽과 같은 모양으로 맞춘다. 새 축을 만들지 않는 이유는
`amount_gap` 이 이미 "집합을 묻는 질문에 답이 침묵했다" 를 뜻하기 때문이다.

### 시험

- Q-106 문면(근거 비율 7종, 답변 비율 2종) → 발화
- 답변이 비율 5종을 담으면 → 침묵
- 거절 답변 → 침묵
- 근거 비율 2종 → 침묵 (최소 근거 미달)

## 4. C. Q-106 — 보유비율 시계열 줄

### 데이터가 이미 충분하다

`artifacts/holding_records.jsonl` 이 **타입이 잡힌 필드**를 갖고 있다.
정규식으로 문자열을 파싱할 필요가 없다.

```
20231013000473  ratio_prev=None   ratio_current=68.19  shares_current=44,200,027
20250305000647  ratio_prev=68.19  ratio_current=68.15  shares_current=44,177,137
20250707000299  ratio_prev=68.15  ratio_current=68.11  shares_current=44,149,065
20260227007254  ratio_prev=68.11  ratio_current=50.06  shares_current=32,449,065
```

골든 요점 여섯 중 **다섯이 이 네 줄에서 직접 나온다**. 여섯째(누적 18.13%p)는
68.19 − 50.06 = 18.13 으로 계산된다.

### 어떻게 바꾸는가

`aggregate.revision_series` 와 같은 갈래의 함수를 새로 세운다.

```python
def holding_series(records, question: str) -> str:
    """보고자별 보유비율 추이를 접수일 순으로 한 줄에 편다.

    LLM 호출도 검색도 없다. `revision_series` 가 정정 체인 금액에 하는 것을
    대량보유 보고의 비율에 한다. 다른 점은 두 가지다 — 묶는 축이 정정 체인이
    아니라 보고자이고, 값이 `amount` 가 아니라 `ratio_current` 다.
    """
```

- 발화 조건: 대량보유 레코드가 2건 이상이고 같은 보고자로 묶인다
- 보고자 필터: `reporter` 필드로 묶는다. 같은 기간 국민연금공단·코봇홀딩스
  보고서가 섞여 있어 (문항 `notes` 가 명시) 필터 없이는 다른 체인을 끌어온다
- 출력 형태

```
- [결정적 집계] (주)두산의 두산로보틱스 보유비율 추이 (4건):
  2023-10-13 68.19% (44,200,027주) → 2025-03-05 68.15% → 2025-07-07 68.11%
  → 2026-02-27 50.06% (32,449,065주) · 누적 -18.13%p
  (이 값은 시스템이 위 근거의 비율 필드에서 직접 읽은 것이다. …)
```

- 배치: `pipeline._prepend` 로 근거 머리에. `unit_line` 과 같은 독립 형제 블록
- 사유(RSU 지급 / 주식매매계약 체결 완료)는 **줄에 싣지 않는다**. 근거 블록의
  `보고사유` 에 이미 있고, 한 줄에 다 넣으면 길이가 근거 블록을 넘는다

### `_SERIES_ASK` 를 재사용하지 않는다

`revision_series` 의 발화어에 "어떻게 변했" 은 있으나 Q-106 의 "어떻게 변해
왔는지" 는 걸리지 않는다. 발화어를 넓히면 `revision_series` 의 발화 범위가
같이 움직여 이미 잰 아암의 동작이 바뀐다. **`holding_series` 는 자기 발화어를
따로 갖는다** — 대량보유 레코드가 2건 이상 묶이는 것 자체가 강한 신호이므로,
"추이·변해·변화·변동·바뀌" 정도로 느슨하게 두고 레코드 조건으로 조인다.

### 시험

- Q-106 네 건 → 여섯 요점이 모두 줄에 나타남
- 보고자가 섞이면 → 상위 보고자 하나만
- 1건 → 침묵
- `ratio_current` 가 없는 레코드 → 침묵
- 누적 변동폭 부호와 자릿수

## 5. D. Q-107 — 사업 단위 거르기 + 합

### 코드가 이미 결함을 적어 뒀다

```python
# src/argus/agent/aggregate.py:_sum_rows
# A counterparty filter on its own does not pin the set, because a hub
# holds several contracts and summing them all overshoots. What such a
# question narrows is the project, and that axis is not available here.
return rows if _DATE_NOTE in note else None
```

**"질문이 좁히는 것은 사업이고, 그 축이 여기 없다."** 이번에 그 축을 만든다.

### 색인 재빌드가 필수다 — 실측

```
20251216801147 두산에너빌리티  raw_rows: ["4. 판매ㆍ공급지역", "체코 남부 Dukovany Site"]
20251216801163 두산에너빌리티  raw_rows: ["4. 판매ㆍ공급지역", "체코 남부 Dukovany Site"]
20251212801320 한전기술        raw_rows: ["4. 판매ㆍ공급지역", "체코"]
20251224800396 한전기술        raw_rows: ["4. 판매ㆍ공급지역", "체코"]

네 레코드 모두  supply_region 키 없음 · markdown 에 공급지역 줄 없음
```

`normalize.py:496` 과 `markdown.py:72` 에 `supply_region` 배선은 이미 있다.
**빌드된 색인이 그 변경보다 앞선다.** 그래서 재빌드가 코드 작업이 아니라
데이터 재생성 작업이다. `scripts/v7_rebuild_index.py --check/--apply/--restore`
를 그대로 쓴다.

### 사업 토큰이 어디서 걸리는가

| 접수번호 | 제목 | 공급지역 | 계약상대 |
|---|---|---|---|
| 20251216801147 | Dukovany 5&6 NSSS Contract | 체코 남부 Dukovany Site | 한국수력원자력(주) |
| 20251216801163 | Dukovany 5&6 Turbine Generator | 체코 남부 Dukovany Site | 한국수력원자력(주) |
| 20251212801320 | 체코 두코바니 5&6호기 종합설계용역 | 체코 | 한국수력원자력(주) |
| 20251224800396 | 체코 두코바니 5&6호기 원자로계통설계용역 | 체코 | **두산에너빌리티(주)** |

`두코바니` 는 한전기술 두 건의 제목에만 있고, `Dukovany` 는 두산 두 건의
제목과 공급지역에만 있다. **공통으로 걸리는 토큰은 `체코` 하나**이고, 그것은
재빌드 뒤에야 존재한다.

### 어떻게 바꾸는가

`aggregate.select()` 에 **세 번째 필터 축**을 더한다.

```python
def _project_tokens(question: str) -> list[str]:
    """질문이 지목한 사업의 지명·고유명 토큰."""
```

- 후보 텍스트는 레코드의 `title` + `supply_region`
- **근거 안에서만** 거른다. 코퍼스 전체를 훑지 않으므로 오탐이 검색 결과로
  이미 제한된다 — `체코` 가 다른 사업에도 있어도 그 사업이 근거에 없으면
  걸릴 일이 없다
- 걸러진 뒤 기존 계약상대 필터가 이어 돈다. 20251224800396 은 이 단계에서
  빠진다 (계약상대 두산에너빌리티)
- `notes` 에 `"체코 사업분"` 을 적고, `_sum_rows` 가 **`_DATE_NOTE` 뿐 아니라
  사업 표시도 집합을 고정한 것으로 인정**한다

```
4,928,968,079,043 + 711,106,288,572 + 1,250,850,298,678 = 6,890,924,666,293
```

골든과 일치한다.

### 유일성이 깨지지 않게

`select` 의 docstring 이 "축을 더하면 유일성이 깨지고, 유일성 없이는 이 모듈이
침묵해야 한다" 고 적었다. 그래서 **사업 필터가 걸러 낸 결과가 비면 필터를
적용하지 않은 것으로 되돌린다** (기존 계약상대 필터와 같은 방어). 그리고
사업 토큰이 하나도 안 잡히면 축 자체가 발화하지 않는다.

### 플래그

`ablation.Arm` 에 `project_scope: bool = False`. `retrieval="meta"` 에서도
`select` 는 도달하므로 `META_UNREACHABLE_FLAGS` 에 넣지 않는다.

### 시험

- Q-107 네 건 → 3건 선택, 합 `6,890,924,666,293`
- 20251224800396 이 빠지는지 (계약상대 축)

4까지 서면 5는 모델이 추론할 여지가 생긴다.

### 어떻게 바꾸는가

갈래별로 **대표 계약의 계약명과 금액**을 싣는다. `aggregate._subject` 가 이미
제목 꼬리를 뽑고 `MAX_SUBJECT_CHARS = 44` 로 자른다 — 그대로 쓴다.

```
- [결정적 집계] 계약상대 11곳이 두 갈래로 나뉜다:
  발주처 10곳 — 한국수력원자력(체코 두코바니 5&6호기 종합설계용역

  373,449,426,066원)

```

- 갈래별 대표 계약 수: **재수주 갈래는 최대 2건, 발주처 갈래는 각 1건**.

- 길이 상한: 줄 전체가 근거 블록 하나를 넘지 않게 `MAX_PARTNER_PROFILE` 과
  같은 갈래의 상수로 조인다

### 판별어 누출 재발 방지

`counterparty_branch` 의 docstring 이 기록한 사고 — 판별 술어(`70개사`)를 줄에
적었더니 모델이 답변에 옮겨 적었다. **계약명과 금액은 근거의 원문 값이라 옮겨

## 7. F. 오픈 이슈 1 — 코퍼스 밖 출처 후처리 삭제

### 왜 후처리가 가능한가

이슈 1 은 "새는 문장이 거절 문단과 이어져 있어 문장 단위로 지우면 답이
잘린다" 고 적었다. 관측된 네 문면을 다시 보면 **가르는 규칙이 선다**.

```
AUD-05   삼성전자 매출액 정보는 네이버 검색 또는 금융감독원 전자공시시스템(DART)
         내 다른 보고서 … 를 통해 확인하실 것을 추천드립니다.
AUD2-06  … 현대건설의 공식 웹사이트나 금융감독원 전자공시시스템(DART)을
         참고하거나, 관련 기관에 문의해 보시는 것을 추천드립니다.
S-010    증권사 리포트와 같은 전문적인 자료들을 참고하시는 것도
S-011    DART 시스템 또는 회사의 공식 발표 채널을 주기적으로 확인하는 것을 권장
```

넷 다 **외부 출처 이름**과 **권유 동사**가 **같은 문장 안에** 있다. 앞 문단의
거절 문장에는 둘 다 없다.

### 어떻게 바꾸는가

```python
def strip_external_referral(answer: str) -> tuple[str, list[str]]:
    """코퍼스 밖 출처를 안내하는 문장만 지운다. LLM 호출 없다."""
```

- 문장 분할 후, **출처 이름 ∧ 권유 동사** 인 문장만 제거
- 출처 이름: `DART`·`전자공시시스템`·`네이버`·`증권사`·`공식 웹사이트`·
  `공식 발표 채널`·`관련 기관` 등
- 권유 동사: `추천`·`권장`·`권해`·`참고하`·`확인해 보시`·`문의해 보시`·`바랍니다`
- 접수번호를 담은 문장은 **무조건 보존**. 우리 근거 표기가 `DART` 를 언급할 수
  있고, 그것을 지우면 근거가 사라진다
- 제거 뒤 답변이 비면 **원문을 되돌린다**

### 남는 잔여 — 명시한다

`AUD2-06` 의 앞 문장 "박영희씨와 관련된 추가적인 정보가 필요하시다면 다른
방법을 통해 확인해 보시기 바랍니다." 는 권유 동사는 있으나 **출처 이름이
없어** 살아남는다. 이는 의도한 동작이다 — 그 문장은 코퍼스 밖 경로를 사실처럼
안내하지 않으므로 §5 위반이 아니다. 잘린 문장을 억지로 이어 붙이지 않는다.

### 플래그

`external_referral_strip: bool = False`.

### 시험

- 위 네 문면 → 해당 문장만 제거, 거절 문단 보존
- 접수번호 담은 문장 → 보존
- 정상 답변 → 무변화
- 전부 제거되는 문면 → 원문 되돌림

## 8. G. 오픈 이슈 3 — 발생 불가로 닫는다

§1-2 의 실측에 따라 **코드를 고치지 않고 닫는다.** 이슈 문서에 다음을 적는다.

- 코퍼스 전 파일에서 `법인등록번호` 0건, 13자리 패턴 0건
- 그러므로 근거를 옮겨 적다 정당한 숫자가 훼손되는 경로가 없다
- 112문항 전수 마스킹 표식 0건이라는 기존 실측이 이것으로 설명된다
- 처방(코퍼스 조회)은 조회 대상이 없어 성립하지 않는다
- 마스킹 규칙은 **그대로 둔다**. 좁히면 가공 주민등록번호가 통과할 경로가 는다

## 9. 아암 구성

### 먼저 `A46`·`A47` 이름을 정리한다

두 이름은 **이미 쓰였다.** `artifacts/ablation/v7/A4{6,7}_*_r1` 이 있고
`docs/open-issues.md:280` 이 그 수를 싣는다. `scratch/combo_run.py` 를 읽어
확인했다.

```python
FLAGS = ("amount_coverage_gate", "counterparty_branch")
arm = replace(ablation.current(), name=name, **{f: True for f in FLAGS})
```

**둘은 같은 구성이다.** 이름만 다르게 두 번 돌린 것이고, `ablation.py` 에
등록된 적이 없다. 이슈 문서가 "`A46` 과 `A47` 이 둘 다 109/112 인데 오답
문항이 다르다" 고 적은 것은 아암 차이가 아니라 **같은 구성의 두 표본**이다.

그러므로 `A47` 을 새 조합에 재사용하지 않는다. 기록의 뜻이 바뀐다.

```
A43  = A42 + unit_line                                   현 운용 기본
A44  = A43 + amount_coverage_gate                        등록됨, 단독 미측정
A45  = A43 + counterparty_branch                         등록됨, 단독 미측정 (§6 에서 확장)

A46  = A43 + amount_coverage_gate + counterparty_branch  ← 등록한다
       (기존 `A46`·`A47` 산출물 2회분이 이 구성의 두 표본이다)
V8-1 = A46 + project_scope                               Q-107
V8-2 = A46 + holding_series                              Q-106
V8-3 = A46 + external_referral_strip                     이슈 1
A48  = A46 + project_scope + holding_series
             + external_referral_strip                   채택 후보
```

`A47` 은 **등록하지 않고 비워 둔다.** 이슈 문서에 그 이름이 `A46` 의 2회차를
가리킨다는 각주를 단다.

`ratio_gap`(§3-B)은 아암 플래그가 아니다. `amount_gap` 검사의 값 범위를 넓힌
것이므로 `amount_coverage_gate` 플래그를 그대로 탄다.

판정기 변경도 아암이 아니다. **채점기**이므로 모든 아암에 동시에 적용된다.

## 10. 측정 계획

### 10-1. 로컬 — 각 플래그가 주장한 일을 하는가

`V8-1`·`V8-2`·`V8-3` 을 겨냥 코호트에서 **1회씩**. 목적은 성적이 아니라
**결정적 줄이 실제로 서는지** 확인하는 것이다. 근거 덤프를 직접 읽는다.

### 10-2. 기준선 재채점 — 같은 분모를 만든다

`A43` 의 기존 서버 3회 응답이 `artifacts/ablation/v6/server_*` 에 저장돼 있다.
**응답을 다시 생성하지 않고 판정만 다시 돌린다.** 개방형 43문항 × 3회 =
129회 LLM 호출. 이것이 `v8` 을 비교할 유일하게 정직한 기준선이다.

### 10-3. 로컬 — 후보 아암 3회

`A48` 을 전 코호트 3회. 회차 간 흔들림을 읽는다. `scripts/v7_run.py` 의
전송 오류 재시도와 `index_fingerprint()` 를 그대로 쓴다.

### 10-4. 서버 — 골든셋 3회 (사용자 요구)

- 재빌드된 색인을 서버에 올린다 (`exchange_records.jsonl` 4.7MB +
  `exchange_bm25.json` 1.0MB)
- `A48` 을 운용 기본으로 배포
- `scratch/server_sweep.py <host> --round N` 3회
- 429 방어는 이미 들어가 있다 (`clova._RETRY_ATTEMPTS`, 336/336 무사고)
- 저장: `eval_server/*.json` + `artifacts/ablation/v6/server_*_r{1,2,3}`
- 채점: 새 판정기로. `A43` 재채점 결과와 나란히 놓는다

### 10-5. 통계

문항별 오답 횟수 히스토그램, 회차 간 뒤집힘, 요점별 미달 분포(새로 얻는 것),
`A43` 대비 증감.

### 채택 규칙

`v7` 규칙을 그대로 쓴다.

1. 3회 모두에서 기준선 이상
2. 영구 회귀(3회 모두 새로 틀린 문항) 없음
3. 뒤집힘이 기준선보다 늘지 않음

### 요구와 채택 규칙이 충돌할 때

사용자 요구는 **Q-106·Q-107·Q-117 이 정답**인 것이다. 채택 규칙은 **회귀가
없을 것**을 요구한다. 둘이 갈릴 수 있다 — 세 문항을 고치면서 다른 문항이
영구 회귀하는 결과다.

그 경우 **혼자 정하지 않는다.** 양쪽 수를 나란히 보고하고 사용자가 고른다.

- 세 문항 정답 + 회귀 N건 (`A48`)
- 세 문항 중 일부 오답 + 회귀 0건 (`A46` 또는 부분 조합)

되돌림 경로(`A43`)는 항상 살아 있게 둔다.

## 11. 색인 재빌드 절차

```
python scripts/v7_rebuild_index.py --check      지문 비교, 무엇이 바뀌는지
python scripts/v7_rebuild_index.py --apply      백업 뜨고 재빌드
python scripts/v7_rebuild_index.py --restore    되돌림, 백업 삭제
```

`--apply` 는 백업이 이미 있으면 거부한다 (두 번 돌려 백업이 파괴되는 사고를
막는다). 재빌드 뒤 `index_fingerprint()` 를 측정 산출물에 남겨, 어느 색인으로
잰 수인지 나중에 판별할 수 있게 한다.

**영향 범위 예측**: `supply_region` 은 거래소공시에만 있는 필드다.
`exchange_records.jsonl` 만 바뀌고 `holding`·`major`·`periodic` 은 불변이다.
바뀐 레코드는 markdown 에 줄 하나가 늘어난다. BM25 색인은 그 줄을 포함해
다시 세운다.
