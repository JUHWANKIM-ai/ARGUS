## 0. 현재 성능 — **Ablation v2 · 제출 구성 A8** (2026-08-10)

### 🔴 heldout 일반화 낙폭 — 축마다 다르고, 좁아진 것은 개선이 아니다

`evalset/heldout.jsonl` 18문항은 **최종 구성 1회용**이다. v1 에서 `A6` 로 1회 썼으므로
**이번이 2회째**이고, 최종 구성 `A8` 하나로만 돌렸다. 산출물 `artifacts/ablation/v2/heldout/`.

| 축 | 구성 | dev 그리드 | heldout | 낙폭 |
|---|---|---|---|---|
| v1 · dev 36 | A6 | 31/36 (86.1%) | 15/18 (83.3%) | −2.8%p |
| **v2 · dev 72** (이번 판의 축) | **A8** | 61/72 (84.7%) | **15/18 (83.3%)** | **−1.4%p** |
| v2 · `measured 36` (v1 과 같은 문항, **재생**) | A8 | 33/36 (91.7%) | 15/18 (83.3%) | **−8.4%p** |

**판정 — 과적합 신호가 아니다** (임계 −10%p). 다만 두 가지를 함께 적어야 정직하다.

1. 🔴 **낙폭이 −2.8 → −1.4%p 로 좁아진 것은 일반화가 좋아진 것이 아니다.** heldout 쪽 수가
   v1 과 글자 하나 다르지 않다(15/18, 같은 3문항). 좁아진 몫은 **dev 쪽이 내려간 것**이다.
2. 🔴 **가장 나쁜 축은 `measured 36` 의 −8.4%p** 로 임계에 가장 가깝다. v1 과 문항이 같은
   유일한 축이므로 판정은 이 수로 해야 하고, 그 축의 dev 값(33/36)은 **재생**이다.

**heldout 이 새 실패 유형을 내놓지 않았다** — 잔여 3건은 `VERIFY/VERIFY` 2 ·
`RETRIEVAL/MULTI_POINT_QUERY` 1 로, dev 그리드 잔여 실패의 상위 두 종류와 **같은 것**이다.
이것이 낙폭이 작은 이유이고, 동시에 **처방이 dev 와 같다**는 뜻이다.

**누적 지출 12,612원.** 웰컴 크레딧 100,000원의 **12.6%** (내역은 §1 하단).

## 0b. 🔴 Ablation v2 의 핵심 발견 3개

### ① `A0 → A1` 이 **−8.3%p** — v1 의 `+2.8%p` 에서 부호가 뒤집혔다

**기전은 문항 구성이 아니라 문서군 커버리지다.** `A1` 은 정의상 exchange 인덱스
1,469건만 보므로, 그 손실은 문서군 축에서만 드러난다.

```
A0 → A1   exchange  +1건        ← BM25 순위는 인덱스가 닿는 곳에서 제 일을 한다
          major·holding·periodic  −7건
          순 −6건 = −8.3%p 의 전부
```

`A1` 의 `ROUTING` 실패 **39건**(A0 은 0건)은 라우터 버그가 아니다 — arm 정의상 검색이
exchange 로 강제되므로 `parse_trace` 가 문서군 불일치로 읽는다. 실체는
**major·holding·periodic 질의가 검색 단계에서 통째로 떨어지는 것**이고, 그것이 곧 `A1b` 의 Δ 다.

🔴 **"문항이 늘어 뒤집혔다" 는 절반만 맞다.** 그리드 72를 v1 이 실제로 잰 36문항과
증설 36문항으로 갈라 보면 **동일 코호트가 이미 뒤집혀 있다.**

| 구간 | A0 | A1 | Δ |
|---|---|---|---|
| v1 measured 36 | 10/36 | 11/36 | **+2.8%p** |
| **v2 measured 36 (동일 코호트)** | 11/36 | 9/36 | **−5.6%p** |
| **v2 증설 36** | 13/36 | 9/36 | **−11.1%p** |

두 성분이 같은 방향이고 크기가 다르다. 동일 36문항의 몫은 **문항 증설이 아니라 v1→v2 코드
변화**다. 🔴 **어느 커밋이 원인인지는 v2 산출물로 특정할 수 없다** — 특정하려면 커밋별
재측정이 필요하고 그것은 별개 작업이다.

### ② `A8` 은 그리드 Δ 0 · 밸류체인 +16.7%p — 통제 증거는 토큰 전항목 일치

A8 의 성공 기준은 **정답률이 아니라 완결성**이다. 밸류체인 12문항을 세 갈래로 가른다.

| 갈래 | 문항 | A8 | L3 |
|---|---|---|---|
| ① 완전 열거 (A8 의 진짜 겨냥점) | Q-110 Q-114 Q-117 | **2/3** | 0/3 |
| ② 완결성 확인 불가 | Q-116 | 1/1 | 1/1 |
| ③ 이미 닿는 나머지 (깨지면 순손실) | 8문항 | 3/8 | 3/8 |

**③이 안 깨지고 ①에서 2건을 벌었다** — 이것이 A8 을 넣는 근거다. 발주처 hop 은 그리드
88문항에서 **발화 0건**, 밸류체인 12문항에서 **8건** 발화한다. 그래서 그리드 Δ 는
**측정값이 아니라 정의상 0** 이고, 통제 증거는 A5~A8 토큰 **337,603 전항목 일치**다.

🔴 **미발화 4건(Q-108 Q-111 Q-112 Q-117)의 처방은 정반대다** — hop 이 약한 것이 아니라
**라우터가 발주처를 못 알아본 것**이므로, hop 개선이 아니라 노드 이름 인식이 처방이다.

### ③ 처방이 두 번 뒤집힌 Q-065 — 우리 변환은 정확했고 **모델이 10배를 틀린다**

### 🔁 같은 실수를 막는 장치 — `completeness_audit()`

이번 혼선의 원인은 **"7/7 이 어느 스냅샷 기준인지"가 안 적혀 있던 것**이다.
`critic.completeness_audit()` 이 **전제가 선 횟수(`checked`)와 발화 횟수를 분리**해 기록한다.

```
stale_value   checked 1 → 7  (factor 7.0)   ← drifted.  발화는 1 → 1 로 그대로
```

`fire_rate` 의 분모는 **전제가 선 횟수**다 — 전체 문항 수로 나누면 전제가 안 선 문항이 분모에 들어가
**규칙이 저절로 좋아진 것처럼 보인다.** `factor ≥ 2.0` 이면 `drifted` 로 뜬다.

**Recall 을 더 올리면 이 표가 먼저 깨지도록** 스냅샷 기준선을 테스트에 박아 뒀다.

## 2c. Q-022 판정 — **파이프라인 결함이 맞다** (2026-08-09)

Ablation A6 에서 `TOOL` 실패로 잡힌 문항이다. 원문을 확인한 결과:

```
질문   "삼성SDI가 2025년 3월에 결의한 유상증자의 자금조달 목적별 금액과 총 조달 규모"

정답   시설 454,100,000,000 + 타법인 1,546,013,200,000 = 2,000,113,200,000
답변   1,654,940,000,000                ← 체인 최신본 값
```

체인이 **20,001억 → 17,282억 → 16,549억**으로 감소하는데, 파이프라인이 **최신본을 답했다.**

**골든셋 문제가 아니라 능력 부재다.** 질문이 `2025년 3월에 결의한` 으로 **시점을 지정**했는데,
A4 의 체인 hop 이 붙은 뒤 파이프라인이 **항상 최신값으로 수렴**한다. 시점 지정 질의를 구분하지 못한다.

**두 읽기가 모두 테스트되고 있다** — 회귀 문항 **Q-061 이 같은 체인의 최신값**을 묻는다.
따라서 질문 문구를 고치는 것은 **한쪽 능력을 시험에서 빼는 것**이므로 하지 않는다.

→ **필요한 능력**: 질문이 특정 공시·시점을 지정하면 **그 시점 값을 답하고 정정 사실을 부기**한다.
정정이 있는데 시점 지정이 없으면 최신값을 답한다.

✅ **해소** — `A7`(`pipeline._as_of_ym`)로 구현했다. 🔴 **`A7` 은 플래그로 끌 수 없는 무조건
코드**이므로 사다리의 `Δ(A6→A7)` 은 측정값이 아니라 정의상 0 이다. 실효는 42문항 코호트로
따로 쟀다 — **grid +2.8%p · 환각 1→0**. Q-022 는 v2 A8 에서 정답이다.

## 2d. A2 임베딩 하이브리드 — **Δ = 0** (2026-08-10, 사용자 지시로 실측)

v1 에서 "겨냥할 실패 0건"을 근거로 보류했던 arm 을 실제로 붙여 쟀다. **결론은 같고 근거는 훨씬 강해졌다.**

### 모델 — CLOVA Studio 3종을 직접 호출해 확인

| 모델 | 차원 | 1,200자 입력 | 판정 |
|---|---|---|---|
| `clir-emb-dolphin` · `clir-sts-dolphin` | 1024 | **40003 Context length exceeded** | ✗ 512토큰 상한 |
| **`bge-m3`** | 1024 | 200 (1,051토큰) | ✓ 채택 |

정기공시 색인 문자열이 1,200자라 dolphin 2종은 **애초에 못 넣는다.** 외부 임베딩은 쓰지 않았다(G1).

### 전량 임베딩을 막은 것은 **비용이 아니었다**

```
비용   160,547건 · 86.8M토큰 · 8,681원        ← 상한 10,000원 안. 통과
상주   정기공시 전량 float16 307MB            ← 여유 73MB.  ✗
시간   분당 60회 고정창 · 배치 미지원 → 46시간  ✗
```

**분당 60회 고정창**은 실측이다 — 60초 냉각 후 200연타에 앞 60건만 200, 나머지 전부 429.
병렬화하면 오히려 느려진다. → 범위 축소: 정형 3종 전량 3,150건 + periodic 은 **프리필터 통과 후보만**.

**측정 손실은 없다** — 융합이 프리필터 뒤에 있어, 프리필터가 거른 조각은 전량 인덱스가 있어도 후보가 아니다.

### 검색 지표 — 한 칸도 안 움직였다

| arm | 골든 근거 | 전건 | R@1 | **R@5** | 블록 | hop | 스텝 |
|---|---|---|---|---|---|---|---|
| A6 | 59/60 | 35/42 | 41/60 | **0.967** | 143 | 10 | 5 |
| **A2F = A6+dense** | 59/60 | 35/42 | 41/60 | **0.967** | 143 | 10 | 5 |
| A1b | 43/60 | 24/42 | 34/60 | 43/60 | 99 | 0 | 4 |
| **A2 = A1b+dense** | 43/60 | 24/42 | 34/60 | 43/60 | 99 | 0 | 4 |

난이도별·문서군별 전부 동일. 유일한 차이는 근거 글자 **+315자(+0.19%)**.

**dense 가 안 돌아서 0 이 아니다** — 융합 75회, **dense 가 top_k 에 새로 올린 문서 31건**,
그중 **골든 0건**. 이것이 "이 코퍼스에서 임베딩이 왜 안 듣는가"의 직접 증거다.

### 왜 0인가 — 근거 수치

```
① 후보가 없다        검색 75회 중 32회(42.7%)가 후보 1건, 76%가 5건 이하 (중앙값 2)
② BM25 가 이미 먹었다  골든 60건 중 55건 top-3, 41건 1위
③ 미적중 2건이 임베딩 문제가 아니다
     Q-023  체인 길이 7 > MAX_CHAIN_DOCS=6.  골든 5건은 이미 근거에 다 실림
     Q-054  목차 단서 부재 → A3 겨냥점
④ dense 가 31건을 새로 올렸는데 골든 0건 ← 숫자 토큰비 7.5~20% · 표 문자비 0.71~0.93 의 귀결
```

**정답률은 측정하지 않았다** — 검색 지표가 전부 동일하므로 생성을 생략했다. **생성 호출 0회.**
**총 지출 113.4원** (상한의 0.76%). 단가가 10배여도 1,134원이다.

### 판정

**제출 구성에서 A2 는 뺀다.** Δ 0 인데 상주 +9.5MB 와 신규 질의 지연(최초 1회 최대 6분)이 붙는다.
**이 판정은 규정이 아니라 실측이 내렸으므로 G1 이 허용돼도 결론은 같다.**

`dense` 는 사다리 어느 칸에도 켜져 있지 않다. 불허 확정 시 `ablation.DENSE_ARMS` 두 줄만 지우면
**v1 곡선은 숫자 하나 안 바뀐다** — 테스트로 고정했다.

| **periodic 섹션 하강** | F-4 미완 항목으로 남겨 뒀다 | 회수 동일한데 스텝 2배 → **넣지 않는다** (F-8) |
| **Q-065 의 처방** | A5(계산 도구)가 겨냥할 문항 | A5 를 **끄면 맞는다** — 우리 변환은 정확했고 모델이 10배를 틀린다 (§0b ③) |

**진단이 틀린 적도 있다.** EDA 는 정정 체인 실패를 `<TU>` 셀 미독으로 진단했는데,
실제 값은 **표 밖 `<P>` 단락**에 있었다(`<TU>` 에서 발견된 건수: **0**).
커버리지 통계와 실패 원인은 다른 것이었고, 상관을 원인으로 적으면 다음 사람이 엉뚱한 것을 고친다.

**병목은 돈으로 푸는 것이 아니었다.** Phase H 가 지목한 상위 2개를 포함해
5개 병목을 **전부 크레딧 0원**으로 해소했다 — 안 뽑은 값과 안 부른 도구였다.
