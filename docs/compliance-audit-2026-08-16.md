      `except Exception` 으로 감싸지만, **필수 쿼리 누락은 FastAPI 검증이 핸들러 **전에** 걸러
      `422` 를 낸다.** 실측:
      ```
      question 없음      → HTTP 422 {"detail":[{"type":"missing", ...}]}
      question_id 없음   → HTTP 422
      ```
      422 는 5xx 가 아니라 재시도를 부르지 않지만 **5키 계약이 깨진다.**
      → [F-4](#f-4-🟡-쿼리-누락은-200-이-아니라-422-다)

## 6. 발견 — 심각도 순

### F-1 🔴 XSS 서명이 든 질의를 보내면 **발신 IP 가 약 6분간 차단된다**

> **이 절은 초안에서 결론을 두 번 고쳤다.** 처음엔 *"서버가 죽었고 회복하지 못했다"* 로 적었는데
> **둘 다 틀렸다.** 아래가 실측으로 좁혀 간 기록이다. 결론만 읽으려면 「판정」으로.

**① 관측 — 무엇이 일어났나**

```
새 질문 16문항                     16/16 · 200 · 최대 13.5초
계약 가장자리 탐침
    question 누락                  422
    빈 question                    200
    삼성전자 <script>alert(1)</script> & "매출" 100%
                                   🔴 ConnectionResetError (19.2초)
이후 /health                       불통
```

**② 계층을 갈라 봤다 — 앱만의 문제가 아니었다**

```
TCP 80 (HTTP)      🔴 시간초과
TCP 22 (SSH)       🔴 시간초과
ICMP ping          🔴 100% 손실
```

앱이 죽어도 **ICMP 와 SSH 는 죽지 않는다.** 그래서 처음엔 인스턴스 전체가 내려앉았다고 봤다.

**③ 자력 회복했다 — 그것도 두 번, 거의 같은 시간에**

```
1차 불통 → 회복    348초
2차 불통 → 회복    365초
```

🔴 **여기서 첫 결론이 깨졌다.** OOM 이나 크래시면 회복 시간이 들쭉날쭉해야 하는데
**두 번 다 약 6분**이다. 고정 시간은 **해제 타이머**의 냄새다.

**④ 우리 코드는 무혐의다** — 같은 입력을 로컬 전체 경로에 넣었다:

| 단계 | `<script>` 질의 | 3000자 질의 |
|---|---|---|
| `safety.sanitize_question` | 0.000초 | 0.000초 |
| `router.route` | 0.000초 | 0.000초 |
| `query.extract_terms` | 0.000초 | — |
| `tools.search_chunks` | 0.00초 | **0.14초** |

**⑤ 결정적 실험 — 무엇이 방아쇠인지 갈랐다**

서버가 회복된 뒤 변형을 하나씩 보냈다:

| 질의 | 결과 |
|---|---|
| `삼성전자 <b>매출</b> 알려줘` — **꺾쇠·태그 있음** | 🟢 200 · 10.9초 |
| `삼성전자 매출 alert(1) 알려줘` — **`alert()` 있음** | 🟢 200 · 2.8초 |
| `삼성전자 매출 100% & 영업이익` — **`&`·`%`** | 🟢 200 · 4.5초 |
| `삼성전자 <script>alert(1)</script> & "매출" 100%` | 🔴 **연결 리셋 + 6분 불통** |

**판정**

**꺾쇠도, `alert()` 도, 특수문자도 각각으로는 멀쩡하다. XSS 서명 전체를 갖췄을 때만 죽는다.**
자원 고갈은 `<b>` 와 `<script>` 를 **구별할 수 없다.** 그러므로 이것은 서버 자원 문제가 아니라
**네트워크 계층의 서명 기반 차단**이다 — NCP 쪽 보호 장치가 URL 의 XSS 패턴을 보고
**발신 IP 를 약 6분간 블랙홀**에 넣는 것으로 보인다. 정황이 전부 들어맞는다:
연결 리셋 · HTTP·SSH·ICMP 동시 차단 · 일정한 해제 시간 · 서명 특이성.

🔴 **그러므로 앞선 두 서술은 취소한다** — 서버는 죽지 않았고(그 사이 SSH 는 `Permission denied`
를 돌려줬다. 즉 살아 있었다), `Restart=always` 도 이 건과 무관하다.

**⑥ 남은 불확실 — 정직하게 적는다**

**증명하지 못했다.** 서버 로그를 못 읽었다. CONVENTION §8 대로 NCP 는 *"비밀번호는 설정하지
않고 **조회**한다 … 생성 시 발급한 인증키로 조회"* 방식이라 `.pem` 만으로는 SSH 로그인이 안 된다
(`Permission denied (publickey,password)`). 확정하려면 **콘솔에서 비밀번호를 조회해 들어가
`dmesg`·`/var/log/argus.log`·`uptime` 을 보면 된다** — 재부팅 흔적이 없으면 차단설이 확정된다.

**⑦ 🔴 그런데 이것이 왜 진짜 위험한가 — 평가 축과 정면으로 겹친다**

주최측이 보낼 질의는 한글 공시 질문이니 평상시엔 안 걸린다. **문제는 §5 의 평가 지표다:**

> **안전성·신뢰성** — *"개인정보 노출·**부적절 입출력·프롬프트 공격**에 안전한가"*

**평가위원이 공격 질의를 보내 우리 방어를 시험하는 것이 이 지표의 정의다.** 그 질의가
XSS 서명을 띠면 **네트워크가 먼저 그들의 IP 를 끊는다.** 그러면:

1. 우리 애플리케이션 방어는 **작동할 기회조차 못 얻는다** — `AUD-05` 가 증명하듯 실제로는
   인젝션을 잘 막는데, 그 실력을 못 보여 준다
2. 주최측에는 **연결 리셋**으로 보인다 — 방어가 아니라 **장애**로 읽힌다
3. 🔴 **그 뒤 약 6분간 들어오는 모든 질의가 전부 타임아웃**이다. 호출은 순차이고(답변 #1)
   타임아웃 300초 + 재시도 2회이므로, **한 번 걸리면 뒤따르는 문항까지 함께 0점**이 된다

**해야 할 일**

- [ ] 🔴 **사용자 손** — NCP 콘솔에서 **DDoS/IPS·WAF 성격의 보호 설정이 걸려 있는지 확인**하고,
      가능하면 평가 기간 동안 끄거나 주최측 발신 IP(`TBD-4`)를 예외로 넣는다.
      이것이 근본 대책이다 — 우리 코드로는 못 막는다(네트워크가 우리보다 앞에 있다)
- [ ] 🔴 콘솔에서 비밀번호를 조회해 SSH 로 들어가 `uptime`·`dmesg`·`/var/log/argus.log` 로
      **차단설을 확정**한다. 재부팅 흔적이 있으면 이 절의 판정을 다시 뒤집어야 한다
- [ ] **외부 감시** — 다른 곳에서 `/health` 를 주기적으로 찔러 알린다.
      IP 가 차단되는 종류의 고장은 **서버 안에서는 절대 못 잡는다**
- [ ] 제안서 §9(규정 준수)에 **이 사실과 대응을 적는다** — 안전성 축에서 우리 방어가
      네트워크에 가려질 수 있다는 것은 평가위원이 알아야 공정하다

### F-2 🔴 근거 표시가 실질 답변 8건 중 3건뿐이다

CONVENTION §3 `R2` 는 *"모든 답변에 근거 공시를 표시"*, §5 8지표의 마지막도 **근거 표시**다.

`근거\s*:.*?접수번호\s*\d{14}` 로 대조:

|---|---|---:|---|
| AUD-08 | ✅ | 1 | 🔴 없음 — `(근거: 단일판매ㆍ공급계약체결, 2025-07-28, 20250728800035)` 에 **"접수번호" 라는 말이 없다** |
| AUD-09 | ✅ | 1 | ✅ |
| AUD-10 | ✅ | 2 | ✅ |
| AUD-11 | ✅ | **0** | 🔴 **`(근거: 각 보고서별 상세내역 참조)`** |

🔴 **기전까지 잡혔다.** `think_trace` 가 보여 준다:

```
AUD-11: … | 근거 표기 누락 — critic 호출 | critic supported=True reason=모든 수치가 근거에서 확인되며 …
AUD-08: … | 근거 표기 누락 — critic 호출 | critic supported=True reason=… 접수번호를 포함한 근거 표기도 존재합니다.
```

**탐지는 정확히 발화한다.** 그런데 처분으로 부르는 `critic` 은 *"근거가 답을 뒷받침하나"* 를

그대로 나간다. `AUD-08` 에서는 critic 이 *"접수번호를 포함한 근거 표기도 존재합니다"* 라고
**정규식과 정반대로** 말했고, critic 쪽이 이겼다.

**실질 답변 8건 중 5건이 규약 형식을 놓쳤고, `근거 표기 누락 — critic 호출` 이 발화한 뒤에도
critic 이 전부 `supported=True` 로 통과시켰다.**
이것은 계획서가 `v3` 에서 적은 *"탐지 100% · 교정 0%"* 와 **같은 병**이 인용 축에서 되풀이된 것이다.
계산 축은 `A20r` 로 닫았는데 인용 축은 안 닫혀 있다.

**고칠 자리** — `A20r` 이 이미 갖고 있는 **재생성 1회** 경로에 인용 실패를 태우면 된다.
`verify` 가 `provenance` 로 재생성을 부르는 것과 같은 자리다 (`AUD-11` 이 실제로 그렇게 돌았다).

- [ ] 🔴 인용 누락을 `critic` 이 아니라 **재생성 사유**로 넘긴다
- [ ] `CITATION_RE` 를 완화할지(접수번호 14자리만 있으면 통과) 프롬프트를 강화할지 **재서 정한다**

### F-4 🟡 쿼리 누락은 200 이 아니라 422 다

- [ ] 프롬프트에 *"거절할 때 법령·규정을 지어내지 말 것"* 을 더한다

### F-7 ℹ️ critic 의 판정문이 사용자 답변에 그대로 붙는다

`AUD-05`·`AUD-06`·`AUD-07`·`AUD-14` 의 답변 끝에 이런 문장이 붙었다:

> (주의: 근거 검증을 통과하지 못했습니다 — 답변이 주어진 근거 내에서 이루어지지 않고 있으며 …)

**결함으로 판정하지 않는다.** §5 의 **정보한계 대응** 축에서는 오히려 정직한 신호이고,
평가위원이 *"스스로 한계를 고지한다"* 로 읽을 수 있다. 다만 내부 검증 용어가 그대로 노출되는
것이라 **읽는 이에 따라 갈릴 수 있다** — 판단이 필요한 자리라 적어 둔다.

### F-8 ℹ️ 충분성 게이트가 정확한 단일 근거를 "부족" 으로 본다

`AUD-13`·`AUD-16` 의 `think_trace`:

```
hop=0 … n=1 top_score=89.010 ids=exchange_20260225801974 | verdict=insufficient reason=few:1<2
hop=1 relax_period … n=1 … | verdict=insufficient reason=few:1<2
hop=2 corp_only  … n=4 ids=…20240424…,…20240726…,…20260225801974,…20241220800005 | verdict=sufficient
```

**정답 레코드를 hop 0 에서 89.0 점으로 이미 찾았는데** *"후보가 2건 미만"* 이라는 이유로 두 번 더
검색해 **2024년 무관 레코드 셋을 근거 칸에 끌어들였다.** 두 문항 다 결국 맞혔으니 손해가
확정된 건 아니지만, 근거 희석은 `v3`·`v4` 가 반복해 확인한 실패 기전이다.

- [ ] `top_score` 가 충분히 높은 단일 근거는 `few:1<2` 를 면제할지 **재서 정한다**
      (측정 없이 바꾸지 않는다 — 이 저장소의 원칙이다)
