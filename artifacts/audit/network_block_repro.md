자원 고갈은 `<b>` 와 `<script>` 를 구별할 수 없다 → **네트워크 계층의 서명 기반 차단**이다.

## 🔴 확정 (2026-08-16 오후) — **차단은 NCP 가 아니라 우리 캠퍼스 망이다**

### ① 서버 쪽 증거 — 서버는 관여하지 않았다

`argus_ed25519` 키로 접속해 확인했다 (`~/.ssh/config` 의 `Host argus`).

```
uptime          1일 17시간      ← 불통 구간에도 재부팅 없음
NRestarts       0              ← 서비스 재시작 0회
OOM             0건
"script" 요청   로그에 0건      ← 그 요청은 서버에 닿지도 않았다
/answer 42건    전부 166.104.16.55 (우리) · 그중 422 3건 = 가장자리 탐침
```

### ② 관측점을 바꿨더니 갈렸다 — **결정적**

같은 페이로드를 **캠퍼스 밖**(ARGUS 서버 자신)에서 보냈다:

| 발신 | 페이로드 | 결과 |
|---|---|---|
| `166.104.16.55` (한양대) | `<script>alert(1)</script>` | 🔴 연결 리셋 + 약 6분 불통 |
| `223.130.129.131` (NCP) | **같은 페이로드** | 🟢 **200 · 3.0초 정상 처리** |

되꺾임(hairpin)이 아니다 — 서버 로그의 발신 IP 가 사설 `192.168.1.6` 이 아니라
**공인 `223.130.129.131`** 로 찍혔다. NAT 를 거쳐 밖으로 나갔다 들어왔다는 뜻이고,
**그 경로에서 막히지 않았다.**

### ③ NCP 콘솔에 차단 기록 없음 (사용자 확인)

`Event` 메뉴에 아무 기록이 없다. ②와 합치면 NCP 는 관여하지 않았다.

## 판정

**한양대 망의 나가는 쪽 검사 장치**가 URL 의 XSS 서명을 보고 목적지를 약 6분간
블랙홀에 넣는다. 서버도 NCP 도 정상이었다.

🟢 **평가에 미치는 영향은 사실상 없다.** 평가 때 주최측은 **자기 망에서 우리 서버로**
접속하므로 우리 캠퍼스 검사 장치는 그 경로에 아예 없다.

🟡 남는 위험은 하나뿐이고 우리 손 밖이다 — 주최측 망에도 비슷한 장치가 있고 그들이
`§5` 안전성 시험으로 공격 서명 질의를 보낼 경우, **그들 쪽에서** 막힐 수 있다. 그것은
모든 팀에 똑같이 적용된다.

🔴 **우리가 개발 중에 알아야 할 것**: 캠퍼스에서 공격 서명 질의로 우리 서버를 시험하면
6분간 접속이 끊긴다. 그때 **서버가 죽은 것이 아니다.** 이 문서를 먼저 볼 것.

## 종전에 남겼던 불확실 (해소됨)

**증명하지 못했다.** 서버 로그를 못 읽었다 — NCP 는 인증키로 **콘솔에서 비밀번호를 조회**하는
방식이라(CONVENTION §8) `.pem` 만으로는 SSH 로그인이 안 된다
(`Permission denied (publickey,password)`). 다만 그 거절 응답 자체가 **차단 해제 후에는 SSH 데몬이
살아 있었다**는 증거다.

**확정 방법** — 콘솔에서 비밀번호를 조회해 접속한 뒤:

```bash
uptime                              # 재부팅 흔적이 없으면 차단설 확정
systemctl show argus -p NRestarts   # 재시작 0 이면 앱은 죽지 않았다
dmesg -T | grep -i "oom\|kill"      # OOM 흔적
tail -100 /var/log/argus.log        # 그 시각 요청이 도달했는지
```

**재부팅·재시작 흔적이 나오면 이 판정을 뒤집어야 한다.**
