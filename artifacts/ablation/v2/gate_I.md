**두 성분이 같은 방향이고 크기가 다르다.** 동일 36문항에서 v1 은 `+2.8%p` 였는데 v2 는 음수다 — 그 몫은 **문항 증설이 아니라 v1→v2 코드 변화**다. 🔴 **어느 커밋이 원인인지는 v2 산출물로 특정할 수 없다** (v1 이후 파이프라인이 여러 트랙에서 바뀌었고, 이 트랙은 arm 플래그만 변수로 뒀다). 특정하려면 커밋별 재측정이 필요하고 그것은 별개 작업이다.


## 13. 이 표를 읽을 때 주의할 것

- **`Δ(A5→A6)` · `Δ(A6→A7)` · `Δ(A7→A8)` 은 88문항 그리드에서 정의상 0 이다.** A6(Verifier)은 경고만 붙이고 답을 갈아엎지 않으며(LLM 0회), A7 은 플래그가 없고, A8 의 발주처 hop 은 그리드 88문항에서 발화가 0건이다. 셋 다 **생성 프롬프트가 A5 와 바이트 동일**임을 LLM 0회로 확인했다.

- `DATA_LIMIT` 은 정답률 분모에서 뺀다. 정보한계 문항은 `answerable=false` 로 따로 세고, 지어내면 `HALLUCINATION` 으로 잡는다 (§4).

- 근본 원인 히스토그램은 **그리드 기준**이다 (`root_cause_histogram_grid`). 전체 88 기준을 쓰면 회귀 트랙이 섞여 겨냥 건수가 부푼다.

- 🔴 **`latency_s_mean` 을 '평균 응답 시간' 으로 인용하지 않는다.** 그 값은 응답 파일에 저장된 벽시계 시간의 평균이고, 그 파일을 만들 때 요청 캐시가 적중했다면 파이프라인이 ~1ms 에 끝난 시간이 저장돼 있다 — 실측으로 A0 은 3.73초(88 중 28건만 <0.5s)인데 **A5·A8 은 0.02~0.03초**(88/88 캐시 적중)다. 기울기가 언제나 **빠르게 보이는 한 방향**이라 그대로 인용하면 두 자릿수 배로 틀린다. `summary.json` 에서는 이름을 `latency_s_mean_recorded` 로 갈고 경고를 붙였다. 진짜 응답 시간은 캐시 없이 다시 재야 나온다 (제출 후).

- **A2·A3 는 v1 에서 실측으로 제외했다** — A2 는 dense 가 top_k 에 31건을 새로 올렸는데 골든 0건, A3 는 겨냥점 1건. 다만 **A3 겨냥점의 종류가 바뀌었다**: v1 의 `WRONG_SECTION` 은 해소됐고, 신규 섹터에서 `RANKING/LOW_RANK` (Q-094, rank 8·9) 가 새로 섰다.


## 14. heldout 최종 측정 — 일반화 낙폭

🔴 **2회째 사용이다.** 앞선 사용: 1회 A6 15/18. 이번이 두 번째이자 최종 구성 `A8` 1회다. arm 별로 돌리지 않았다 — 그러면 heldout 이 개발셋이 되고 되돌릴 수 없다. 원장 `heldout_run.json` 이 `artifacts/` 아래 **어디에라도** 있으면 러너가 유료 실행을 거부한다 — `--out` 으로 우회되지 않는다 (`scripts/ablation.py::assert_heldout_unused`).

🔴 **낙폭은 축마다 다르게 나온다.** dev 쪽 분모가 v1 36 → v2 72 로 늘었으므로 세 축을 다 낸다 — 하나만 적으면 그것이 '그 낙폭' 으로 굳고, 가장 유리한 축이 뽑히기 쉽다. heldout 쪽 18문항만 두 판에서 동일하다.

| 축 | 구성 | dev 그리드 | heldout | 낙폭 |
|---|---|---|---|---|
| v1 · dev 36 | A6 | 31/36 (86.1%) | 15/18 (83.3%) | -2.8%p |
| **v2 · dev 72 (증설 후 · 이번 판의 축)** | **A8** | 61/72 (84.7%) | **15/18 (83.3%)** | **-1.4%p** |
| v2 · measured 36 (v1 과 같은 문항 · dev 쪽이 **재생**) | A8 | 33/36 (91.7%) | 15/18 (83.3%) | **-8.3%p** |

🔴 **비교 축.** v1 낙폭은 **A6 시점 · dev 분모 36**, v2 낙폭은 **A8 · dev 분모 72** 다. heldout 18문항만 두 판에서 동일하다. 두 낙폭의 차를 Δ 로 읽지 않는다.

🔴 **가장 큰 낙폭은 `measured 36` 축의 -8.3%p 다** — dev 쪽을 v1 과 나란히 읽는 유일한 축이므로 **판정은 이 수로 해야 한다.** 다만 이 축의 dev 값은 재생(replay)이다 — 답변이 A7 과 바이트 동일이라 독립 측정이 아니다 (§12).

🔴 **정답 집합이 v1 과 문항 단위로 완전히 같다** — 15/18 (83.3%) 이고 틀린 문항도 같은 Q-021, Q-057, Q-058 다. 그러므로 `-2.8%p → -1.4%p` 로 낙폭이 좁아진 몫은 **일반화가 좋아진 것이 아니라 dev 쪽 정답률이 내려간 것**이다 (문항 증설로 84.7%). 좁아진 낙폭을 개선으로 읽으면 안 된다.

🔴 **그러나 이것은 재생이 아니다 — 독립 유료 측정이다.** 답변 텍스트가 **18/18 전부 다르고**(v1 A6 시점 코드와 프롬프트가 달라 요청 캐시 적중 0) 토큰도 79,326 → 95,984 로 늘었다. 정답 집합만 같다. 그래서 이 15/18 은 **이 판에서 유일한 독립 측정치**이고, `measured 36`(dev 쪽이 재생)과 성격이 다르다.

**판정** — 과적합 신호 아님 — 가장 나쁜 축 -8.3%p > 임계 -10.0%p. 🔴 여유는 1.7%p 뿐이고 최악축은 n=36 이라 1문항 = 2.8%p — **dev 가 1문항만 더 맞아도 임계를 넘는다**

🔴 **이 게이트는 이번이 마지막 사용이다.** heldout 을 다시 못 재므로 낙폭의 분자가 83.3% 에 영구 고정된다. measured 36 은 n=36 이라 1문항 = 2.8%p — dev 33→34 만으로 낙폭이 -11.1%p 가 되어 임계(-10%p)를 넘는다. 성능 향상과 과적합이 같은 수에서 나오는 지표는 지표가 아니다. 이후 회귀 10 · 밸류체인 12 로 감시한다.
